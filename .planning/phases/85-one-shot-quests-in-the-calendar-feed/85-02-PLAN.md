## The open calls 85-CONTEXT.md left to Claude's Discretion, resolved here

Each of these was genuinely open. Each is decided now, with its rationale, so no downstream task re-opens it.

**1. Where the one-shot narrowing happens.** In `CalendarSubscriptionService.GetFeedAsync`, by filtering the `memberships` list that method already reads for `memberGroupIds` and `boardNamesById`. No new database read. `IBoardTypeResolver` is not touched: it answers for the *active* group and returns null by construction on a session-less request. This single derived set encodes membership and board type simultaneously, because it is a subset of the fresh per-request membership read — there is no way to satisfy one predicate without the other.
— **Reversibility: reversible.** One derived list in one method; removing it restores every-board reach at the next poll, with no stored data and no migration.

**2. Query shape.** A single query rooted at `Quests`, with the seat condition and the Dungeon Master condition combined by a logical OR *inside the same `Where`* as the board-id containment — not a literal `Union()` of two separately rooted queries, and not two materialized lists concatenated in C#.

Rationale, and this matters: `GroupRepository.GetGroupsForUserAsync` is the only in-repo, production-proven precedent for an `Any()`-in-`Where` predicate translating against SQL Server, and a repo-wide search for `.Union(` returns zero hits, so the union shape has no translation precedent here at all (85-RESEARCH.md Pitfall 1).

**D-01's mandatory dedup requirement is satisfied structurally, not dropped.** D-01 states a distinct-by-quest-id step is mandatory because two branches matching one quest would emit two VEVENTs sharing one UID. Rooting the query at `Quests` means each quest row is visited at most once no matter how many of the OR's operands it satisfies, so the duplicate cannot be constructed rather than being constructed and then removed. This is a conversion of the requirement into a structural property, and it is pinned by a test in plan 85-03 (a reader who is both the Dungeon Master and the holder of a confirmed seat on one quest yields exactly one VEVENT).
— **Reversibility: reversible.** Output scoping only.

**3. Membership and board type as two independent predicates.** Both apply, and both apply inside the same `Where` as the seat-or-Dungeon-Master OR. Composing the Dungeon Master branch as a separate query and concatenating would let it escape the board-id containment — that is `T-85-03`, rated high.
— **Reversibility: reversible.**

**4. `CalendarFeedSource` gains a `Quest` member.** `BuildUid` is not touched: it already derives the identifier from the member's own name.
— **Reversibility: reversible.** An additive enum member; the identifier text is derived, not stored.

**5. `CalendarFeedEntry`'s shape for a source with no vote.** The vote-suffix branch in `BuildSummary` is gated on the entry's source being an event *before* the availability value is consulted at all. It is not solved by having the quest projection set a "safe" availability value, because the availability enum's zero-valued default is the declined case — an entry constructed without setting it renders a declined marker today. Gating on source removes the landmine for every present and future construction site rather than relying on each one remembering.
— **Reversibility: reversible.** One conditional in a pure function.

**6. The window comparison's time basis — stated, not silently mixed.** The window bounds stay exactly what Phase 84 computes: a `DateOnly` derived from `timeProvider.GetUtcNow().UtcDateTime`, unchanged. They are widened to `DateTime` at the repository boundary using the first instant of the start day and the last instant of the end day, and compared against `FinalizedDate`, which `PROJECT.md` documents as stored in **server local time**.

This deliberately compares a UTC-derived bound against a server-local value. At a window measured in months, the host's UTC offset (one to two hours for the deployment timezone) can only move a quest across a bound within a couple of hours of the boundary itself. The impact is accepted as negligible and is recorded here rather than left implicit. **The underlying server-local-time storage is not fixed by this phase** — it is a standing, separately tracked known issue and is out of scope.
— **Reversibility: reversible.**

**7. The new session-length option's validation.** A new integer option, four by default, validated in the same refuse-to-start predicate the existing bounds use, with the registration's failure message extended to name it. A value below one hour stops startup rather than failing per request.
— **Reversibility: reversible.** An additive option with a code default, so a deployment with no matching configuration section still works.

**8. Ordering of the merged document.** The two entry lists are concatenated and then ordered by date, then start time, then source, then source identifier.

Start time is ordered **without** substituting a sentinel for the absent value, so an entry with no start time sorts before the timed entries on its day — which is exactly the relative order the shipped event query already produces, since the database orders a null start time first too. Substituting a maximum-time sentinel would silently reverse the shipped ordering of all-day entries against timed ones and change the document — and therefore the entity tag — for every existing subscriber on the first poll after deployment, for no benefit. Quests always carry a real start time, so they are never in the null bucket. Source is the third key so that at an identical date and time an event precedes a quest deterministically; source identifier is the final tiebreak, which for an events-only feed is the same final tiebreak Phase 84 used.

The consequence, and it is an acceptance criterion in plan 85-05: **a feed with no qualifying quest is byte-identical to the document the event-only pipeline produced for the same data.**
— **Reversibility: reversible.** A sort expression.

## Assumption delta — pluralization

**Detector signals:** "second source", "also carries", "alongside". A second source is being introduced where there was one.

**The noun that is now primary:** *the calendar feed entry, of which an event is one variant.* Not "the event feed."

**Decision: `promote`.**

**Rationale.** Phase 84 already named the generalized noun in two of the three places that matter — `CalendarFeedSource` exists as an enum with an event member, and `BuildUid` already derives the identifier from whichever member it is handed, so identity was generalized from the start. What stayed singular is the *rendering* layer: the timed branch hard-codes an event's one-hour block as a literal, and the title rule consults an event-only availability field unconditionally. This plan promotes both:

- duration moves off the writer as a literal and onto the entry as data, with a default that leaves every existing event call site and unit test byte-identical;
- the availability suffix is gated on the entry's source before the field is read at all.

After this plan, every field the writer consults is either genuinely shared across sources or explicitly source-gated.

**What is deliberately *not* promoted, recorded as accepted debt:** the availability field itself stays physically on the shared entry type rather than moving into a per-source payload or a type hierarchy. It is now unreachable for a non-event source, so the *behavioural* risk is closed, but the type still carries a field that is meaningless for one of its two sources.

**What would force a later full promote:** a third source that needs a source-only field of its own. At that point the shared entry type would carry three mutually exclusive optional fields and three source gates in the writer, and the correct move becomes a per-source payload rather than a wider flat record. One source-only field is a smell; three is a design.

**Invariant test encoding the generalized intent** (required, not optional — Task 3): a theory over **every** availability value, asserting that a quest-sourced entry renders a title terminated immediately after the quest title, with no appended answer. A future phase that reintroduces the singular assumption — by dropping the source gate, or by adding a fourth availability value whose suffix is non-empty — goes red immediately rather than shipping a wrong marker to every subscriber's phone.
</assumption_delta_decision>

## Known gap, stated rather than carried silently

**The integration suite cannot prove this query translates to SQL Server.** The shared harness backs every suite with the EF Core in-memory provider, which evaluates every predicate as ordinary in-memory enumeration. The new seat-or-Dungeon-Master disjunction over a navigation collection, the board containment over an id collection, and the filter bypass interacting with the signup entity's own board-navigating filter are all exercised only in memory. Green facts here are facts about this application's own scoping logic, not about relational translation.

**This phase defers closing that gap, for the third time, deliberately.** Phase 82 named it and left it open; Phase 84 named it and left it open; this phase does the same. The reasons, stated so a later reader can weigh them rather than guess:

- Closing it means standing up a relational test project against a real SQL Server instance — a new test infrastructure, not a new test. That is a larger piece of work than this entire phase, and folding it in would triple the phase and put an infrastructure change on the critical path of an output-scoping change.
- The risk this phase adds on top of the inherited one is small and bounded: the new predicate's only unprecedented element is the disjunction, and its `Any()`-in-`Where` half copies the shape of `GroupRepository.GetGroupsForUserAsync`, which has run against the production database since it was written.
- The failure mode is loud, not silent: an untranslatable predicate throws at first request with an explicit client-evaluation message, rather than returning wrong rows.
