<objective>
Prove the two rules that govern a quest's *presence over time*: it disappears silently when it stops qualifying, and it lives inside the same rolling window events already use.

Purpose: these are the rules a subscriber experiences rather than reads. Every one of them is expressed purely as a query predicate, which means every one of them can be dropped without breaking a build and without failing any fact that only ever fetches once. The disappearance facts are therefore written as transitions — fetch, change one thing, fetch again — because two separate facts proving two end states would both stay green against a feed that simply never updates.

Output: five behavioural facts on the live feed address, all in the file the tracer created.
</objective>

Every one is a **transition**: seed a qualifying quest, mint a subscription, fetch and assert the quest is present, change exactly one thing through the seeding context, fetch the same address again, and assert on the second body. Two fetches in one test body, one subscription, one change.

**Fact one — un-finalizing and deleting.** Cover both in one fact if the class's helpers make it clean, or two if not; either is acceptable, but each change must be its own before-and-after pair rather than two changes applied at once.

Seed a finalized quest the reader holds a confirmed seat on. Fetch; assert present. Clear the quest's finalized flag and its finalized date. Fetch; assert the title and the identifier are both absent and the event-opener count is zero. Then, for the delete half, seed a second qualifying quest, fetch, assert present, delete the quest row outright, fetch, assert absent.

On each second body, additionally assert that the document carries **no cancellation status property at all** — not for this quest and not anywhere. Assert on the absence of any status property in the whole body rather than on a particular status value, because the decision is that no tombstone is emitted, not that a specific tombstone value is avoided. Comment the accepted cost this locks in, in plain language: a cancellation reaches the subscriber only as a silent disappearance, which is most acute for a called-off game night, and a reader is unlikely to notice an entry they are no longer looking for.

**Fact two — the seat goes away.** Seed a finalized quest with a confirmed seat for the reader. Fetch; assert present. Delete the signup row. Fetch; assert absent with a zero event-opener count. This is distinct from 85-03's waitlist fact, which flips the confirmed-seat flag on a surviving row — here the row itself is gone, which is what withdrawing from a quest actually does.

**Fact three — the finalized date moves.** Seed a finalized quest with a confirmed seat, finalized on a date comfortably inside the window. Fetch; capture the quest's identifier line and its start line from the body. Move the finalized date to a different date still inside the window. Fetch again and assert two things together: the start line now names the new date, **and the identifier is byte-identical to the one captured from the first fetch**.

That second assertion is the load-bearing one and deserves a comment explaining it: an identifier that changed between fetches would make every subscriber's phone accumulate a fresh copy of the session on every reschedule instead of updating the existing entry in place, and nothing server-side would show it.

Then move the finalized date to a date outside the window, fetch a third time, and assert the quest is absent — which covers the fourth exit route and connects this fact to the window facts in Task 2.

Write **no** fact about a closed quest. Closing is campaign-only and is rejected on a one-shot board, so it is unreachable for every quest this phase can emit; a fact asserting behaviour for it would be asserting on dead code. Record that reasoning in a short comment near these facts rather than leaving its absence to look like an omission.

**Fact one — the backward bound.** Read the configured month counts from the options helper. Seed two finalized quests on one one-shot board, both with a confirmed seat for the reader: one finalized comfortably inside the backward bound, and one finalized comfortably outside it. Fetch once and assert the inside quest's title is present, the outside quest's title is absent, and the event-opener count is exactly one.

**Fact two — the forward bound.** The same shape against the forward bound: one quest comfortably inside, one comfortably outside, one fetch, present-absent-and-count.

Two things about how the dates are chosen, both of which need to be explicit in the fact and in a comment.

First, derive every date from the configured month counts read out of the running host, never from a literal number of months. A fact that hard-codes three months back stops testing the bound the moment the default changes, and silently passes.

Second, place each date **comfortably** on its side of the bound — a day or more clear of it, not an hour. Comment why: the window bounds are derived from a coordinated-universal clock while the quest's finalized date is stored in server local time, so a date within the host's offset of a bound is genuinely ambiguous by design. That ambiguity is a recorded, accepted decision rather than a defect, and a fact that sat on the boundary would be flaky for a reason the failure message would never reveal. Do not write a fact that probes the exact boundary instant.

Use one fetch carrying both quests per fact rather than two fetches of one quest each, so a predicate that lost the window clause entirely fails on the count as well as on the absence.

Finally, add one assertion to whichever of these two facts is more natural: that the configured month counts the fact read are the same values the event window facts in the shipped suite use — that is, that no second pair of knobs came into existence for quests. The cheapest form of this is to assert the options object exposes exactly one backward bound and one forward bound and that the fact used them; if the class shape makes a stronger assertion available, prefer it.
