<objective>
Prove the two scoping rules that this phase's whole security argument rests on — membership and board type, applied independently and both — prove the drop-and-log branch that exists for the case where they somehow fail, and prove the merged document's ordering including the guarantee that an events-only feed is unchanged from what Phase 84 shipped.

Purpose: this phase writes the second cross-board read in the entire codebase, and serves it to an unauthenticated machine reader holding only a bearer address. A leak here has nobody to notice it — no rendered page a person looks at, no error, just wrong lines in a document a phone silently absorbs. The ROADMAP names collapsing membership and board type into one filter as a primary risk precisely because a query that satisfies one and drops the other looks correct in every single-board test. Every fact in this plan is therefore built around a *second* board with an *opposite* expected outcome in the *same* fetch, because absence alone cannot distinguish "correctly scoped" from "accidentally scoped to nothing".

Output: four behavioural facts on the live feed address, a new unit suite that reaches the drop-and-log branch the real repository cannot trigger, and the byte-identical guarantee that closes the events-keep-their-reach prohibition.
</objective>

**Fact one — board type narrows quests and only quests.** Seed two boards the reader belongs to: one one-shot, one campaign. On the campaign board seed a finalized quest with a confirmed seat for the reader **and** an event with a signup row for the reader. On the one-shot board seed a finalized quest with a confirmed seat for the reader. Fetch once.

Assert four things. The one-shot board's quest title is present. The campaign board's quest title is absent. The campaign board's event title **is** present. And the total event-opener count is exactly two — the one-shot quest and the campaign event.

That third assertion is the whole point and deserves its own comment: the previous phase gave events every board's reach, this phase narrows quests only, and a change that retroactively restricted events to one-shot boards would satisfy every other assertion in this suite while quietly emptying half of every existing subscriber's calendar. **Fact two — a campaign quest the reader runs is still out.** Same two-board setup, but the campaign board's quest is owned by the reader as Dungeon Master with no signup row. Assert it is absent and the one-shot board's quest is present.

This is deliberately the same scenario as fact one from a different route in, because the Dungeon Master route is the one that can escape board scoping if the two conditions are ever composed as separate queries rather than one predicate. Comment it as such, in plain language: this fact exists because a second way into the feed is a second way to bypass a filter that is not applied to both ways at once.

**Fact three — a board the reader never joined.** Seed a second one-shot board the reader is **not** a member of, carrying a finalized quest with a confirmed seat row for the reader — an impossible state in production, seeded deliberately so the fact tests the board predicate rather than the seat predicate. Fetch once; assert the member board's quest is present, the non-member board's quest is absent, and the event-opener count is exactly one.

Seeding the contradictory row is the point: without it, a query that scoped on seat alone and ignored boards entirely would still pass, because in normal data a non-member has no seat.

**Fact four — leaving a board.** Seed a one-shot board the reader belongs to with a qualifying quest. Fetch; assert present. Remove the membership row. Fetch the same address again; assert absent with a zero event-opener count.

A normal, correctly scoped fetch must produce no error — the drop-and-log branch is for a predicate that has gone wrong, and a re-check that fires on healthy data is a re-check that will be ignored when it matters.

Across all four facts, seed board ids distinct from the default seeded board so each fact controls its own board names, and clear the active board before every fetch so each fact proves the path does not lean on one.
