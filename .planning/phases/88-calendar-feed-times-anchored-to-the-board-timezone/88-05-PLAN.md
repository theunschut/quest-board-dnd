<objective>
Close gap G-88-4 at its root on one real path first: give every event and quest a stored revision, raise it in the store on every save that changes what the calendar feed shows, and have the feed publish it — so a rescheduled quest goes out under the same UID with a higher `SEQUENCE` and a later `DTSTAMP`, which is the signal a revision-comparing calendar client needs before it will replace the copy it holds. Then prove the store-side rules field by field and close the one hole a store-side hook has: writes that bypass the change tracker.

Purpose: the UAT diagnosis found every entry written with `SEQUENCE:1` and `DTSTAMP` = `CreatedAt` forever, so after a reschedule only `DTSTART`/`DTEND` differ and a client ordering revisions by sequence then stamp (RFC 5546 §2.1.5) keeps its stale copy. RFC 5545 §3.8.7.2 defines `DTSTAMP` in a method-less calendar as the time the entry was last revised, so the creation time is wrong after any edit. The operator locked the fix (planning_context decisions 1–5): an EF Core migration adding a per-entry revision to `Events` and `Quests` that also bumps every existing row once (every entry goes out as `SEQUENCE:2`, repairing the UAT test-4 entry), a revision that rises on every feed-visible write, `DTSTAMP` from the last revision time as a real UTC instant with the WR-02 `SpecifyKind` labelling, and the defect-pinning tests rewritten on purpose. D-07's one-way rule (never below 1, never back down) and D-08's UID stability both stand.

Output: the migration, the stamper wired into `QuestBoardContext`, the revision-carrying feed entry, a writer that publishes it, the rewritten reschedule fact, the stamper's unit proofs and the write-seam guard.
</objective>

<recorded_choices>
Decisions the operator left to the planner, made once here so every later gap plan inherits them:

1. **Mechanism — a store-side hook inside `QuestBoardContext`, not explicit bumps at each write path, and not a registered `SaveChangesInterceptor`.** Operator decision 3 asked which is more robust. The hook wins on three counts:
   - *Coverage.* It covers every write path that exists today — `BaseRepository.UpdateAsync`'s map-over-tracked-entity (the events edit form, a board rename), `EventRepository.ApplyTemplateToOccurrencesAsync`, `QuestRepository.FinalizeQuestAsync`/`OpenQuestAsync`/`UpdateQuestPropertiesWithNotificationsAsync` — and every path added later, with nothing at the call site to forget.
   - *Precision.* It compares each property's original value with its current one, so it bumps only when a feed-visible value really changed. Explicit bumps would need their own "did it change" logic at every path, or they would bump when a DM re-saves an unchanged form or edits only a description. That would break the operator's rule that an unedited entry stays byte-identical, and with it the ETag/304 behaviour.
   - *Placement.* It sits in the context's own `SaveChanges`/`SaveChangesAsync` overrides rather than in an interceptor. `WebApplicationFactoryBase` removes every EF registration and calls `AddDbContext` again with no interceptors, and about twenty unit tests call `new QuestBoardContext(...)` directly. An interceptor would silently vanish on both paths; an override cannot.
   - *Blind spot.* A hook cannot see writes that bypass the change tracker (`ExecuteUpdate`, raw SQL, `Attach`/`Update` of a detached entity). None exist in production code today, so Task 2 pins that with a guard test whose allowlist is empty.
2. **Column names — `FeedRevision` (int) and `FeedRevisedAt` (UTC `DateTime`) on both entities.** A bare `Revision` would read as a general row version, and a future contributor would expect a description edit to raise it. The prefix says the value is the row's revision *as a calendar entry*. The store owns both columns: the entity-to-domain map carries them out, and the domain-to-entity maps ignore them.
3. **Values.** A new row starts at revision 1 with `FeedRevisedAt` = `CreatedAt`, so a never-edited entry still publishes the `SEQUENCE:1` and stamp it always had. The migration raises existing rows from 1 to 2 and stamps them with `SYSUTCDATETIME()`, because the migration *is* their revision. `FeedRevisedAt` never moves backwards: under clock skew between the database server and the app host it keeps the stored value, and the sequence still rises.
4. **Feed-visible fields.** Events: `Title`, `Date`, `StartTime`, `CancelledAt` and `GroupId`. Quests: `Title`, `FinalizedDate`, `IsFinalized` and `GroupId`. `CancelledAt` and `IsFinalized` are included because they decide whether the entry is in the feed at all. A restored event, or a quest reopened and then finalized again (named in operator decision 3), comes back under the same UID and must carry a higher number than any copy a client may still hold. `GroupId` is included because the board name prefixes `SUMMARY`. A board *rename* has the same effect and is added in 88-07. The quest session length and the board zone are configuration, not stored rows, so they are out of reach of a per-row revision; that is a deploy-time change the operator makes knowingly.
5. **Planner-decided in later plans, recorded here for traceability.** `LAST-MODIFIED` is emitted equal to `DTSTAMP` (88-08). A reader's own availability answer moves only that reader's stamp, not the shared sequence (88-06, with its reasoning). A board rename raises every entry on the board (88-07).
6. **Why the tracer spans many files.** Removing the creation-time input from `CalendarFeedEntry` is one compile-time unit: the writer, the service and the three unit test files that build entries must change in the same commit or the solution does not build. The migration must exist in the same commit as the entity columns, or `has-pending-model-changes` fails. The only behavioural test change in the tracer is the one integration fact that pinned the defect. Every other test edit is a compile-forced rename that keeps the same instant, so the whole-block byte pins pass unchanged here and are rewritten deliberately in 88-08.
</recorded_choices>
