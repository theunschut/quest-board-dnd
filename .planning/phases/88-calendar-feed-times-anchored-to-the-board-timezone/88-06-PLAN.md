<recorded_choices>
**Operator decision 6: a reader's own availability change raises that reader's `DTSTAMP` (and `LAST-MODIFIED`), not the sequence number.**

The vote marker in `SUMMARY` (" (maybe)", " (declined)") is part of what the feed shows for the reader's entry. The operator's rule is that every change to what the feed shows must carry a revision signal. Leaving the marker unsignalled would repeat the G-88-4 failure for the marker, so the answer is not "leave it out".

The sequence number is still the wrong carrier, for three reasons:
- **The sequence is shared.** It is stored on the event row and published to every reader of that event. Raising it on one person's vote would change every other member's document too: a new ETag, a 200 instead of a 304, and a higher sequence number for a change none of them can see.
- **A per-reader sequence cannot be made one-way.** The only per-reader store is the reader's `EventSignups` row. `EventSignupRepository.WithdrawAsync` deletes it, and a later answer re-creates it, so any counter kept on it resets. A client that missed that gap (Google batches its polls over many hours) would then see the same UID with a lower sequence number. It would treat the entry as older and ignore every later change. That is exactly the lock-out D-07 forbids.
- **The stamp already fits.** RFC 5546 §2.1.5 uses `DTSTAMP` as the tie-breaker at equal sequence numbers. The stamp is per-reader already, because each reader's document is composed separately. The answer time is a real instant that only moves forward, even when the row is deleted and re-created: `UpdatedAt` is written on every answer and `CreatedAt` when the row is made.

So an event entry's stamp is the later of the event's `FeedRevisedAt` and the reader's answer time (`UpdatedAt`, or `CreatedAt` when no person has answered). Its sequence number stays the event's `FeedRevision`.

Accepted cost: a client that ignores the stamp and orders updates only by sequence number may keep a stale marker until the event itself is next revised. The marker is a note about the reader's own answer, which the reader set on the board themselves.

Two side effects follow and are accepted:
- `SetAvailabilityAsync` stamps `UpdatedAt` on every submission. Re-submitting the same answer therefore moves the stamp while the content stays the same, which is harmless.
- Changing an automatic Yes row to a chosen Yes moves the stamp without changing the marker.
</recorded_choices>
