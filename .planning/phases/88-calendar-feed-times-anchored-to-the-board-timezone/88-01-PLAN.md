<recorded_choices>
Claude's-discretion items from 88-CONTEXT.md, decided here so every later plan inherits one answer:

1. **How the zone reaches the writer — a required per-document parameter.** `ICalendarFeedWriter.Write` gains `TimeZoneInfo boardZone`. One zone per document makes "the header, the block and every timed line cannot disagree" a structural fact rather than a tested one, keeps the writer a pure text-in/text-out singleton that tests drive with no DI, and matches D-01 (one zone). A per-entry property was not chosen: it would let entries disagree with the single header and needs multi-zone block logic no decision asks for. The service gains `IBoardClock` (a singleton, safe to inject into the scoped service) and passes `boardClock.TimeZone`.
2. **TZID string form.** Keep the resolved id verbatim when it contains `/` or equals `UTC`; otherwise convert a Windows-style id with `TimeZoneInfo.TryConvertWindowsIdToIanaId` and fall back to the raw id when there is no mapping. The UTC fallback is written as the literal `UTC` — the id the clock actually resolved (`TimeZoneInfo.Utc.Id` on both platforms) — rather than `Etc/UTC`.
3. **VTIMEZONE span and shape.** The block covers the timed entries' own span — earliest start to latest end — read as UTC instants and padded one day each side; it is emitted if and only if at least one timed entry exists; it carries a leading observance dated `19700101T000000` for the offset in effect at the window start, then one fixed-date observance per offset change found by one-day steps plus whole-minute bisection over `TimeZoneInfo.GetUtcOffset` (D-03). No `TZNAME` (display names differ by platform), no `RRULE`. It sits after the calendar headers and before the first `VEVENT`.
4. **X-WR-TIMEZONE placement.** Directly after `X-WR-CALNAME`, emitted on every document including one with no timed entry (single code path, D-06).
5. **Why this tracer touches eight files.** Changing the `Write` signature is one compile-time unit: every caller must change in the same commit or the solution does not build. Three production files carry the behaviour; the two integration files carry the end-to-end proof; the three unit test files receive only compile-forced argument additions and flips of the assertions the reversed contract falsifies. New facts belong to 88-02 and 88-03. Splitting this task would leave a commit where the solution does not compile.
</recorded_choices>

<assumption_delta_decision>
The orchestrator's assumption-delta scan fired on two prose phrases ("on another" phone, an "X-WR-TIMEZONE fallback"). Both are false positives — neither introduces a second instance of any modelled noun. The identity question that genuinely sits nearby is whether the zone belongs to the document or to each entry.

- **Primary noun:** the single board zone — one resolved `TimeZoneInfo` per process, owned by `IBoardClock`.
- **Decision:** `no-change`. The feed consumes that one zone as a per-document input; no per-entry or per-board zone representation is introduced, because D-01 fixes one zone and per-board zones are a deferred idea.
- **What would force a later promote:** the deferred per-board timezone setting. Then the zone would move onto each entry (or entries would be grouped by zone) and the writer would emit one `VTIMEZONE` per distinct zone. The per-document parameter chosen here is a single call site, so that change stays cheap.
</assumption_delta_decision>

- `AppendTimeZone(StringBuilder builder, TimeZoneInfo zone, string tzid, IReadOnlyList<CalendarFeedEntry> entries)`: port 88-RESEARCH.md "Target writer shape" into the writer's style. Collect timed entries (`StartTime.HasValue`) as start `entry.Date.ToDateTime(entry.StartTime!.Value)` plus `entry.Duration`; return without writing anything when there are none. Window start is the earliest start and window end the latest start-plus-duration, each passed through `DateTime.SpecifyKind(…, DateTimeKind.Utc)` and padded by one day (`AddDays(-1)` / `AddDays(1)`). Write `BEGIN:VTIMEZONE`, then `TZID:` + `EscapeText(tzid)`. Write the leading observance: kind from `zone.IsDaylightSavingTime(windowStart)`, onset `19700101T000000`, `TZOFFSETFROM` and `TZOFFSETTO` both `zone.GetUtcOffset(windowStart)`. Walk the window in one-day steps; when `zone.GetUtcOffset(next)` differs from the current offset, bisect on whole minutes between the step start and `next` (low bound still on the old offset, high bound on the new one) until they are one minute apart; the change instant is the step start plus the high bound in minutes; write an observance whose kind comes from `zone.IsDaylightSavingTime(instant)`, whose onset is `FormatBasicDateTime(instant + previousOffset)`, and whose from/to are the old and new offsets; carry the new offset forward. Write `END:VTIMEZONE`. Every line goes through `AppendFoldedLine`. Comments must explain, in plain language: offsets are found by asking the zone for its offset at a moment because Windows and Linux describe a zone's rules in different shapes (a short repeating rule versus a year-by-year list) yet agree on the offset at any moment, so this block is byte-identical on both — which is why `GetAdjustmentRules` is not used; no `TZNAME` is written because zone display names such as `StandardName` differ by platform; fixed-date observances need no recurrence rule because they cover exactly the window the entries span; the one-day pad exists because a wall-clock value lies within a day of the same digits read as UTC in every real zone; bisecting whole minutes keeps onsets free of fractional seconds.
- `AppendObservance(StringBuilder builder, bool daylight, string dtstartLocal, TimeSpan offsetFrom, TimeSpan offsetTo)`: writes `BEGIN:DAYLIGHT` or `BEGIN:STANDARD`, `DTSTART:` + onset, `TZOFFSETFROM:` + `FormatUtcOffset(offsetFrom)`, `TZOFFSETTO:` + `FormatUtcOffset(offsetTo)`, and the matching `END:` line.
