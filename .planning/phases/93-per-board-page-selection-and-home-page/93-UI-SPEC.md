# Phase 93 — UI Design Contract

> Visual and interaction contract for per-board page selection and the board home page. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> **Retroactive:** written after planning and part-way through execution (waves 1-2 built and merged; plans 06, 07, 08, 09, 10, 11, 12 not built). It
> describes and locks what the plans and the merged code already decide. It introduces no new visual direction, palette, component or copy.
> Server-rendered Razor + hand-written CSS, no new JavaScript. Baseline for format and conventions: `91-UI-SPEC.md` and `92-UI-SPEC.md` (both approved).

Sources: `93-CONTEXT.md` (D-05, D-07, D-10, D-11, D-13 to D-16, D-19 to D-21 are the UI-relevant decisions, all locked); `93-RESEARCH.md` (Platform Edit and Index
section, pitfalls 1, 2, 3, 7, 8); `93-PATTERNS.md`; plans `93-01` to `93-15`; summaries `93-01` to `93-05`, `93-13` to `93-15`; `.claude/ui-guidelines.md`;
the merged views (`Views/Shared/_Layout.cshtml`, `_Layout.Mobile.cshtml`, `_Toasts.cshtml`, `Areas/Platform/Views/Group/Index*.cshtml`, `Edit*.cshtml`,
`_LinkedDayEntries.cshtml`, `Players/Index*.cshtml`, `DungeonMaster/Profile*.cshtml`); `site.css`, `mobile.css`, `modern-card.css`,
`platform-group.mobile.css`, `players.mobile.css`, `account.mobile.css`.

Items marked **(built)** are merged and are described, not re-specified. Items marked **(assumption)** are presentation details the plans leave open; the conservative
default consistent with existing conventions was taken and each is listed under "Assumptions". Items marked **(discretion)** are Claude's Discretion in CONTEXT.md.

**Governing principle (D-18, D-09):** a board nobody configures looks and behaves byte-for-byte as it does today. Every conditional below renders only when a page is
off, the home is not the quest list, or the board type forbids the page. A switch hides; it never deletes.

## Color

60/30/10 as the app already lives it; this phase adds **no new colour value**.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | Notice-board photo backdrop | Page |
| Secondary (30%) | Glass `rgba(255,255,255,0.15)` cards: `modern-card` (desktop Edit), `platform-group-card-mobile` (mobile Edit) | Edit card, board list card |
| Accent (10%) | Bootstrap warning amber `#ffc107` and info cyan | Reserved list below |
| Destructive / error | `#ff6b6b` desktop (`modern-card.css` `.text-danger`), `#dc3545`-family on mobile, `#dc3545` for `btn-danger` | Refusal lines on the Edit page only. No destructive button is added by this phase (the board list's existing Delete is untouched). |

Text on the page is the app-wide parchment `#F4E4BC` (desktop forced by `modern-card.css`/`site.css`; mobile per card class).

Accent reserved for: (1) the existing `btn-warning` "Save Changes" on the Edit page (unchanged); (2) the checked state of a page switch on desktop (`site.css` fills a checked
`.form-check-input` with `#ffc107`); (3) the `Info` toast header (`bg-info`, existing) that announces a refused page. Nothing else: not the new Quests nav item (normal nav-link colour), not the Home badge (`bg-secondary` grey), not the lock reasons, not the Quests nav item.

Colour is never the only carrier: a switched-off page is carried by the unchecked control **and** its absence from menus; a locked row by the disabled control **and** the reason text;
a refusal by the red line **and** an icon and the sentence.

### Known contrast limitations (existing, not introduced here)

- Desktop `Home: X` badge: `.modern-card span` forces parchment text on the `bg-secondary` grey (about 3.8:1). The existing board-type badges share the problem (parchment on cyan/blue).
  **(built, accepted)**; the badge also carries a house icon and the words "Home:".
- Desktop lock reasons and hints render as `small.text-muted` / `.form-text`, which `modern-card.css` forces to 70% alpha parchment. The Platform area already uses this for all helper text and the
  text is also carried by the disabled control. Accepted on desktop; on mobile the reason is hardened to an opaque colour (see Surface 1) following the 91/92 rule "secondary text is opaque, never alpha".

## Surface Contract

### 1. Pages section on the Platform Edit page (plan 06, most detail)

Placement: inside the existing form, between the Board Type `div.mb-3` and the `<hr>`. The existing `<hr>` and the `d-flex justify-content-between` button row (Back to Groups left,
Save Changes right) are unchanged. Order inside the section, top to bottom:

1. Heading: desktop `<h5 class="mt-4 mb-2">` with `fa-table-columns me-2`, text `Pages`. Mobile `<h6>` with the same icon, inside the `platform-group-pages-mobile` wrapper.
2. Hint line: `small.text-muted` (the section hint copy), `d-block mb-2`.
3. One switch row per switchable page, in the Catalogue order (Copywriting). Row markup: `div.form-check.form-switch.mb-2`.
   - **Unlocked row:** hidden `name="Pages[n].Page"` (enum name), checkbox `class="form-check-input"` `name="Pages[n].Enabled"` `value="true"` (checked when on), hidden `name="Pages[n].Enabled"`
     `value="false"` after it, then `label.form-check-label` with the page label. `n` is a running index that counts **only posted rows** (no gaps).
   - **Locked row** (type forbids, or Quest Log while Quests is off): checkbox with `disabled`, **no `name`**, unchecked (an off switch), the label, and the reason as `small.text-muted.d-block`
     inside the same `.form-check`, directly under the label. A locked row posts nothing; the server also ignores it (never trust the form).
   - **(assumption, discretion)** each checkbox gets `id="page-{PageName}"` and its label `for` matches, so the label is a real tap target; the checkbox gets `role="switch"`; a locked row's
     checkbox gets `aria-describedby="page-reason-{PageName}"` with the same id on the reason element. No icons on the rows.
4. Home page block: `div.mb-3` with `label.form-label` `Home page` (`for="HomePage"`), `select asp-for="HomePage" asp-items="Model.HomeChoices" class="form-select"` (no blank option, so it always
   posts a value), then `div.form-text` with the home hint.

Desktop rendering: card `col-md-6` centred, `modern-card`. `site.css` forces `.form-check-input` to a 1.25rem square with the app's check mark and a `#ffc107` checked fill, overriding Bootstrap's pill
shape. **This phase accepts that rendering** (it is the app's one checkbox look) and adds no desktop override. A disabled input is `opacity: .5` with `pointer-events: none` (`site.css`) and its label is
dimmed by Bootstrap; the reason `small` is a sibling, not the label, so it stays at full strength. Labels are parchment 500 (forced by `site.css`).

Mobile rendering (chrome is the Platform mobile layout; styles are scoped by class so they also hold if the twin ever renders inside the desktop chrome): wrapper `div.platform-group-pages-mobile` around
the section, inside `platform-group-card-mobile`. Bootstrap's native switch renders. The new rule block in `platform-group.mobile.css`, **all selectors scoped under `.platform-group-card-mobile`** so they
out-rank the existing `!important` rules in that file:

- `.platform-group-card-mobile .platform-group-pages-mobile h6, .platform-group-card-mobile .platform-group-pages-mobile .form-check-label`: parchment `#F4E4BC !important` with the card's existing text-shadow
  (`2px 2px 4px rgba(0,0,0,0.9), -1px -1px 2px rgba(0,0,0,0.9)`). The existing rule colours `h5`, `.form-label`, `p` only; without this the `h6` and the switch labels would not match the rest of the card
  (the same fix `account.mobile.css` and `admin-form.mobile.css` carry for `.form-check-label`).
- `.platform-group-card-mobile .platform-group-pages-mobile .form-check`: `padding-top: 0.5rem; padding-bottom: 0.5rem; min-height: 44px;`, and the label `display: block`, so a row is a 44px tap target.
- `.platform-group-card-mobile .platform-group-pages-mobile small, .platform-group-card-mobile .platform-group-pages-mobile .form-text`: `font-size: 0.875rem; color: #D9CDA8 !important;` (opaque, the 91/92 mobile
  secondary colour, 5.5:1 on the dark glass) with the existing `1px 1px 3px rgba(0,0,0,0.9)` shadow. **(assumption)** The plan says only "smaller muted line"; opaque is the project convention.

Refusal block (both twins): **(assumption, see A1)** the form shows refusals in a `div role="alert" class="mb-3"` placed where the existing validation summary sits (top of the form, above Name), one
`div.text-danger.mb-1` per ModelState error with the empty key, each starting with `<i class="fas fa-circle-exclamation me-2" aria-hidden="true"></i>`. The text and its source (ModelState errors added by the
controller) are exactly what the plan specifies. `div` is used on purpose: `modern-card.css` repaints `li` and `p` parchment but gives `div.text-danger` the error red `#ff6b6b` on desktop, and on mobile
`.platform-group-card-mobile p` repaints `p` parchment while a `div.text-danger` keeps Bootstrap red. The field-level `span asp-validation-for="Name"` is unchanged.

Re-render after a refusal (HTTP 200, nothing saved, no toast): Name keeps what was typed; the Board Type select shows the board's **real** type (never the `OneShot` default); switch rows show the
**resulting** state of the post (what the super admin asked for, after sanitising) with lock reasons recomputed from it; the Home select shows the chosen home. After a success: redirect to the board list
with `Board settings saved.`

Interaction rules:
- Absent means unchanged: a form that posts no Pages rows or no HomePage (old clients, tampering) changes nothing. The UI never relies on an unchecked box meaning "off" (hence the paired hidden `false`).
- One Save commits the name, every switch and the home together. There is no per-switch auto-save and no JavaScript.
- The Home select lists every candidate the board **type** allows, including pages currently off, so a super admin can switch Calendar on and make it home in one save. The server refuses a home that is
  unavailable in the resulting state with the "can't be the home page" error.
- Creating a board is unchanged (D-17): no Pages section on Create. A new board starts with every allowed page on and the quest list as home.
- Keyboard order: Name, each enabled switch in list order (disabled rows are skipped by Tab), Home page, Back to Groups, Save Changes. Native controls only; the existing focus ring is used.
- Screen readers: switches announce as switches; a locked row is read with its reason; the refusal block is `role="alert"`; icons `aria-hidden`.

### 2. Refusal toast (built, plans 01, 02; coverage extended by 12)

Mechanism: a global resource filter (`BoardPageGateFilter`) runs after authorization, for every verb and role (D-06). If a page named on the endpoint is not available, it sets `TempData["Info"]`
to the page's sentence and redirects to the effective home (`BoardPageRoutes.HomeRoute`). The home is an available page by construction, so the redirect cannot loop; a board with no possible home
falls back to the account page. A return URL a visitor followed never reaches the filter's choice: the filter always goes home. With no resolved board it does nothing.

Visual: the existing `Info` toast only. No new toast block, no new `TempDataKeys` entry. Picture endpoints (`GetCroppedPicture`, `GetProfilePicture`, `GetDMProfilePicture`,
`GetOriginalDMProfilePicture`) are exempt so portraits already shown keep loading.

### 3. Layout menus, brand link, Quests item (built, plan 03)

- Both layouts (`_Layout.cshtml`, `_Layout.Mobile.cshtml`) ask `BoardPages` once per request. Two helpers: `Allows` (resolved **and** offered; an unresolved board hides the item, the project's
  allowlist rule) is used for Calendar, Shop, Manage Shop, Edit My Profile, Players and Board Availability; `Serves` (an unresolved board passes, mirroring the gate) is used for Quest Management,
  Create Quest, Create Event, Quest Log, Characters and Contacts.
- A switched-off page's menu item is **not rendered** (no disabled item, no placeholder). The desktop Dungeon Master dropdown is skipped entirely when none of its five items would render ("a menu with
  nothing in it is worse than no menu"); the Admin dropdown always keeps User Management.
- Brand link ("D&D Quest Board"): signed in, it leads to the effective home route; anonymous, to `Home/Index` (unchanged). Order and icons of every item are unchanged.
- **Quests item:** `li.nav-item > a.nav-link#nav-quests` (desktop, `fa-scroll me-1`) and `#nav-quests-mobile` (mobile, `fa-scroll me-2`), label `Quests`, leading the "available to all" group (immediately
  before Shop). Rendered only when the effective home is not the quest list **and** the quest list is available. On a default board the menu is byte-identical to today.
- My Agenda's Board Availability button follows Events on both twins (built); a DM with no resolved board still sees it.

### 4. Home badge on the board list (built, plan 15)

`span.badge.bg-secondary.ms-1` with `<i class="fas fa-house me-1"></i>Home: {Label}`, placed directly after the board-type badge inside the same cell (desktop table) or `div` (mobile card), on both twins.
Rendered only when the **stored** home is not the quest list; a default board looks exactly as before. No count of switched-off pages (rejected). On a 390px phone the badge wraps beneath the type badge
rather than overflowing (backstop, below).

### 5. Linked-calendar entries (built, plan 05)

When the owning board has switched the entry's page off (events for Events, quests for Quests), the entry stays on the viewer's calendar with title, board name and time, but renders as the existing inert
markup (`.linked-entry--static` `div` on desktop; the non-member agenda row on mobile; the same in "Also that day"): no anchor, no pointer cursor, no focus stop, same `title` tooltip. A board the viewer is not a
member of is inert as before. `ViewerIsMember` keeps its meaning. Nothing is filtered out.

### 6. Hidden character pickers and plain-text DM names (plan 07)

When Characters is not served (`Serves(BoardPage.Characters)` false):

## Interaction Contract

- **Switch off a page:** super admin opens the board's Edit page, unchecks a page, Save. Server checks the type ceiling, the home page, the Quest Log dependency, upcoming events and series (and, after plan
  10, live quests) against the **edited** board, not the super admin's active board. Success: redirect to the board list with `Board settings saved.` Refusal: form re-shown with the reason, nothing saved.
- **Effect on the next request, for everyone on that board:** menus drop the item, in-page links and pickers disappear, a typed URL or old email link redirects home with the toast. Settings are read fresh
  per request; no session or claim caching, so no sign-out is needed.
- **Switch back on:** everything returns as it was (shop items, characters, contacts, events, quests, and the stored Quest Log setting). Nothing is deleted at any step.
- **Quests off:** Quest Log is unavailable whatever its own switch says; its row shows off, locked, "Needs the quest list"; its stored bit is kept. A Quests item appears in the menus only while the home is
  elsewhere and Quests is on (with Quests off it does not appear).
- Motion: none added. Toasts keep Bootstrap's own behaviour.
- All new POST behaviour stays behind the existing `[ValidateAntiForgeryToken]` on Edit; no new form or action is added to the visual layer.

## Assumptions

Conservative defaults taken where the plans or CONTEXT leave a presentation detail open. None changes a locked decision. No operator was available to confirm; the plan owner may veto any of them.

1. **A1, refusal markup (the one place this spec adds to plan 06).** Plan 06 says "keep the existing `asp-validation-summary="ModelOnly"`". That helper renders `ul > li`, and on the desktop `modern-card`
   `.modern-card li` forces parchment `!important`, so a refusal would show as ordinary parchment text with no error colour. This spec renders each ModelState error as a `div.text-danger` line with an icon in a
   `role="alert"` wrapper instead. The error text, its source (ModelState empty-key errors added by the controller) and every test assertion on the response body are unchanged. If the plan owner prefers to
   keep the summary tag helper, the refusal lines must still read as errors on both layouts.
2. **A2, desktop switch look.** `site.css` forces every `.form-check-input` to the app's square checkbox style. The `form-switch` class is kept (plan 06) but renders as that checkbox on desktop; no
   override is added. `role="switch"` carries the switch semantics for assistive technology.
3. **A3, mobile Pages styling lives in `platform-group.mobile.css` and is scoped under `.platform-group-card-mobile`**, adds parchment for the new `h6` and `.form-check-label`, a 44px row, and opaque
   `#D9CDA8` secondary text. Plan 06 names only spacing and a smaller muted line.
4. **A4, ids and aria** on the switch rows (`id`, `for`, `role="switch"`, `aria-describedby`) are added so the label is a tap target and a locked row's reason is announced.
5. **A5, Platform mobile chrome.** `_Layout.Platform.Mobile.cshtml` (loads `mobile.css`) exists, while `PROJECT.md` records that Platform mobile views render inside the desktop chrome (known debt). All new
   mobile rules are class-scoped so they hold under either chrome; the executor confirms with a phone user agent.
6. **A6, Home dropdown includes Quest Log** whenever the board type allows it, even when Quests is switched off in the same post. The server then refuses it with "Quest Log can't be the home page because
   it isn't available on this board." (consistent with "list candidates by type, refuse by state").
7. **A7, copy left verbatim although imperfect.** `Needs the quest list` has no full stop while `Not available on Campaign boards.` does; the Events refusal says "Delete them" even for one event, and the one-live-quest refusal says "them". All are pinned
   by built or planned tests, so they are not changed here.
8. **A8, DM chevron and history modifier** (Surfaces 6 and 10): the chevron is dropped on an inert Players row and `dm-profile.mobile.css` gains one optional modifier.
9. **A9, Info, not Error, for a refused page.** The toast is neutral because the visitor did nothing wrong (built).
10. **A10, no share-link surfaces.** Phases 78 and 79 are not built, so there are no share links or link cards to gate; the share-link wording in D-07 is a forward contract for those phases only.
11. **A11, contact category back link (D-07).** The back link lives inside Contacts pages, which are themselves gated, so no separate markup change exists in this phase.
