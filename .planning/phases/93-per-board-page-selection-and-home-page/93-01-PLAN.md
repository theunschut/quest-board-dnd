<objective>
Prove the whole page-switch architecture on one page before anything is built on it. A board whose stored settings switch Shop off and open on Calendar refuses `/Shop` with a toast and lands on `/Calendar`. The path runs from two new columns on `Groups`, through the entity, the mapping and the domain policy, through one scoped resolver, to a global MVC filter that redirects to the board's home page.

Purpose: the risk in this phase is two components disagreeing (a menu showing a page the server refuses, a home page pointing at a refused page). One policy, one resolver and one home function remove that class of bug, so they are built and proven first. Every later plan asks the same resolver.

This plan is the tracer only. Everything else expands from it in wave 2 and later: every other page's gate (plans 02 and 12), the view helpers and menus (plan 03), the home redirect at `/` and the other home entry points (plan 13), and the unit tests that pin the policy, the route table and the storage mapping (plan 14).

Output: the `BoardPage` catalogue with `BoardPageSet`, `BoardPagePolicy`, `IBoardPageResolver` with `BoardPageAvailability`, `BoardPageResolver`, the `AddBoardPageSettings` migration, `BoardPageGateFilter` with the `[BoardPage]`/`[BoardPageExempt]` attributes, `BoardPageRoutes`, the Shop gate, and the shared `BoardPageSeed` test helper.
</objective>

<recorded_choices>
Phase-wide choices made at planning time. Later plans repeat the ones they rely on.

1. **Storage (discretion).** Two `int NOT NULL DEFAULT 0` columns on `Groups`: `DisabledPages`, a bit mask of switched-off pages where bit `1 << (int)page` set means off, and `HomePage`, where `0` is `BoardPage.Quests`. A mask of *disabled* pages makes the CLR default mean "nothing off, quest list home", so the ~40 test seeds that build `new GroupEntity { ... }` and every existing board behave unchanged (D-18). No `HasDefaultValue` call.
2. **One source of truth (discretion).** `BoardPagePolicy` (Domain, pure static) decides availability and the effective home. `IBoardPageResolver` (scoped) applies it to the active board. Menus, in-page links, the gate filter, the home redirects, the Platform form, linked calendars and moves all ask one of these two. The board type always comes from `IBoardTypeResolver`, so no fourth board-type lookup is added.
3. **Server check (discretion).** A global `IAsyncResourceFilter` reads `[BoardPage]` and `[BoardPageExempt]` from endpoint metadata. It runs after authorization, so an anonymous user or a Player on a DM-only page still gets today's login or AccessDenied response, and it refuses every HTTP verb.
4. **The unresolved state keeps today's behaviour.** The gate passes through when the resolver returns null. Views use two helpers that plan 03 adds: `Allows(page)` (null means hidden) wherever today's markup checks the board type, and `Serves(page)` (null means shown, exactly what the gate lets through) wherever today's markup has no board-type check. This supersedes research assumption A5 because `LayoutNavigationTests.Nav_UnresolvedBoardTypeDm_BoardAvailabilityLinkAbsent` asserts Create Event renders with no resolved board type, and D-18 says nothing users see changes until a super admin changes a setting.
5. **Quests switch built last.** `BoardPagePolicy.IsSwitchable` returns false for `Quests` until plan 10, which makes Quests switchable in the same plan as every surface that must change when quests are off (the research verdict on D-03 asked for exactly this order). The policy already treats a set Quests bit correctly from this plan on, so plan 10 only flips the switchable flag and adds the quest-specific surfaces.
6. **Toast.** `TempData["Info"]` (auto-hiding), one sentence per page in `BoardPageRoutes.NotUsedMessage`; Shop's is the CONTEXT example verbatim.
7. **Spec-less probe fallback skipped.** This phase has no requirement IDs to probe. This is a visible, recorded choice. Edge coverage comes from the D-01..D-21 truths lifted into each plan's must_haves.
8. **Migration reversibility: costly.** Adding the columns is reversible by the down migration, but a rollback drops any settings saved since, and the enum's stored int values become a persisted contract (never reorder `BoardPage`).
9. **Share-link controls and preview cards have no code to gate (D-07 part, discretion item).** Phases 78 and 79 are not built: there is no mint control, preview route or link card in the repository. Nothing in this phase edits them. The forward contract (the anonymous preview route asks `IBoardPageResolver` after scoping to the signed board and falls back to the generic response while Characters or Contacts is off) stays in 93-RESEARCH.md § "Share-link previews" for those phases to inherit.
10. **Cross-board deep links switch the session first (accepted).** The deep-link middleware repoints the session to the entry's board before the gate runs, so an old link into a switched-off page lands on that board's home with both banners. CONTEXT accepts this ("which the D-05 redirect then handles"). The middleware is not changed, so its oracle-parity tests keep covering it.
11. **Companion types share a file (sizing).** Three small types live in the file of the type they serve, following the codebase's existing multi-type files (`IImageValidationService.cs`, `EventMovePlan.cs`): `BoardPageSet` beside the `BoardPage` enum in `QuestBoard.Domain/Enums/BoardPage.cs` (namespace `QuestBoard.Domain.Enums`; its bit positions are the enum values, so the stored contract reads in one place); `BoardPageAvailability` beside `IBoardPageResolver` in `QuestBoard.Domain/Interfaces/IBoardPageResolver.cs` (namespace `QuestBoard.Domain.Interfaces`; it is what the resolver returns); and `BoardPageAttribute` and `BoardPageExemptAttribute` beside the filter that interprets them in `QuestBoard.Service/Filters/BoardPageGateFilter.cs` (namespace `QuestBoard.Service.Filters`). Names, members and behaviour are as listed in the artifacts table; only the files are shared.
12. **The tracer is one path (sizing).** This plan carries only what the Shop refusal needs end to end. The `/` redirect (`HomeController`) moves to plan 13 with the other home entry points; the policy, route and mapping unit tests move to plan 14; the `Allows`/`Serves` helpers and the `_ViewImports` injection move to plan 03. All of them run in wave 2 against this plan's code.
</recorded_choices>

The detector fired on "choose which pages" and "chosen home page" (chosen), with weak pluralization cues. Two derived values become chosen: which pages a board offers (derived from `BoardType` alone until now) and the home page (always the quest list until now).

- **Noun now primary:** a board's page availability, `BoardPageAvailability`, computed by `BoardPagePolicy` from board type, stored switches and stored home.
- **Decision: promote.** Every page-availability question moves to the policy. The layouts' inline `activeBoardType == BoardType.OneShot` checks are replaced by policy calls (plan 03), and every hard-coded `Quest/Index` home target routes through `BoardPageRoutes.HomeRoute` (this plan for the refusal, plans 03 and 13 for the brand link, `/`, the picker and the Account page). `BoardType` is demoted to one input of the policy: a hard ceiling that switches can only narrow, by the operator's explicit choice in D-01 (the rejected alternative was board type as an overridable default).
- **Accepted debt:** the two private board-type lookups in `QuestController` and `QuestLogController` stay for non-page decisions (campaign quest behaviour). They are not consolidated here.
- **Invariant tests (accepted):** plan 14 pins that, for both board types, every mask and every stored home, `EffectiveHome` is null or an available candidate. Plan 12 adds the second invariant: every home candidate's route lands on a controller carrying that same `[BoardPage]`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → any gated controller action | Typed URLs, bookmarks, emailed links and crafted POSTs to a switched-off page cross here |
| session → active board | The active board id selects which board's settings apply; it is never taken from the request |
| filter → redirect | The refusal builds a redirect; its target must never come from request data |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-93-01 | Elevation of privilege | BoardPageGateFilter | high | mitigate | Global resource filter refuses every verb on a page that is off or type-disallowed (D-01, D-06); runs after authorization so it never weakens a policy; Campaign and SuperAdmin refusals tested here; plan 12 adds the reflection coverage test that fails the build when an action is unclassified |
| T-93-02 | Spoofing (open redirect) | BoardPageGateFilter | medium | mitigate | Redirect target is built from `BoardPageRoutes` route names only, never from query or form data; the existing `Url.IsLocalUrl` return-URL handling is untouched |
| T-93-03 | Denial of service (redirect loop) | BoardPageRoutes.HomeRoute | medium | mitigate | `EffectiveHome` is available by construction (pinned by the 2 x 512 x 9 invariant test in plan 14); a null home falls back to ungated Account/Profile; the gate passes through when no board resolves (tested here) |
| T-93-04 | Tampering | EntityProfile Group map | medium | mitigate | The `LinkedBoardSetId`/`LinkedBoardSet` Ignore() lines stay, so a settings save cannot overwrite the link or defeat its concurrency token; the existing Edit POST suites run here, and `BoardPageSettingsMappingTests` (plan 14) pins it |
| T-93-05 | Information disclosure | BoardPageResolver | low | accept | The decision depends only on the active board's own settings and type, never on whether an entity id exists, so a refusal reveals nothing about other boards |
| T-93-06 | Tampering (stale authorization state) | BoardPageResolver | low | mitigate | Read fresh per request (scoped memo keyed on the active group id), never cached in session or claims, so a super admin's change applies on the next request |
