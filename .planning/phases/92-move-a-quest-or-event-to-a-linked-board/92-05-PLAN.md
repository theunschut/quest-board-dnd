<objective>
Make a moved quest look as if it had been created on the target board. Keep target members' signups with characters cleared, drop non-members with their votes, move the waitlist up for every freed seat, cut chain links that would cross boards, refuse a DM who cannot run the quest there, and mail the people on the quest. All of it lands in the tracer's single save.

Purpose: these are D-03 to D-07, D-10 and D-17. They are computed on the plan 01 `QuestMovePlan` contract, so the repository's write order and the page are unchanged. The waitlist rule is applied in memory before the save, because filtered repository reads would find nothing once the quest has left the source board. A parity test pins it to the existing repository rule.

Output: full `QuestMoveRepository.ApplyAsync` reconciliation, the real plan in `QuestMoveService`, `WaitlistOrdering.SelectPromotions`, `IIdentityService.IsSuperAdminAsync`, the after-save mail fan-out, and unit and HTTP proofs for D-21.4 to D-21.7, D-21.9 and D-21.12.
</objective>

The research found `QuestService.PromoteNextWaitlistedPlayerIfSeatFreedAsync` private, saving per candidate, and filtered by board. `BoardMoveWaitlistParityTests` pins the selection to `GetTopWaitlistedCandidateAsync`. The rule ignores `TotalPlayerCount`, exactly as the existing rule does.
2. **The DM rule uses the D-03 addendum** (operator, 2026-10-18). The DM passes when they are an Identity SuperAdmin, read by id through the new `IIdentityService.IsSuperAdminAsync` because there is no principal for the DM at move time. Otherwise the raw `UserGroups` role on the target must be DungeonMaster or Admin. This overrides the research's original "refuse" recommendation.
3. **Mail recipients (discretion):**
   - The acting super admin is never mailed about their own move.
   - The DM gets only the DungeonMaster variant, even if they also hold a signup.
   - A promoted player gets only the Waitlist Promoted after-move mail (operator decision).
   - Each enqueue sits in its own try/catch, because the move is already committed.
4. **A chain link whose other end is on another board** (which current code cannot produce) is still cleared by its scalar id. Its preview row has no title and so does not render; plan 07 renders chain rows only when a title is present.
5. **Reversibility: reversible.** The work is behaviour behind the plan 01 and plan 03 contracts plus one new interface method, with no schema change.
