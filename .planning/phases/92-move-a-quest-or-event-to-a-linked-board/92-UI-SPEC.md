# Phase 92 — UI Design Contract

> Visual and interaction contract for moving a quest or event to a linked board. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> Server-rendered Razor + hand-written CSS, no new JavaScript. Every value is pinned to tokens and classes that already exist in
> `wwwroot/css`; the only new classes are listed under "New classes introduced". Baseline for format, tokens and the
> Details-page vocabulary: `91-UI-SPEC.md` (approved), which this spec does not re-litigate.

Sources: decisions D-01 to D-21 from `92-CONTEXT.md` (locked; D-13, D-14, D-16, D-17 and "Claude's Discretion" are the UI-relevant ones);
`.claude/ui-guidelines.md`; `91-UI-SPEC.md` and `91-UI-REVIEW.md` (the `.modern-card span` colour trap and the `fw-bold` weight trap);
existing `Quest/Details.cshtml`, `Quest/Details.Mobile.cshtml`, `Events/Details.cshtml`, `Quest/CreateFollowUp*.cshtml`,
`Shared/_Toasts.cshtml`, `modern-card.css`, `quest-followup.mobile.css`, `Components/Emails/QuestDateChanged.razor`, `AddedToGroup.razor`,
`WaitlistPromoted.razor`, `Controllers/Admin/EmailPreviewController.cs`.

Items marked **(assumption)** are presentation choices the decisions leave open; the conservative default was taken and each is listed under
"Assumptions to confirm with the operator". Items marked **(discretion)** are Claude's Discretion in CONTEXT.md and need no sign-off.

## Typography

Declared for all new content on the Move page, one complete size set per layout. Existing heading styles are reused unchanged; their sizes are listed because they render on the page. Bootstrap's own sizes apply: `h2` 2rem, `h4` 1.5rem, `h5` 1.25rem, `h6` 1rem.

**Desktop Move page: 4 sizes** (32 / 24 / 16 / 14)

| Role | Size | Weight | Line Height | Where |
|------|------|--------|-------------|-------|
| Page title | 32px (`h2`) | 600 | 1.2 | Move card header |
| Section heading | 24px (`h4`) | 600 | 1.2 | Summary card heading ("This Quest" / "This Event") and the preview heading |
| Body | 16px (`1rem`) | 500 (inherited from `modern-card`, see Weights) | 1.5 | Consequence sentences, intro line, summary lines, button labels |
| Label | 14px (`.875rem`) | 500 (inherited) | 1.5 | Secondary text only: hints ("Add them to {Board} first..."), disabled-control reason, role annotation on a person |

**Mobile Move page: 4 roles, 3 distinct sizes** (20 / 16 / 16 / 14)

| Role | Size | Weight | Line Height | Where |
|------|------|--------|-------------|-------|
| Page title | 20px (`h5`) | 600 | 1.2 | Card 1 title |
| Preview heading | 16px (`h6`, Bootstrap 1rem; same size as body, set apart by weight and the heading element) | 600 | 1.2 | Card 2 preview heading |
| Body | 16px (`1rem`) | 400 | 1.5 | Consequence sentences, intro line, button labels |
| Label | 14px (`.875rem`) | 400 | 1.5 | Secondary text only: summary lines for secondary info, hints, disabled-control reason, role annotation on a person |

The 14px label role is for secondary text only (hints, roles, reasons). Primary content never drops to 14px.

Emphasis is a weight change inside a line, not a size: entry titles, board names inside sentences, person names and the "Selected" mark use `<strong class="move-strong">` at 600 and the size of the line they sit in.

Weights: **400 regular, 500 inherited, 600 semibold** across both layouts, but **two per layout**: desktop renders 500 and 600, mobile renders 400 and 600.
- 500 is the weight `modern-card.css` already forces on `p`, `li`, `span` and `small` inside `.modern-card`, so desktop body and label text render at 500. It is declared here because it renders; it is inherited and not overridden on this page. Do not add an override or a fight against it. Mobile has no `modern-card`, so mobile body and label are 400.
- 600 is emphasis and headings. Use `<strong class="move-strong">` with `font-weight: 600`. Never `fw-bold` (Bootstrap forces 700 with `!important`, the trap 91's review caught) and never a bare `<strong>` (renders `bolder`, 700 inside a 500 parent).
- No italics on the Move page and the Details controls. This rule does not extend to the email: the email subtitle and note stay italic, as in the existing poster templates.

## Color

60/30/10 as the app already lives it; this phase adds no new dominant or secondary surface.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | Notice-board photo backdrop | Page |
| Secondary (30%) | Glass `rgba(255,255,255,0.15)` cards: `modern-card` (desktop), `.move-card-mobile` (mobile) | Summary card, picker card, consequence card |
| Accent (10%) | Bootstrap info cyan `btn-info` | Reserved for the "Move to Linked Board" control on Details, the "Show What Will Happen" button, and the heading icon on the Move page. Nothing else. |
| Destructive | `#dc3545` | The "will be removed" row border, the refusal alert, and nothing else. There is **no `btn-danger`** on this page: confirming a move is not a delete. |

Text on the page is the app-wide parchment `#F4E4BC` (desktop, forced by `modern-card.css`) and parchment with `1px 1px 3px rgba(0,0,0,0.9)` shadow (mobile cards). That is the app's text colour and not the accent.

Accent reserved for: (1) the Details "Move to Linked Board" control in both its enabled and disabled forms; (2) the picker's "Show What Will Happen" button; (3) the `fa-right-left` icon in the Move page title. Never used for borders, board names or the confirm button.

Confirm button: `btn-warning` (filled, dark text, existing Bootstrap style): a consequential admin action whose chain-link cut and dropped signups are not undone by moving back. The back button (`Back to This Quest` / `Back to This Event`) is `btn-secondary`.

Secondary text colour: opaque, never alpha. Desktop hints inherit the forced parchment (differentiated by 14px size alone). Mobile hints use `#D9CDA8` (the 91 value, 5.5:1 on the dark card). **Do not use `.text-muted` or `.form-text` anywhere on the Move page**: both resolve to 70% alpha parchment.

### New classes introduced (no new palette values)

Consequence row left borders reuse values already in the app. Colour is decorative; every row also carries an icon and full text, so colour is never the only carrier.

| Modifier | Border | Icon | Meaning |
|----------|--------|------|---------|
| `move-consequence--kept` | `4px solid #28a745` | `fa-check` | Stays as is |
| `move-consequence--notice` | `4px solid #ffc107` | `fa-eraser` characters cleared, `fa-hourglass-half` waitlist, `fa-link-slash` chain, `fa-user-plus` Campaign rows, `fa-ban` cancelled | Changes the viewer may not expect |
| `move-consequence--dropped` | `4px solid #dc3545` | `fa-user-minus` | Removed |
| `move-consequence--neutral` | `4px solid #6c757d` | `fa-envelope` | Information only |

Other new classes: `move-consequences` (list), `move-consequence` (row), `move-consequence-icon`, `move-consequence-body`, `move-people` / `move-person` (names list), `move-person-mark` (the "Selected" mark), `move-strong`, `move-hint`, `move-control-reason`, `move-card-mobile` (mobile glass card, a copy of `quest-followup-card-mobile`'s rule). Rows use `display: flex; gap: 8px; padding: 8px 8px 8px 16px; margin-bottom: 8px`; body text wraps with `overflow-wrap: anywhere` and `min-width: 0` so long titles and board names never push the row wide.

**Cascade trap (from 91's review):** inside `.modern-card`, `p`, `li`, `span` and `small` are forced to parchment with `!important`. Therefore on the desktop Move page and Details controls: no `<span>` that needs its own colour or weight, no `badge ... text-dark` span (it would render parchment on yellow), no `.text-muted`. Use `<strong class="move-strong">`, `<p>` and `<div>`. The "Selected" mark is a `strong`, not a badge.

## Copywriting Contract

Players never see this page; only a super admin does. Copy still uses **board** and **linked board** (never "set" or "group"). No planning IDs anywhere. Names (entry title, board, DM, person) are user text: always Razor-encoded, never concatenated into HTML.

### Changed between preview and confirm (discretion)

When the recomputed consequences differ from the preview, the POST does not move anything; it re-renders the Move page (HTTP 200, not a redirect) for the same target with a fresh preview and a fresh stamp, and this notice above the preview heading: `alert alert-warning` with `fa-triangle-exclamation me-2`, `role="alert"`: `Things changed while you were reviewing this. Check what the move will do now, then confirm again.`

### Email (surface 5)

One new template `QuestMoved.razor`, three audiences through a single `Audience` parameter (`Player`, `DungeonMaster`, `Removed`), built from the `QuestDateChanged.razor` poster structure (`Poster6.png`, 800px tall, `_EmailLayout`, Cinzel heading 40px, title 26px, 15px italic subtitle, gold divider, 14px info table, gold CTA).

**Email typography: 4 sizes (40 / 26 / 15 / 14).** The existing poster templates (`QuestDateChanged.razor`, `WaitlistPromoted.razor`) already render exactly this set: heading 40px (Cinzel, 700), title 26px (Cinzel, 700), subtitle 15px (Georgia, italic), info table 14px (Georgia, labels 700, values 400). The CTA label is 15px bold Cinzel, the same size as the subtitle. `QuestMoved.razor` reuses these four sizes and their markup unchanged; the note is 14px, the info-table size, so it adds no fifth size. The italic subtitle (and the italic note) stay italic as in the existing poster templates. Parameters: `QuestTitle`, `DmName`, `BoardName`, `SessionDate` (nullable `DateTime`), `QuestUrl`, `AppUrl`, `Audience`.

| Note (14px, `#5a4030`, Georgia italic, line-height 1.5, the note style of `AddedToGroup.razor` set at the 14px info-table size instead of its 13px) | Player: `Your signup and date votes came with it. Session date formatting: `QuestDateChanged.razor` formats its dates inside the `.razor` itself, as `@OldDate.ToString("dddd, MMMM d")` on a plain `DateTime` parameter (`WaitlistPromoted.razor` does the same with `QuestDate`); the job and caller pass the stored value through and format nothing. `QuestMoved.razor` reuses exactly that pattern: the `Session Date:` value is `@SessionDate.Value.ToString("dddd, MMMM d")` (no time, no year), or `Still being decided` when `SessionDate` is null. The value is a wall-clock value, a floating local time with no UTC instant, and is never timezone-converted: no `ToLocalTime`, no `TimeZoneInfo`, no `Html.LocalTime`, in the template, the dispatcher or the job.

Recipients, per D-17: the DM and every kept signup get the Player / Dungeon Master variant; every dropped player gets Removed; confirmed addresses only. The acting super admin is not mailed about their own move **(discretion)**. A player promoted off the waitlist by the move gets **one** mail, not two (operator decision): the existing Waitlist Promoted mail, enqueued with the target board's id, with one extra line, and no Quest Moved mail.

The extra line lives in `WaitlistPromoted.razor` behind a new optional parameter `MovedToBoardName` (nullable string, default null). When it is null the template renders byte-identical to today, so every existing promotion is unchanged. When it is set, one note paragraph renders directly under the subtitle, in the same 14px `#5a4030` note style as the Quest Moved note (14px is the info-table size already in that template, so it adds no new size): `This quest has moved to {MovedToBoardName}. If you had picked a character, pick one from {MovedToBoardName} again on the quest page.` The preview text gains no change; the subject stays the existing one.

`EmailPreviewController`: four new actions and four links on its index, labelled `Quest Moved (player)`, `Quest Moved (Dungeon Master)`, `Quest Moved (signup removed)` and `Waitlist Promoted (after a move)`, the last rendering `WaitlistPromoted` with `MovedToBoardName` set. Sample data: title `The Tomb of Annihilation`, board `The Silver Tankard`, DM `Dungeon Master Theomund`, date `DateTime.Today.AddDays(7)`.

## Surface Contract

### 1. Move page, desktop

Layout: Bootstrap `row`; left `col-lg-4`, right `col-lg-8`, the pairing `Events/Details.cshtml` already uses.

- Left, summary card (`card modern-card mb-3`): `card-header modern-card-header` with `h4.mb-0` ("This Quest" / "This Event"); body per the Copywriting table, each line a `p.mb-1` with its icon (`fa-scroll`, `fa-calendar-day`, `fa-clock`, `fa-user`, `fa-circle-check`, `fa-ban`; icons `me-2`, `aria-hidden`). Dates only through `Html.WallClock` (`date-time` for a finalized quest session, `date` for an event); never `.ToString()` on a `DateTime` in the view.
- Right, move card (`card modern-card`): header `h2.mb-0` with the title and icon. Body in this order:
  1. Changed-since-preview notice, only when re-shown.
  2. Intro `p`.
  3. Picker: a `<form method="get" asp-fragment="move-preview">` with the select and `Show What Will Happen`, laid out `row g-2 align-items-end` (select `col-md-8`, button `col-md-4`, `w-100`). When there is one other board this is replaced by the `Moving to {Board}` line.
  4. Preview section `<section id="move-preview" aria-labelledby="move-preview-heading">`: the `h4`, then either the refusal alert or `ul.move-consequences.list-unstyled` of rows. The fragment means picking a board lands the viewer on the preview, with no script.
  5. `<hr>`, then `d-flex justify-content-between`: `Back to This Quest` / `Back to This Event` left, and on the right the confirm `<form method="post">` (antiforgery by tag helper) with hidden `entryId`, `targetBoardId` and the opaque preview stamp. With no chosen target, or a refusal, the confirm form is not rendered at all (hidden, not disabled) and the back button sits alone on the left.
- Consequence row (`li.move-consequence.move-consequence--{kind}`): `div.move-consequence-icon` (`<i class="fas fa-fw ...">`), then `div.move-consequence-body` holding a `p.mb-0` sentence and, for removal rows, the names list and hints. Use `div`/`p`/`strong`, never `span` (cascade trap).

## Interaction Contract

- Order of use: Details control, Move page (choose target if more than one, read the preview, confirm), toast on the source board. No JavaScript at any step; the picker is a plain GET form, the confirm a plain POST.
- The GET and POST both enforce super admin only, the fresh linked-set read, and eligibility on the server. The preview is never trusted at confirm; the stamp only lets the server notice that the consequences changed and re-show the page.
- Keyboard: tab order is picker, `Show What Will Happen`, `Back to This Quest` / `Back to This Event`, confirm (visual order). Every control is a native `a`, `button` or `select`. Visible focus uses the existing Bootstrap focus ring.
- Screen readers: icons `aria-hidden="true"`; the preview is a labelled `section`; the removal list has an `aria-label`; the changed notice and the refusal use `role="alert"`; the disabled Details control is focusable and described by its reason; the "Selected" mark is real text, not an icon alone.
- Motion: none added.
- After a successful move: redirect to the source board's Quest Board (quest) or Events list `Events/Index` (event) with the toast. The session is not switched to the target board.
- An entry that cannot move is never reachable through the page: a direct GET gets the Error toast and a redirect to Details.

## Assumptions to confirm with the operator

Everything here is a conservative default taken because CONTEXT.md and the 91 baseline do not settle it. None changes a locked decision.

1. **Picking a target is a GET round trip** (select, then `Show What Will Happen`), not an instant update. This keeps the phase free of JavaScript and keeps "consequences computed for the chosen board" true. An `onchange` auto-submit would be the alternative.
2. **One Move view pair for quests and events**, with copy and rows switching on kind, instead of separate quest and event pages.
3. **Control look:** label `Move to Linked Board`, `btn-info`, icon `fa-right-left`; disabled state is `aria-disabled` with a visible one-line reason.
4. **Confirm button is `btn-warning` labelled `Move to {Board}`, with no `confirm()` dialog**, since the preview already names everything destroyed. No `btn-danger` on the page.
5. ~~A player promoted off the waitlist gets two mails.~~ **Resolved by the operator, 2026-10-17: one mail.** The existing Waitlist Promoted mail gains an optional "moved to {Board}" line and the move mail is skipped for that player (see Email).
6. ~~The calendar-feed effect is not mentioned on the Move page.~~ **Resolved by the operator, 2026-10-17: add a neutral row** (see the Calendar apps rows in the consequence tables). Nothing changes in the feed itself.
7. **One email template with three audiences**, and the removed-player variant carries no button (they cannot open the quest on a board they are not in).
8. **Event removal rows list names only**, not each person's answer.
9. **A toast with the "Open it on {Board}" link does not auto-hide.**
10. **Characters-cleared row is shown only when at least one kept signup actually has a character.**
