<objective>
Put the availability write actions and the create-time campaign fan-out on the controller, and give the details view everything it needs to render.

Three availability actions land on `EventsController`: `SetAvailability` (one click both creates and answers, D-06), `Withdraw` (deletes the row, restoring the genuine not-answered state, one-shot boards only and enforced server-side, D-07/D-08), and a `Create` path that on a campaign board writes the event and a Yes row for every member in one unit of work (D-14/D-15/D-16). Every write takes the acting user from `User` and never from request input (D-09), and every write re-verifies the event's board explicitly rather than trusting the read filter alone (D-28).

**Planner decision PD-01 — past events stay answerable.** CONTEXT.md left this to the planner. A past-dated event still accepts a new or changed answer, and Withdraw still works on one. Rationale: the create-time fan-out already runs regardless of date, past-dated events are allowed to exist by design, and an event here is a record rather than a booking — a dungeon master correcting who actually turned up is a legitimate use. Neither `SetAvailability` nor `Withdraw` contains a date comparison of any kind. Plan 75-05 asserts this.

Purpose: this is the only plan that opens a write path to `EventSignups` from a browser, so it is where the two-layer tenant defence and the ownership rule are actually enforced.
Output: two view models, one mapper entry, three controller actions changed or added, and an atomic create-with-fan-out repository path.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → `POST /Events/SetAvailability/{id}` and `DELETE /Events/Withdraw/{id}` | Untrusted event id and untrusted availability value; the actor's identity must never come from the request |

| `EventsController` → `EventSignups` insert | The read filter offers no protection on an insert, so the board must be re-verified in the controller |
