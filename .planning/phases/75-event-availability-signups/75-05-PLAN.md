<objective>
Prove the five requirements with automated tests, and close the validation contract.

The two-group isolation class is not optional. The standard integration harness shares one mutable group context that defaults to group 1, so an ordinary test is structurally blind to a cross-board leak — which is exactly the bug class this application has already shipped twice and found a third live instance of during a later discussion. The isolation class seeds a genuine second board through the unfiltered seeding context, acts as a member of the first, and asserts both the read and the write are refused.

The remaining facts extend the Phase 74 controller class: the one-shot opt-in lifecycle, the campaign opt-out lifecycle, the ownership rule, the server-side withdraw refusal on a campaign board, and planner decision PD-01 that a past-dated event stays answerable.

One harness trap governs how these are written: the shared context's board-type flag is a hardcoded settable property decoupled from any database row. It is the right lever for anything that resolves the board type through a normal request, and the wrong lever for anything that reads the group row directly. Where a fact needs a real board type, seed a real group row with it.

Purpose: without these, four of the five requirements have no proof and the fifth has no proof that survives the harness's blind spot.
Output: an extended controller test class, a new isolation class, and a filled-in validation map.
