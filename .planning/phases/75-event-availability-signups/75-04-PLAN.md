<objective>
Make the event details page the single availability surface. It gains three answer buttons following the established vote idiom, a withdraw control on one-shot boards, a named roster visible to every board member, and a delete confirmation that says how much availability the delete destroys.

This page has no mobile variant, so one view serves both platforms and there is no platform-divergence risk to manage. Nothing about availability goes anywhere near a calendar surface: `Views/Shared/_Calendar.cshtml`, `Views/Calendar/Index.cshtml` and `Views/Calendar/Index.Mobile.cshtml` are untouched this phase, which is what keeps the five protected quest details call sites entirely outside this phase's blast radius. The calendar chip already links here, so no information becomes unreachable.

The roster deliberately shows plain Yes / Maybe / No with no marker for an untouched campaign default. That distinction belongs to the availability overview phase. Until then a fresh campaign event's roster reads as unanimous agreement nobody actually gave — a known, accepted cost, and the reason the underlying data records the difference even though this view does not show it.

Purpose: this is the only place a player answers, so if it is wrong the feature is unusable regardless of how correct the layers below are.
Output: the extended details view plus render tests proving the controls appear and disappear under the right conditions.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Rendered markup → browser | What the page renders is a convenience, never an enforcement point; every control's server-side counterpart re-checks its own precondition |
| Browser fetch → the two write endpoints | The antiforgery token must accompany every request or the server rejects it |
| View model → rendered page | Anything not on the view model cannot leak; anything on it will render somewhere eventually |
