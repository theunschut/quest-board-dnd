<objective>
Keep campaign-board event availability in sync with membership. Joining a campaign board backfills a Yes row on every event dated today or later (D-14, D-16 symmetry, D-17); leaving any board deletes every event signup that member holds on that board, past and future (D-20). Both hook the two verified `GroupService` chokepoints (D-18, D-23), and the join plus its backfill are atomic (D-19). The Platform Members remove control gains the confirmation that makes the new destructiveness visible (D-24).

EVTAVAIL-04 and the matching roadmap criterion were already reworded on 2026-08-27 to agree with D-20 — treat the current wording as canonical and do not preserve past answers on leave (D-21). D-22 records, knowingly, that this makes event availability the only thing erased when a member leaves; quest signups, date votes, characters, gold and transactions all still survive. Do not "fix" that inconsistency here.

This plan touches no migration and no event view. Purpose: a later phase's availability grid can trust that "is a member of a campaign board" implies "has a row on every upcoming event".
Output: an atomic `GroupRepository.AddMemberAsync`/`RemoveMemberAsync`, chokepoint documentation on `GroupService`, two confirmation dialogs, and unit tests proving the boundary and the scoping.
</objective>

The backfill body:

1. Read the target board with `var group = await DbContext.Groups.FirstOrDefaultAsync(g => g.Id == groupId, token);`. Resolve the board type from `group.BoardType` compared against `(int)BoardType.Campaign`. 2. When the board is not campaign, stage nothing further — a one-shot board is opt-in and must have no rows until a player creates one.
3. When the board is campaign, compute `var today = DateOnly.FromDateTime(DateTime.Today);` and call a new private helper `GetFutureEventIdsForGroupIgnoringActiveBoardAsync(groupId, today, token)`. 4. For each returned event id, `DbContext.EventSignups.Add(new EventSignupEntity { EventId = eventId, UserId = userId, Availability = (int)VoteType.Yes })`. Leave `UpdatedAt` at its default null and add a comment saying, in plain language, that an automatic signup deliberately leaves the answered marker unset so it stays distinguishable from an answer the member actually gave. Do not filter by role — every member of a campaign board gets a row, dungeon masters and admins included, because a campaign board has no opt-in path and a role filter would lock them out of the feature rather than merely omit them.

Add the private helper `private async Task<List<int>> GetFutureEventIdsForGroupIgnoringActiveBoardAsync(int groupId, DateOnly today, CancellationToken token)` returning `await DbContext.Events.IgnoreQueryFilters().Where(e => e.GroupId == groupId && e.Date >= today).Select(e => e.Id).ToListAsync(token)`. The `IgnoreQueryFilters` call and the `Where` clause must be written on adjacent lines with nothing between them. Comment it in the style of the existing cross-group query in `QuestRepository`: state that the ambient board filter answers for the caller's selected board and therefore answers the wrong question for an operation that targets a board named by an argument, and that scope is re-imposed immediately and explicitly by that argument, so this query is strictly narrower than an unscoped bypass rather than broader. The method name is the contract — anything that reads it must see that it steps outside the ambient board scope on purpose.

Also add a short comment above the `catch (DbUpdateException)` block noting that the same save now also carries the automatic signup rows, so a failure there is no longer guaranteed to be the duplicate-membership race; the friendly message is kept because that race remains the only realistic trigger for a member who was not already on the board.
