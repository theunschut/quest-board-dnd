# Phase 82 — UI Design Contract

> Visual and interaction contract for the Personal Cross-Board Event Agenda. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Stack note:** Existing ASP.NET Core 10 MVC + Razor + Bootstrap 5.3.0 + FontAwesome 6.4.0 (solid set, `all.min.css` + `v4-shims.min.css`) codebase. No component registry, no shadcn, no React. This page is a **direct sibling of Phase 77's Availability Overview** and inherits its design system, cell vocabulary, and card idiom wholesale — it does not invent a parallel visual language. Where this spec diverges from Phase 77 (row anatomy, click target, board identity), the divergence is deliberate and is called out explicitly with its reason, exactly as CONTEXT.md's D-12 asks.

## Spacing Scale

Declared values (must be multiples of 4), identical to Phase 77's scale:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Gap between name and cell inside one roster chip; gap between icon and label |
| sm | 8px | Gap between roster chips when wrapped; gap between board-name badge and board-type badge |
| md | 16px | Vertical padding of each agenda row (desktop); gap between mobile card sections |
| lg | 24px | Space between the page header/filter block and the row list |
| xl | 32px | Not used on this page |
| 2xl | 48px | Not used on this page |
| 3xl | 64px | Not used on this page |

**Exceptions (both inherited from Phase 77, both apply here for the same reason):**
- The mobile "Show Roster" toggle is a `<button>` and must keep a minimum **44×44px** tap target — pad the button to reach 44px height, not just its visible chevron+text content.
- **D-12's explicit control** (the row's action button/link) is a genuinely separate tap target from the "Show Roster" toggle on the same mobile card (see Component Spec 3). It must also clear 44×44px and sit far enough from the roster toggle that a thumb cannot ambiguously hit either — minimum **8px gap**, and never stacked directly on top of one another.

### 1. Board identity on a row — text + shipped type badge, no new color system

**Decision:** every row names its board with **plain semibold text for the board name**, immediately followed by the app's **already-shipped board-type badge**, reused byte-for-byte from `Areas/Platform/Views/Group/Index.cshtml`:

```html
<span class="fw-semibold">@row.BoardName</span>
@if (row.BoardType == BoardType.Campaign)
{
    <span class="badge bg-info text-dark"><i class="fas fa-book-open me-1"></i>Campaign</span>
}
else
{
    <span class="badge bg-primary"><i class="fas fa-dice-d20 me-1"></i>One-Shot</span>
}
@if (row.IsActiveBoard)
{
    <span class="badge bg-success-subtle text-success-emphasis border border-success-subtle">
        <i class="fas fa-check-circle me-1"></i>Active
    </span>
}
```

**Why not a per-board colour chip (the research question this settles):** the operator's own stated case is *two campaigns* — same `BoardType`, so type alone cannot distinguish them, and there is no existing "stable colour derived from group id" mechanism anywhere in this codebase to generalise (`GroupPicker`, the admin Group list, and every other board-listing surface use name + type badge only, never colour). Inventing one here would mean: (a) a new hashing/assignment scheme with no precedent to review it against, (b) a scheme that must independently survive greyscale to satisfy the accessibility requirement — doable for 2 boards, unreliable past 4–5 without perceptually-adjacent hues, and (c) decoration that duplicates information the name text already carries unambiguously. **Rejected.** Name text is the primary identity signal (it is unique per board by construction); the type badge is a secondary, already-legible-in-greyscale cue (icon + text, not fill alone); the new "Active" badge (subtle/emphasis pairing, matching Phase 77's own accessible-contrast idiom for its muted-yes cell) is what actually answers "how do I tell rows apart from my current session" — which is the real scanning need, not board-to-board differentiation by hue.

### 2. Row anatomy, desktop — a divided list inside one `modern-card`, not a table

**Why not Phase 77's table:** D-02 explicitly does not port the member axis — across boards there is no single, stable member set to use as fixed columns, and roster length varies row to row. A table needs a fixed column set; this page cannot have one. The row is therefore a self-contained block, stacked vertically inside one outer `modern-card`, separated by a hairline rule rather than each row being its own nested glass card (nesting ten translucent cards inside one would be visually heavy and fight the "keep it scannable" goal the research question raises).

```html
<div class="card modern-card">
    <div class="card-header modern-card-header">
        <h2 class="mb-0"><i class="fas fa-calendar-days text-purple me-2"></i>My Agenda</h2>
    </div>
    <div class="card-body modern-card-body">
        <!-- Filter panel — Component Spec 4 — sits here, above the list -->
        <div class="agenda-list">
            @foreach (var row in Model.Rows)
            {
                <div class="agenda-row">
                    <div class="d-flex justify-content-between align-items-start flex-wrap">
                        <div>
                            <strong class="fs-6">@row.Title</strong>
                            <div class="small text-muted">
                                @row.Date.ToString("ddd, MMM d")
                                @if (row.StartTime.HasValue)
                                {
                                    @:&middot; @row.StartTime.Value.ToString("HH:mm")
                                }
                            </div>
                        </div>
                        <div class="text-end">
                            <!-- board name + type badge + Active badge, Component Spec 1 -->
                        </div>
                    </div>

                    <div class="mt-2 d-flex align-items-center gap-2">
                        <span class="small text-muted">Your answer:</span>
                        @await Html.PartialAsync("_AvailabilityCell", row.MyCell)
                    </div>

                    <div class="agenda-roster mt-2">
                        <span class="small text-muted me-1">Roster:</span>
                        @foreach (var member in row.Roster)
                        {
                            <span class="agenda-roster-entry">
                                <span class="small @(member.IsViewer ? "fw-semibold" : "")">
                                    @member.Name@(member.IsViewer ? " (you)" : "")
                                </span>
                                @await Html.PartialAsync("_AvailabilityCell", member.Cell)
                            </span>
                        }
                    </div>

                    <hr class="my-2" />
                    <div class="text-end">
                        <!-- The row's only click target: a small explicit control, never the whole row -->
                    </div>
                </div>
            }
        </div>
        <!-- Show More Events control, Component Spec 5 -->
    </div>
</div>
```

```css
.agenda-row {
    padding: 16px 0;
    border-bottom: 1px solid rgba(244, 228, 188, 0.15);
}
.agenda-row:last-child {
    border-bottom: none;
    padding-bottom: 0;
}
.agenda-roster {
    display: flex;
    flex-wrap: wrap;
    align-items: center;
    gap: 8px 16px;
}

```

**What keeps ten of these scannable:** the viewer's own answer is a fixed, always-in-the-same-place line near the top of every row (never buried in the roster), the board identity line is right-aligned and consistently placed so the eye can scan down that column, and the roster — the heaviest content — sits last, after the two facts (own answer, whose board) a reader needs first. The `<hr>` before the action control follows CLAUDE.md's button-section convention and doubles as the visual boundary between "information" and "action" on every row.

### 3. The explicit control (D-12) — a real focusable element, label + icon carry the distinction

**Both variants are filled, colored buttons** (per CLAUDE.md's button convention — no outline buttons for primary row actions). The distinction between "goes straight through" and "prompts first" is carried by the row's own **Active** badge (Component Spec 1, visible before the reader's eye even reaches the button) plus the button's label and icon — not by filled-vs-outline styling.

**Same-board row (active board) — a real anchor, direct link:**
```html
<a asp-controller="Events" asp-action="Details" asp-route-id="@row.EventId"
   class="btn btn-primary btn-sm">
    <i class="fas fa-arrow-right me-1"></i>Open Event
</a>
```

**Other-board row — a real button, opens the switch-confirm modal (never a bare `onclick`):**
```html
<button type="button" class="btn btn-primary btn-sm"
        data-bs-toggle="modal" data-bs-target="#switchBoardModal"
        data-group-id="@row.BoardId"
        data-board-name="@row.BoardName"
        data-return-url="@Url.Action("Details", "Events", new { id = row.EventId })">
    <i class="fas fa-right-left me-1"></i>Switch &amp; Open
</button>
```

**Why a real `<a>`/`<button>` and not the app's older `onclick="window.location.href=...">` row pattern (the pattern Phase 77's queued gap-closure plan `77-10` is retrofitting out of the rest of the app):** D-12 already requires the click target be a small explicit control rather than the whole row; building that control as a native focusable element from day one means this page needs no follow-up accessibility retrofit and does not add a tenth instance of the pattern `77-10` is removing. Both variants are keyboard-reachable via Tab, and the `<button>` variant triggers a real Bootstrap modal (native focus trap, `Enter`/`Space` activation, `Esc` to dismiss) rather than any custom JS.

### 4. The switch-confirm modal (D-11) — one shared modal, populated per row

**Decision: a modal**, not an inline confirm or an interstitial page. Reasoning: an inline confirm (e.g. a second click target appearing in place) risks being mistaken for the row's own content given how much is already on each row; an interstitial page is an extra full navigation for a decision that fits in one screenful of text. A modal keeps the reader's place in the list (it returns exactly where they were if they cancel) and this app already has an established modal idiom (`ShopManagement/Index.cshtml`'s deny-item modal is the closest precedent: one shared modal, populated via a `data-*` attribute + `show.bs.modal` listener, `<form>` wrapping the modal content, antiforgery token inside).

```html
<div class="modal fade" id="switchBoardModal" tabindex="-1"
     aria-labelledby="switchBoardModalLabel" aria-hidden="true">
    <div class="modal-dialog modal-dialog-centered">
        <div class="modal-content bg-dark text-light">
            <form id="switchBoardForm" asp-controller="GroupPicker" asp-action="SelectGroup" method="post">
                @Html.AntiForgeryToken()
                <input type="hidden" name="groupId" id="switchBoardGroupId" />
                <input type="hidden" name="returnUrl" id="switchBoardReturnUrl" />
                <div class="modal-header border-secondary">
                    <h5 class="modal-title" id="switchBoardModalLabel">
                        <i class="fas fa-right-left me-2"></i>
                        Switch to <span id="switchBoardName"></span>?
                    </h5>
                    <button type="button" class="btn-close btn-close-white" data-bs-dismiss="modal" aria-label="Close"></button>
                </div>
                <div class="modal-body">
                    <p class="mb-0">
                        Your active board is currently <strong>@Model.ActiveBoardName</strong>.
                        Switching to <strong id="switchBoardNameInline"></strong> will change what you
                        see everywhere else in the app — quests, shop, gold, characters, and navigation
                        will all reflect it until you switch again.
                    </p>
                </div>
                <div class="modal-footer border-secondary d-flex justify-content-between">
                    <button type="button" class="btn btn-secondary" data-bs-dismiss="modal">Cancel</button>
                    <button type="submit" class="btn btn-primary">
                        <i class="fas fa-right-left me-2"></i>Switch &amp; Continue
                    </button>
                </div>
            </form>
        </div>
    </div>
</div>
```

```html
<script>
document.addEventListener('DOMContentLoaded', function () {
    const modal = document.getElementById('switchBoardModal');
    if (modal) {
        modal.addEventListener('show.bs.modal', function (event) {
            const button = event.relatedTarget;
            document.getElementById('switchBoardGroupId').value = button.getAttribute('data-group-id');
            document.getElementById('switchBoardReturnUrl').value = button.getAttribute('data-return-url');
            document.getElementById('switchBoardName').textContent = button.getAttribute('data-board-name');
            document.getElementById('switchBoardNameInline').textContent = button.getAttribute('data-board-name');
        });
    }
});
</script>
```

**Accessibility (non-negotiable per this phase's own requirement):** Bootstrap's modal component provides `aria-modal`, moves focus into the dialog on open, traps Tab inside it, restores focus to the triggering button on close, and is dismissible via `Esc` — all native to the markup above with no extra JS. `aria-labelledby="switchBoardModalLabel"` ties the accessible name to the dynamically-set board name so a screen reader announces "Switch to {BoardName}?" on open, not a generic "dialog."

**Form posts to `GroupPickerController.SelectGroup` unchanged** (D-11/D-13) — `groupId` and `returnUrl` are the only two fields; `returnUrl` is always that row's `Events/Details` URL, never the agenda's own URL, so the reader lands on the event they asked to open, not back on the list they just left.

**Critical inherited fix (D-06), copy exactly, do not regress to the one-`stopPropagation()` shape:** put `onclick="event.stopPropagation();"` on **both** the toggle button and the `.collapse` container div itself. **How D-12's control and D-06's disclosure coexist without competing for the same tap:** they are two visually and physically separate controls — the roster toggle sits directly under the "Your answer" line, the explicit action control sits below a `<hr>` at the very bottom of the card, after the (possibly expanded) roster. Neither overlaps the other's tap area, and the vertical order (own answer → roster toggle → roster, if expanded → divider → action) means a thumb never has to choose between them mid-gesture. This is the reason the viewer's own answer is *not* hidden behind the roster toggle (see Component Spec 2's rationale) — collapsing it too would put the one thing every card must show at a glance behind the same tap as the thing D-12 needs to stay separate from it.

### 6. The board filter (D-04) — a narrowing control, never mistakable for an add

**Desktop:** a Bootstrap dropdown, `data-bs-auto-close="outside"` so ticking a checkbox does not close the panel:

```html
<div class="dropdown mb-3">
    <button class="btn btn-outline-secondary btn-sm dropdown-toggle" type="button"
            data-bs-toggle="dropdown" data-bs-auto-close="outside" aria-expanded="false">

    </button>
    <div class="dropdown-menu p-3" style="min-width: 260px;">
        <p class="small text-muted mb-2">
            Choose which of your own boards to show. This never adds boards you don't belong to — only narrows the ones shown.
        </p>
        <form asp-action="Index" method="get">
            @foreach (var board in Model.AvailableBoards)
            {
                <div class="form-check">
                    <input class="form-check-input" type="checkbox" name="boards" value="@board.Id"
                           id="board-@board.Id" checked="@board.IsSelected" />
                    <label class="form-check-label small" for="board-@board.Id">@board.Name</label>
                </div>
            }
            <hr class="my-2" />
            <button type="submit" class="btn btn-primary btn-sm w-100">Apply</button>
        </form>
    </div>
</div>
```

**Mobile:** same checklist, rendered as a native `.collapse` below the header (matching Phase 77 mobile's own "What do these mean?" legend collapse pattern exactly — no dropdown, consistent with `_Layout.Mobile.cshtml`'s established zero-dropdown convention extended to page-level controls):

```html
<button type="button" class="btn btn-sm btn-outline-secondary mb-2" data-bs-toggle="collapse"
        data-bs-target="#agenda-filter" aria-expanded="false">
    <i class="fas fa-filter me-1"></i>Filter Boards
    <span class="badge bg-secondary ms-1">@Model.SelectedCount of @Model.TotalCount</span>
</button>
<div class="collapse mb-3" id="agenda-filter">
    <div class="card modern-card">
        <div class="card-body modern-card-body p-3">
            <!-- same checklist form as desktop -->
        </div>
    </div>
</div>
```

**Why this reads as narrowing, not adding:** the toggle button itself always states the current state as a fraction ("N of M"), the helper text says so explicitly, and — the load-bearing part — the checklist only ever lists `Model.AvailableBoards`, which is the viewer's own fresh membership set (D-15); there is no code path by which an unticked box could represent a board the viewer doesn't belong to, so the UI cannot visually imply an add it structurally cannot perform.

### 7. Empty states — three distinct renders

Same visual idiom as Phase 77's and the app's existing empty-state pattern (`Calendar/Index.Mobile.cshtml`'s "Nothing This Month" block), each swapping in its own icon/heading/body from the Copywriting Contract:

```html
<!-- (a) No boards -->
<div class="text-center text-muted py-5">
    <i class="fas fa-calendar-xmark fa-3x mb-3"></i>
    <h5>No Boards Yet</h5>
    <p class="mb-0">You're not a member of any board yet. Once you join one, your upcoming events will appear here.</p>
</div>

<!-- (b) Boards, nothing upcoming -->
<div class="text-center text-muted py-5">
    <i class="fas fa-calendar-alt fa-3x mb-3"></i>
    <h5>No Upcoming Events</h5>
    <p class="mb-0">None of your boards have anything scheduled yet. Once a DM schedules a session, it will appear here.</p>
</div>

<!-- (c) Filtered to nothing — the one recoverable empty state -->
<div class="text-center text-muted py-5">
    <i class="fas fa-filter-circle-xmark fa-3x mb-3"></i>
    <h5>All Boards Filtered Out</h5>
    <p class="mb-2">You've hidden every board from view. Adjust the filter above, or</p>
    <a asp-action="Index" asp-route-boards="" class="btn btn-outline-secondary btn-sm">
        <i class="fas fa-rotate-left me-1"></i>Show All Boards
    </a>
</div>
```

Case (c) must be distinguishable from case (b) by the controller — it fires when the viewer's membership set is non-empty, upcoming events exist for it, but the *effective* (filtered) set is empty — never conflated into one generic "nothing to show" message, since only (c) has a one-click fix.

### 8. Paging (D-03/D-04)

Same shipped shape as Phase 77 (`Model.CanShowMore` = `HasMore && NextTake > Take`), applied to the agenda's own take value:

```html
@if (Model.CanShowMore)
{
    <div class="text-center mt-3">
        <a href="@Url.Action("Index", new { take = Model.NextTake, boards = Model.SelectedBoardIds })"
           class="btn btn-primary">
            <i class="fas fa-chevron-down me-2"></i>Show More Events
        </a>
    </div>
}
```

**Carry the current filter selection into the "Show More" link's query string** (`boards = Model.SelectedBoardIds`) — a link that silently dropped the filter and reloaded "all boards" would be a confusing surprise after the reader deliberately narrowed the view. Recommended starting defaults for `AgendaOptions` (a config decision, not purely visual, but stated here since it affects how often this control appears): `DefaultTake = 5`, `PageIncrement = 5`, `MaxTake = 50` — lower than Phase 77's `DefaultTake = 10` because each row here is materially heavier (full roster vs. one grid cell), so five full rows keeps the initial page short enough to actually scan.

### 9. Details back-link (D-13)

Rendered above the `modern-card` wrapper on `Events/Details.cshtml`, conditionally, only when the request arrived via the agenda's `returnUrl`:

```html
@if (ViewBag.ReturnedFromAgenda == true)
{
    <div class="mb-2">
        <a asp-controller="Agenda" asp-action="Index" class="text-decoration-none small">
            <i class="fas fa-arrow-left me-1"></i>Back to My Agenda
        </a>
    </div>
}
```

Placed outside/above the card, not inside `modern-card-header`, so it reads as page-level breadcrumb navigation rather than part of the event's own content — and so it costs nothing to omit when the flag is false (the untouched, non-agenda `Details` view is unaffected).
