<objective>
Ship the mobile agenda: a real `.Mobile.cshtml` selected by user agent, rendering one card per
event with the roster behind a disclosure control and the row's single action control kept
physically apart from it.

Two details are inherited fixes rather than fresh design, and both regressed once already on
the sibling surface:

1. The `stopPropagation` guard goes on the roster's collapse container as well as on its toggle.
   The toggle-only version is what shipped broken on the availability overview and had to be
   fixed in gap closure.
2. The mobile layout links no page stylesheets of its own, so the availability chip rules that
   arrive free on desktop have to be present in this page's own stylesheet or the chips render
   unstyled.

Purpose: make the phone surface real rather than a shrunk desktop page.
Output: one mobile view, one mobile stylesheet, one render-test class.
</objective>

Structure, following `82-UI-SPEC.md` Component Spec 5:

- A `container-fluid px-2 mt-2` wrapper with an `<h4>` carrying
  `<i class="fas fa-calendar-days text-purple me-2"></i>` and the page title.
- The filter, rendered as a `btn btn-sm btn-outline-secondary` toggle with
  `data-bs-toggle="collapse" data-bs-target="#agenda-filter"` and the "N of M" badge, over a
  `div.collapse#agenda-filter` holding a `card modern-card` whose body carries the same GET form
  as the desktop view — including the leading `<input type="hidden" name="boards" value="" />`
  before the checkboxes, without which unticking every box submits no parameter at all. Do not
  use a Bootstrap dropdown here: this layout contains no dropdown anywhere and should not gain
  its first one for a page-level control.
- One `div.agenda-card` per row containing, in this vertical order:
  1. title + date/time on the left, board identity block on the right (board name in
     `fw-semibold`, then the shipped board-type badge, then the `Active` badge when
     `row.IsActiveBoard`), stacked small;
  2. the "Your answer:" line with the viewer's own chip;
  3. the roster toggle — a real `<button type="button" class="btn btn-sm btn-outline-secondary mt-2 agenda-roster-toggle" data-bs-toggle="collapse" data-bs-target="#roster-@row.EventId" onclick="event.stopPropagation();" aria-expanded="false">` labelled `Show Roster` with `fa-chevron-down`;
  4. `<div class="collapse mt-2" id="roster-@row.EventId" onclick="event.stopPropagation();">`
     holding the roster as a `ul.list-unstyled.mb-0.small.agenda-roster` with one `<li>` per
     entry, the name (with ` (you)` and `fw-semibold` for the viewer) and the chip;
  5. `<hr class="my-2" />`;
  6. the single action control, right-aligned.

  Put `onclick="event.stopPropagation();"` on **both** the toggle and the collapse container.
  The sibling surface shipped with it on the toggle only, which let a tap inside the expanded
  roster bubble up and navigate away. These cards carry no card-level click handler at all, so
  this is defence in depth against a handler someone adds later; keep it anyway, it costs
  nothing. Say that in a comment in plain language.

- The action control is identical in contract to the desktop view's: an
  `<a asp-controller="Events" asp-action="Details" asp-route-id="@row.EventId" asp-route-from="agenda" class="btn btn-primary btn-sm">`
  labelled `Open Event` when the row is on the active board, otherwise a
  `<button type="button" class="btn btn-primary btn-sm" data-bs-toggle="modal" data-bs-target="#switchBoardModal" data-group-id data-board-name data-return-url>`
  labelled `Switch & Open`. It sits below the divider at the bottom of the card, after the
  (possibly expanded) roster, so it never shares a tap area with the roster toggle. Neither
  control is a click handler on a non-interactive element, and the card as a whole is not a tap
  target — the row carries a roster, and a whole-card target would swallow text selection while
  its consequence here is a board switch rather than a plain navigation. Record that in a
  comment, in plain language, so a later reader does not "restore consistency" with the app's
  other clickable cards.
- The same shared switch-confirm modal as the desktop view, with the same ids
  (`switchBoardModal`, `switchBoardModalLabel`, `switchBoardForm`, `switchBoardGroupId`,
  `switchBoardReturnUrl`, `switchBoardName`, `switchBoardNameInline`), posting to
  `asp-controller="GroupPicker" asp-action="SelectGroup"` with an antiforgery token, rendered
  only when at least one row is on a non-active board, plus its `show.bs.modal` listener inside
  `@section Scripts`.
- The three empty states and the paging control, with the same copy, the same
  `asp-route-boards="all"` reset sentinel, and the same filter-preserving
  `take`/`boards` paging link as the desktop view.
- Render every chip through the shared partial by full path:
  `@await Html.PartialAsync("~/Views/Events/_AvailabilityCell.cshtml", ...)`. A bare partial name
  does not resolve from `Views/Agenda/`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| request User-Agent → view selection | The user agent decides which view file renders; both must enforce the same contract |
| mobile row control → board switch | The same state-changing path the desktop view exposes, reached from a different surface |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-82-04-01 | Information Disclosure | Mobile view rendering the same model | high | mitigate | The mobile view renders the same controller-built model with no query, filter or scoping logic of its own; every scoping decision was already made server-side before the view is chosen, so the two surfaces cannot diverge on what is visible |
| T-82-04-02 | Tampering | Mobile switch-confirm control | high | mitigate | Identical contract to the desktop control: a real form POST to the existing board-selection action with an antiforgery token and a server-generated local return url; no mobile-only shortcut is introduced |
| T-82-04-03 | Tampering | Mobile filter form | medium | mitigate | The mobile filter submits the same GET parameter as the desktop one and is subject to the same server-side intersection against the fresh membership set; the view can express a narrower selection but never a wider one |
| T-82-04-04 | Denial of Service | Roster expansion | low | accept | The roster is already in the response; expanding it is a pure client-side collapse with no additional request |
| T-82-04-SC | Tampering | npm/pip/cargo installs | high | accept | No package is installed anywhere in this phase; `82-RESEARCH.md` § Package Legitimacy Audit records "not applicable" |
</threat_model>
