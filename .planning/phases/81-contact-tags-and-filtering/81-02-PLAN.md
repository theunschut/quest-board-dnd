group-query-filter block immediately after the existing `ContactNoteEntity` filter so all the
contact-related configuration stays contiguous:

1. A column-level collation on `Name`: `.Property(t => t.Name).UseCollation("SQL_Latin1_General_CP1_CI_AS")`.
   This is what makes the case-insensitive guarantee travel with the migration instead of
   depending on how a given SQL Server instance was provisioned. The dev connection string
   points at a developer's own `localhost` install whose collation is not knowable from this
   repository, so the ambient default cannot be relied on.
2. A unique index: `.HasIndex(t => new { t.GroupId, t.Name }).IsUnique()`.
3. A fail-closed group query filter of exactly the same shape as the `ContactEntity` filter
   above it: `activeGroupContext.ActiveGroupId != null && e.GroupId == activeGroupContext.ActiveGroupId`.
   The lambda must dereference `activeGroupContext.ActiveGroupId` inline. Do not assign it to a
   local first — that captures the value once at model-build time, when it is null, and
   silently disables the filter. Give this entity no cross-board escape hatch, matching the
   comment already sitting above the `ContactEntity` filter about per-board roster data.
4. The many-to-many wiring on `ContactEntity`:
   `.HasMany(c => c.Tags).WithMany(t => t.Contacts).UsingEntity(j => j.ToTable("ContactContactTags"))`.
   Use an implicit, unmapped join — no dedicated CLR join-entity class. No data needs to live on
   the association row, and the join needs no query filter of its own: every read path joins
   through two already-filtered ends, so a join row referencing an out-of-board entity on
   either side structurally cannot appear in a result.

If the build surfaces an EF Core model-validation warning about a required navigation
interacting with a query filter on the join, resolve it by adding an equally fail-closed
filter through the join configuration. Under no circumstances resolve it by disabling query
filters on any read or write path in this feature — that mechanism is forbidden across this
whole phase, and two shipped cross-tenant leaks in this app trace back to exactly that
shortcut.

`dotnet ef migrations add AddContactTags --project ../QuestBoard.Repository`. Do not run
`dotnet ef database update` — migrations auto-apply on startup through the context's own
`Migrate()` call, so no manual database step exists in this project.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| board A session -> board B data | Any tag read or write must be confined to the caller's active board; this is the app's dominant threat class |
| no-active-board session -> all boards' data | A null active group must return nothing, never every board's rows merged |
| application layer -> database constraint | Case-insensitive tag identity must be a database guarantee, because there is no rename path to repair a drifted duplicate later |

|-----------|----------|-----------|----------|-------------|-----------------|
| T-81-01 | Information Disclosure | `ContactTagEntity` reads | high | mitigate | Fail-closed `HasQueryFilter` on `ContactTagEntity` dereferencing `activeGroupContext` inline, with no cross-board escape hatch; proved by `ContactTags_NullActiveGroup_ReturnsNoRows` and `ContactTags_OtherBoardsTag_IsNotVisible` in task 3 |
