<objective>
Complete the controller side of tags: hand the create and edit forms a viewer-scoped suggestion
list, pre-fill the edit form with the contact's current tags, and persist the submitted
comma-separated value on both posts.

The server must parse exactly one value shape whether or not the client script ran. That is
what makes the chips widget a progressive enhancement rather than a dependency: a DM on a
network that blocks the CDN still gets a usable text field, and the same code path handles both.

This is also where a cross-board write would be attempted. Every submitted name is resolved
through the board-filtered reconciliation built in plan 03, so a name that exists only on
another board creates a new row on the caller's own board rather than reaching across.

Purpose: make tags writable, and prove the no-script path.
Output: the create, edit, and details actions plus the write-path integration tests.
Decisions implemented: D-01, D-02, D-04, D-06, D-16, D-23, D-29.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| form post -> tag persistence | Untrusted tag names cross into the database here; this is the phase's only write surface |
| caller's board -> another board's tag rows | A submitted name that exists on another board must create a fresh row locally, never attach across |
| view model -> rendered suggestion list | The suggestion list is derived server-side from the caller's visible contacts and must not become a channel for other tags |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-81-01 | Elevation of Privilege | Tag write path | high | mitigate | The controller never resolves a tag itself; it hands names to the board-filtered reconciliation built in plan 03, which only ever matches rows the caller's board query filter returns. Proved by `Edit_TagNameExistingOnlyOnAnotherBoard_CreatesOwnBoardRow` |
| T-81-02 | Information Disclosure | Suggestion list | high | mitigate | `AvailableTagNames` is derived from the caller's visible contacts through the same helper the index filter uses; there is no separate vocabulary query that could widen it |
| T-81-11 | Spoofing | Unauthorized tag write | high | mitigate | Both posts keep the existing dungeon-master authorization policy and antiforgery token attribute; a player cannot reach either action, so tag authorship is DM-tier by construction |
| T-81-05 | Tampering | Silent tag truncation | medium | mitigate | An over-long name is rejected with a visible model-state error rather than truncated; with no rename path in this feature, a silently shortened tag would be permanent |
| T-81-12 | Denial of Service | Oversized tag payload | medium | mitigate | The bound on the tag input field caps one request's payload; the parser drops empties so a comma run cannot inflate the tag count |
| T-81-13 | Tampering | Lost suggestion list on re-render | low | mitigate | Every invalid-model re-render path routes through one repopulation method, so a future added guard cannot ship a form with an empty suggestion list |
| T-81-SC | Tampering | npm/pip/cargo installs | high | accept | This plan installs no package. The phase's one external dependency is CDN-consumed with verdict OK per 81-RESEARCH.md; its pin is gated in plan 06 |
</threat_model>
