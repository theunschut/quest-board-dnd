<objective>
Wire tags into the Contacts index read path: bind the repeated tag ids from the query string,
derive the filter vocabulary from the viewer's visible contacts, apply the filter in memory
after the visibility gate, and carry the selection through the Show Hidden round trip.

Two ordering traps decide whether this plan is correct. First, the filter must run after the
visibility gate and never inside the query, so it can only narrow what the viewer could
already see. Second, the vocabulary must be derived from the visible-but-unfiltered set — take
it from the filtered set and ticking one tag makes every other tag vanish, so a second one can
never be added.

Purpose: give both index views a correct, tenant-safe filter model to render.
Output: the view models, the mapping, the index and toggle actions, and the integration tests
that prove narrowing, union, silent-drop, and round-trip behaviour.
Decisions implemented: D-01, D-08, D-09, D-10, D-11, D-12, D-13, D-24, D-25, D-26, D-27, D-30.
</objective>

- `ApplyTagFilter(IList<Contact> visibleContacts, IList<int> selectedTagIds)` returning
  `IList<Contact>`: return the input unchanged when no ids are selected; otherwise return the
  contacts carrying at least one selected tag id. Union semantics, so ticking more boxes widens
  the result. An id that matches nothing — unknown, already pruned, or belonging to another
  board — simply contributes no matches. Never treat an unmatched id as an error and never
  return a not-found result for one; an error response would itself confirm that an id in that
  range exists somewhere.

Rewrite the body of `Index` so the order of operations is exactly:
1. resolve the current user and the DM-tier flag, as today
2. load all contacts and apply `IsVisibleTo`, as today, producing `visibleContacts`
3. build the vocabulary from `visibleContacts`
4. apply the tag filter to `visibleContacts`, producing `filteredContacts`
5. map `filteredContacts` to view models
6. build the index view model

Never move the filter into the service or repository query, and never apply it before the
visibility gate. Applying it in the query would place it upstream of the visibility check,
which is the exact way a filter turns into a way of surfacing something hidden.

player supplying a tag id in the query string therefore receives exactly the list they would

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| query string -> contact list | Untrusted repeated tag ids cross into the read path here |
| player-tier session -> DM-only vocabulary | A player must receive no tag names, no tag ids, and no observable difference from supplying one |
| visibility gate -> tag filter | The filter must sit strictly downstream of the gate; upstream it becomes a way of surfacing hidden contacts |
| session toggle POST -> redirect target | The redirect url is composed by the app and must stay local |
