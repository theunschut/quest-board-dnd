# Phase 81 — UI Design Contract

> Visual and interaction contract for Contact Tags and Filtering. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> This phase touches **existing** Contacts views (`Index`, `Index.Mobile`, `Details`, `Details.Mobile`, `Create`, `Create.Mobile`, `Edit`, `Edit.Mobile`) rather than adding new pages. Every value below either reuses an existing token from `contacts.css` / `contacts.mobile.css` / `shop.css` / `modern-card.css`, or is a new value chosen to compose cleanly with them. Nothing here overrides `81-CONTEXT.md`'s locked decisions (D-01–D-30) — this document translates them into pixels, classes, and copy.

## Spacing Scale

Declared values (must be multiples of 4), reusing the app's existing rhythm:

| Token | Value | Usage in this phase |
|-------|-------|-------|
| xs | 4px | Chip vertical padding; gap between a checkbox and its label |
| sm | 8px | Gap between chips in `.contact-tag-list`; gap between filter row controls; gap between the mobile toggle row and the new Filter trigger button |
| md | 16px | Filter row horizontal padding; offcanvas body padding (Bootstrap default) |
| lg | 24px | Vertical gap between the filter row and the contact grid/list below it |
| xl | 32px | Not used this phase |
| 2xl | 48px | Not used this phase |
| 3xl | 64px | Not used this phase |

**Exceptions:**
- Tag chip padding is **4px / 12px** (vertical/horizontal), not a clean 4px multiple on the horizontal axis. This is not a new exception — it is the exact padding already used by `.hidden-badge` (`contacts.css:146`, `0.25rem 0.75rem`), reused verbatim so the two pill-shaped, contact-card-adjacent elements share one padding rhythm.
- `.shop-filter-row`'s existing `8px 16px` padding (asymmetric) is copied as-is per D-20 ("follows the Shop pattern") rather than normalized — do not re-litigate Shop's own spacing here.

## Typography

No new heading role is introduced. Three text roles are new to this phase (chip text, filter labels, muted tag-line/hint body text); all three reuse sizes already present in `contacts.css` / `shop.css`.

| Role | Size | Weight | Line Height | Used for |
|------|------|--------|-------------|----------|
| Body | 16px (1rem) | 400 (regular) | 1.5 | Details/Details.Mobile muted tag line body text; disabled-filter hint paragraph; two-branch empty-state body copy |
| Label | 14px (0.875rem) | 400 (regular) | 1.4 | Filter checkbox labels (`Model.AvailableTags` names), "Tags:" filter-group label, mobile offcanvas form labels, Tagify placeholder text |
| Chip | 12px (0.75rem) | 600 (semibold) | 1.3 | Tag chip text on index cards, mobile rows, and the Details tag line — matches `.hidden-badge`'s existing `0.75rem` / `600` treatment (`contacts.css:148-149`) so both pill elements read at the same visual weight |
| Heading | *not introduced* | — | — | This phase adds no new heading level. Existing `.contact-name` (Cinzel, 700, 1.3rem) and page `h1`/`h4` styles are unchanged. |

**Weights used, exactly two:** 400 (regular — body/label text) and 600 (semibold — chip text, matching the existing `.hidden-badge` weight). Do not introduce a third weight.

## Color

The app's existing 60/30/10 split is unchanged; this phase adds one new element class (the tag chip) that deliberately does **not** draw from the 10% accent budget, to avoid diluting gold as "the interactive-action color."

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | Existing dark page background + `.modern-card` translucent glass (`rgba(255,255,255,0.15)` over dark) | Unchanged — page chrome, card surfaces |
| Secondary (30%) | Existing `.contact-card` / `.contact-section-card` surfaces (`contacts.css:19`, `contacts.mobile.css:5`) | Unchanged — the cards/rows that will now also carry chips |
| Accent (10%) | `#ffc107` (gold) | **Reserved for:** the Apply Filters button's hover state (`filter-apply-btn:hover`, matching Shop), the filter checkbox `accent-color` (matching `.filter-check-label input:checked`), and the existing Create Contact / Show Hidden button treatments. **Not** used for tag chips — see below. |
| Tag chip (new, not part of the 60/30/10 split — a bounded exception for one small, repeated element) | Background `rgba(139, 69, 19, 0.35)` (bronze/leather — matches the existing `.contact-placeholder` gradient family, `contacts.css:130`); border `1px solid rgba(255, 193, 7, 0.4)` (matches `.contact-card`'s own border weight/opacity, `contacts.css:20`); text `#F4E4BC` (parchment, app-wide text color) | Every tag chip, on both index views and both Details views. **All tags render identically — no per-tag color differentiation.** There is no stable per-tag color assignment logic in this app (unlike Shop's fixed `ItemRarity` enum), and D-17's "vocabulary audit" purpose is best served by uniform chips a DM can visually diff for near-duplicates ("Shopkeper" vs "shopkeeper"), not by color noise. |
| Destructive | `#dc3545` (existing `btn-danger`) | Unchanged, and **not used by this phase.** There is no destructive confirmation dialog for tags — removing a tag from a contact happens by editing the Tagify input and saving the form (D-07: no management page), not through a separate delete action. |

**Accent reserved for:** the Apply Filters button hover, filter checkbox `accent-color`, and no other new element in this phase. Tag chips, the disabled-filter hint, and the mobile "Active" badge (which reuses Shop's neutral `badge bg-dark`, not gold) are explicitly outside the accent budget.

## Component Inventory & Placement

*(Supplementary to the template — this phase touches enough existing surfaces that placement must be pinned down explicitly to avoid drift.)*

### 1. Tag chips — `.contact-tag-list` / `.contact-tag-chip`

One chip class, reused verbatim in three contexts (D-17 requires visual consistency across surfaces):

- **Desktop index card** (`Index.cshtml`, inside `.contact-card > .contact-card-content > .contact-info`): render `.contact-tag-list` as the **last child** of `.contact-info`, after the existing `.contact-sub-location` paragraph. Order becomes: name → town/city → sub-location → tags.
- **Mobile index row** (`Index.Mobile.cshtml`, inside the `flex-grow-1` div of `.contact-member-row`): render `.contact-tag-list` **after** `.contact-member-sub-location` and **before** the `IsRevealed` hidden-badge block. Rationale: the Hidden status flag is a call-out that should remain the last, most attention-grabbing element in the stack (it already renders last today); tags are descriptive metadata and belong with the other descriptive lines above it.
- **Details (both platforms)**: render inside the portrait card, immediately after the existing `SubLocation` paragraph and **before** the Hidden badge `<div>`. Mirrors Phase 80 D-16's placement instruction for the category line ("a muted line near TownCity / SubLocation").
- **Overflow:** wrap to multiple lines (`flex-wrap: wrap`, `gap: 8px` on `.contact-tag-list`). **No truncation, no "+N" indicator** — already locked by CONTEXT.md's Claude's-Discretion note ("no hard cap on tags per contact... chip markup required to wrap gracefully instead"). Do not add a cap or overflow indicator not called for by that decision.
- **Shape:** `border-radius: 6px` (rounded rectangle, matching `.filter-apply-btn`'s radius), **not** the fully-rounded 20px pill used by `.hidden-badge`. Deliberately different shape from the Hidden status pill so a DM never confuses a tag chip for a status flag at a glance.
- **DM-tier gate (D-01):** `.contact-tag-list` renders only when `Model.ViewerIsDmTier` is true, on every one of the four surfaces above. A player-tier render must contain zero tag markup — not `display:none`, not empty markup, nothing in the DOM.

### 2. Desktop filter row — `.contact-filter-row`

- **Placement in `Index.cshtml`:** insert directly between the closing `</div>` of the header row (line 35, containing the `h1` + Show Hidden + Create button) and the opening `<div class="card modern-card">` (line 37) that wraps the grid. This mirrors Shop's structure, where `.shop-filter-row` sits below the header/category tabs and above `.shop-inventory`.
- **Gate:** wrapped in the same `Model.ViewerIsDmTier` conditional as Show Hidden/Create (D-01). Players never see this row.
- **Structure (has-tags state):** `method="get"` form, `.contact-filter-row` container (padding `8px 16px`, background `rgba(0,0,0,0.5)`, border `1px solid #444`, border-radius `6px` — copied verbatim from `.shop-filter-row`), containing:
  - `.contact-filter-label` "Tags:" (mirrors `.filter-label`)
  - `.contact-filter-tag-group` — one `.contact-filter-check-label` per available tag (checkbox + tag name, 14px/400), checked state pre-populated from `Model.SelectedTagIds`
  - `.contact-filter-apply-btn` "Apply Filters" (mirrors `.filter-apply-btn` exactly: dark background, gold hover)
  - `.contact-filter-clear-btn` "Clear Filters", rendered **only** when `Model.HasActiveFilters` is true (mirrors Shop's conditional Clear button)
- **Structure (D-19 no-tags-yet state):** same outer `.contact-filter-row` container (so the page layout doesn't shift once tags exist), but its contents are replaced with a single line: `<i class="fas fa-tag me-2"></i>` + the disabled-hint copy above, styled at 60% opacity with `cursor: not-allowed` on the container. No checkboxes, no Apply/Clear buttons are rendered — there is nothing to check yet.

### 3. Mobile filter trigger + offcanvas — `#contactFilterOffcanvas`

- **Trigger button placement in `Index.Mobile.cshtml`:** a new full-width button **below** the existing `.contact-toggle-row` (Show Hidden + Create) and **above** `.contact-section-card`. Do not add it as a third button inside `.contact-toggle-row` itself — three `flex:1` buttons in one row is too cramped on a phone width; Shop's own mobile pattern already establishes "filter trigger gets its own full-width row," which this copies.
- **Trigger button classes/copy:** `btn btn-warning w-100 mb-3` (identical Bootstrap utility classes to Shop's trigger, no new CSS class needed), label "Filter Tags" with `fa-filter me-2`, plus `<span class="badge bg-dark ms-1">Active</span>` when `Model.HasActiveFilters` is true — verbatim copy of Shop's active-filter badge treatment (`Index.Mobile.cshtml:74`, Shop).
- **D-19 no-tags-yet state:** render the trigger button with the `disabled` attribute set, plus a small helper text line directly beneath it using the disabled-hint copy above (Body role, muted). Do not hide the button entirely — per D-19's discoverability rationale (same logic as Phase 80 D-07), a DM should see the control exists even before it has anything to filter.
- **Offcanvas structure:** `offcanvas offcanvas-bottom`, title "Filter by Tag", body containing the same checkbox list (`.contact-filter-check-label`-style `.form-check` rows, one per tag, Bootstrap's native pattern as Shop's mobile rarity checkboxes use) plus Apply Filters / Clear Filters buttons in a `d-flex gap-2` row — structurally identical to `Shop/Index.Mobile.cshtml`'s `#shopFilterOffcanvas` body, minus the category-tab and search sections Shop has and Contacts does not.

### 4. Tag entry widget (Create/Edit, all four views)

- Wrap the real `<input>` in a labeled field: label "Tags", the input itself, helper text "Optional — e.g. shopkeeper, quest giver" below it (matches the existing form-field helper-text pattern already used for `ContactImageFile` on `Create.cshtml:25`).
- Placement on the form: directly after the `TownCity`/`SubLocation` row, before the `_MarkdownEditor` Description partial — tags are identity/classification metadata, grouped with the other short identity fields rather than with the long-form description.
- Tagify CSS override scope: wrap the input in a container class `.contact-tags-input`; override Tagify's CSS custom properties inside that scope only (`--tag-bg: rgba(139, 69, 19, 0.35)`, `--tag-text-color: #F4E4BC`, `--tags-border-color: rgba(0,0,0,0.3)`, `--tags-focus-border-color: #ffc107`) so the widget's chips match `.contact-tag-chip`'s read-only appearance, and its focus ring matches the app's existing gold focus treatment (`modern-card.css:117-118` uses blue for generic inputs, but tags are the one field in this app where gold focus is appropriate — it is functionally a tag/filter control, not a generic text field).
- No hard character-count UI is shown for the ~30-char cap (Claude's Discretion) — rely on `maxlength`/server validation; do not add a live counter, which no other field in this app has.

## State Matrix

| State | Desktop | Mobile |
|-------|---------|--------|
| Board has zero tags, viewer is DM-tier | `.contact-filter-row` renders in the disabled-hint form (no checkboxes) | Trigger button renders `disabled` + helper text beneath it |
| Board has tags, no filter applied, viewer is DM-tier | Full `.contact-filter-row` (checkboxes unchecked, no Clear button) | Trigger button enabled, no "Active" badge |
| Filter applied, results exist | Full `.contact-filter-row` (checked boxes reflect `SelectedTagIds`, Clear button visible) + chips visible on matching cards | Trigger shows "Active" badge; offcanvas pre-checks selected tags |
| Filter applied, zero results (D-21 branch 1) | Empty-state branch 1 copy + Clear filters action; `.contact-filter-row` stays visible above it | Same copy; trigger + offcanvas stay reachable |
| Contact list genuinely empty (D-21 branch 2) | Empty-state branch 2 copy (existing, unchanged); filter row does not render (nothing to filter) | Same |
| Viewer is player-tier (any of the above) | Zero tag markup, zero filter markup — flat list exactly as Phase 80 leaves it | Same |
| Show Hidden toggled with an active tag filter (D-13/D-30) | Filter row's checked state is preserved after the redirect (hidden `<input type="hidden" name="tag">` fields carry `SelectedTagIds` through the Show Hidden `<form>`) | Same, via the mobile toggle form |
| JS blocked/failed on Create/Edit (D-16) | Tag field degrades to a plain `<input>` showing `shopkeeper, quest giver`; label/helper text unchanged | Same |
