<objective>
Render the desktop half of the tag surface: a filter row above the contact grid, tag chips on
each card, a muted tag line on the details page, and the two empty-state branches — all inside
the audience conditional the page already uses.

The index is doing double duty here. It is the only place a DM ever sees the board's whole tag
vocabulary at once, because this feature deliberately ships without a management page. That is
what makes a near-duplicate like a misspelled variant noticeable at all, so the chips and the
filter list matter beyond decoration.

Purpose: make tags visible and filterable on the desktop layout.
Output: the styles, both view changes, and the markup tests covering audience, vocabulary
scoping, empty states, and escaping.
Decisions implemented: D-01, D-11, D-17, D-18, D-19, D-20, D-21, D-24, D-26, D-27.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| DM-authored tag name -> rendered html | Free-typed text reaches every viewer of the page and must never become markup |
| DM-tier surface -> player-tier response | A player must receive no tag markup at all, not hidden markup |
| board vocabulary -> the filter checkbox list | The list names real tags; anything wider than the viewer's visible contacts would leak |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-81-02 | Information Disclosure | Player-tier index and details responses | high | mitigate | Every tag surface sits inside the single existing audience conditional, and the controller already leaves the tag collections empty for a player, so nothing renders even if a conditional were wrong. Proved by the two player tests, which assert absence of the class names and the tag names themselves rather than absence of a visible element |
| T-81-02b | Information Disclosure | Filter vocabulary | high | mitigate | The list is bound straight from the viewer-scoped collection the controller derived; the view adds no second source. Proved by the unrevealed-contact test in both toggle states |
| T-81-15 | Cross-Site Scripting | Tag name rendering | high | mitigate | Tag names render through ordinary escaped output only; the acceptance criteria assert zero raw-output and markdown helpers in the index, and the details markdown count is pinned unchanged. Proved by the markup-characters escaping test |
| T-81-16 | Tampering | Lost filter on the toggle round trip | medium | mitigate | The toggle form carries one hidden input per selected id, asserted by both a markup criterion and a test |
| T-81-17 | Information Disclosure | Empty-state branch confusion | low | mitigate | The no-match branch and the genuinely-empty branch are distinct and separately tested, so a filtered-to-nothing board never implies the board is empty |

## Forward compatibility with category headings

This phase ships against today's flat contact list; the category-heading pass is a separate,
unbuilt phase. The composition guarantee this plan is responsible for is that the view renders
whatever collection the controller hands it, which is already the filtered set — so when
headings arrive they group an already-narrowed list and empty ones drop out under the same
suppression rule, with no second rendering mode and no bypass. Nothing in this plan hard-codes
a flat structure that a grouping pass would have to unpick.
</verification>
