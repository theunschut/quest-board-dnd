Facts the executor needs (verified 2026-11-11 on this machine):
- Linux, zsh/bash. Python 3 is `python3` (there is no `python`), with Pillow 12.1 (WebP supported) and numpy 2.3; scipy
  is not installed. Node 24.
- SQL Server is the operator's Docker container `mssql-dev` on localhost:1433. The SQL login comes from the developer's
  user-secrets. Never edit `appsettings.json`, never read or print the user-secrets, and never start, stop or
  provision the container: if 1433 is unreachable, stop and report.
- Phase 94 scratch (`~/qb-ui-review/phase-94/`): `tools/` holds `playwright` 1.64.1 in `node_modules` (headless
  Chromium cached in `~/.cache/ms-playwright`), plus `login.mjs`, `audit-shoot.mjs`, `register.mjs`, `run-app.sh`,
  `stop-app.sh`, `run-baseline.sh`, `sweep.mjs`, `probes.mjs`, `fixtures.mjs` and more. `credentials.json` has the shape
  `{ board: "Audit Board", accounts: [{ role, email, password }] }` with roles `superadmin` (qb-audit-platform),
  `admin`, `player` and `dm`, all `@example.invalid`.
- The local database is a copy that holds REAL boards and members. All review work stays on the "Audit Board"
  (id 7). Never capture or store another board's data.
- There is no self-registration route. An admin creates accounts at `/Admin/CreateUser` (Email, Name, GroupRole
  Player/DungeonMaster/Admin; Development suppresses the set-password email) and sets a password at
  `/Admin/ResetPassword/{userId}` (NewPassword). SuperAdmin has no UI.
- `MobileDetectionMiddleware` matches `Mobi|Android|iPhone|iPad|Windows Phone|BlackBerry`; Playwright's default
  User-Agent matches none, so the phone pass uses `devices['Pixel 7']` (UA, `isMobile`, `hasTouch`). Resizing alone
  renders the desktop views.
- Authenticated pages also need an active board: log in at `/Account/Login`, pick the board at `/groups/pick` through
  its form, then save `storageState`. A state issued by one source tree is rejected by another (the data protection
  key ring is scoped to the content root), so states are per port.
- The default profile in `launchSettings.json` binds both `https://localhost:8001` and `http://localhost:8000`, which
  would collide with the frozen baseline the next plan starts on 8001. Every launch in this phase therefore uses
  `dotnet run --project QuestBoard.Service --no-launch-profile --urls http://localhost:<port>` with
  `ASPNETCORE_ENVIRONMENT=Development` set explicitly: 8000 is the working tree, 8001 the frozen baseline. The Claude
  preview config `questboard-service` in `.claude/launch.json` may also own 8000; `run-app.mjs` must accept a listener
  on 8000 that serves the repository tree.
