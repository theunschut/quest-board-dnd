<blockers>

**1. 84-02 Task 1 — blocking checkpoint:decision (needs the operator)**

Four one-way concretizations of decisions `84-CONTEXT.md` already locked (D-05 dedicated
token table, D-08 tombstone not hard delete). One-way because Apple and Google store a
subscribed address on their own servers and refetch it indefinitely:

1. **Table** — `CalendarSubscriptions(Id, UserId, Name[60], Token[unique index], CreatedAt, LastFetchedAt, RevokedAt)`. `RevokedAt` keeps revoked rows forever so `410` stays distinguishable from `404`.
2. **Token** — 32 bytes from `RandomNumberGenerator.GetBytes(32)`, Base64Url → 43 chars, stored plain text (per D-06) so the address can be shown again later.
3. **Entry identifier** — `questboard-event-{eventId}`, fixed literal prefix + `CalendarFeedSource` name + numeric id, never derived from config or request host. Changing it later gives every subscriber a duplicate of every event with no server-side remedy.
4. **Route** — `/feeds/calendar/{feedToken}.ics` on its own `[AllowAnonymous]` controller with explicit `[Route("feeds/calendar")]`. `/calendar/...` is unavailable — `QuestBoard.Service/Controllers/QuestBoard/CalendarController.cs` owns that conventional prefix (verified).

Options are `proceed-as-specified`, or `amend-before-shipping` naming which of the four
changes and to what. Full text at `84-02-PLAN.md` lines 163-187.

**2. Retention sub-question raised against item 1 — open, non-blocking**

The operator asked whether revoked rows could be purged after ~30 days via a Hangfire job
instead of kept forever. Findings from this session:

- Hangfire is already wired: `Hangfire.AspNetCore` + `Hangfire.SqlServer` 1.8.23, with two recurring jobs in `QuestBoard.Service/Jobs/` (`DailyReminderJob` 09:00, `RecurringOccurrenceTopUpJob` 03:00) registered at `QuestBoard.Service/Program.cs:355`, both unit-tested. A sweep would be idiomatic and small.
- Purging is safe — 256 bits of token entropy makes collision with a purged token a non-scenario. Storage is a non-argument at this project's scale.
- The real argument for purging is data hygiene: a revoked token sits in the DB in plain text, so an old backup contains fewer live-looking secrets.
- Cost of waiting is zero: `RevokedAt` is exactly the column a retention job needs, so this is **not** a one-way door.
- If adopted: a purged token's response changes `410` → `404`. 84-05's "revoked returns 410" tests still pass (they test fresh revocations), but the retention job needs its own test asserting "purged → 404" so the transition is deliberate.

Recommendation given: approve the four as specified, capture retention as a separate slice.
</blockers>
