# Phase 84 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope reminder:** this contract governs one thing only — a new "Calendar Subscription" section added to the existing Profile page, on both `Views/Account/Profile.cshtml` and `Views/Account/Profile.Mobile.cshtml`. The feed endpoint, the ICS writer, the token table, and the repository query are backend and out of scope here (see `84-RESEARCH.md`). Nothing in this document proposes a new page, a new palette, or a new component library — it detects and locks the design system this codebase already has.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Section heading | "Calendar Subscription" (singular — the feature; the list beneath it may hold several named subscriptions) |
| Primary CTA (empty state) | **Add Subscription** — verb + noun, matching the established "Add Category" CTA shape from Phase 80's Manage Categories page |
| Empty state heading | "No calendar subscriptions yet" |
| Empty state body | "Get this board's schedule onto your phone's own calendar app. The address below acts like a password — anyone who has it can see your events, dates, and times, and it never expires on its own. Press Add Subscription to create one; nothing is generated until you do." |
| Populated-row created label | "Created {MMM d, yyyy}" (matches this codebase's existing `CreatedAt.ToString("MMM d, yyyy")` convention, e.g. `Contacts/Details.Mobile.cshtml`) |
| Populated-row last-fetched, never fetched | "Never fetched yet" — muted, not bold, not styled as an error or warning. Must not read as "broken." |
| Populated-row last-fetched, has fetched | "Last fetched {MMM d, yyyy h:mm tt}" (matches `note.CreatedAt.ToString("MMM d, yyyy h:mm tt")` convention from `Contacts/Details.Mobile.cshtml`) |
| Rename modal heading | "Rename Subscription" |
| Rename field label | "Name" (placeholder: "e.g. My Phone") |
| Copy button, idle | "Copy" (icon: `fa-copy`) |
| Copy button, just-copied feedback | Label swaps to "Copied!" (icon: `fa-check`, color shifts to the existing `btn-success` green) for **2 seconds**, then reverts to "Copy" / `fa-copy`. No toast, no page reload — this is a per-button, self-contained state change, since the row already renders inline and a shared toast container is unnecessary machinery for a same-page confirmation. |
| webcal link | "Open in Calendar App" (icon: `fa-mobile-screen-button`; `href="webcal://..."`) |
| Show QR trigger | "Show QR Code" (icon: `fa-qrcode`) — opens a modal, does not render the QR inline in the row (see UI Considerations, QR presentation) |
| QR modal heading | "Scan to Subscribe" |
| QR modal body copy | "Point your phone's camera at this code to add {subscription name} to your calendar app." |
| QR image accessible text | `aria-label="QR code encoding the {subscription name} calendar subscription address"` — **never** the literal address string. A sighted user already sees the plaintext address in the row; a screen-reader user must not have the bearer token narrated aloud from an image alt attribute. |
| Rename affordance | "Rename" (icon: `fa-pen`) — opens a small modal (reusing this codebase's existing `show.bs.modal` + `event.relatedTarget` idiom, the same pattern `Shop/Index.cshtml` and `_CharacterSelectModal.cshtml` already use), not a navigation to a separate Edit page. The subscription section lives entirely on Profile; navigating away and back for a one-field rename would contradict D-15's "section, not a page." |
| Destructive action label | "Delete" (icon: `fa-trash`) — **the visible label is literally "Delete,"** per 84-CONTEXT D-07/D-08: the UI action is named Delete even though the underlying operation is a revoke-with-tombstone. Do not rename the button to "Revoke" — that would create a second name for one action with no user-facing benefit. |
| Destructive confirmation | Delete: `confirm('Delete "{name}"? Any device using this address will silently stop receiving updates the next time it checks — this cannot be undone. You can always create a new subscription afterward.')` — matches this codebase's existing native-`confirm()` pattern (`ContactCategoryManagement/Manage.cshtml`'s delete-category confirm), and states the specific, otherwise-invisible consequence (a device goes quietly stale) rather than a generic "are you sure." |
| Error state (mint/rename/revoke failure) | Reuse the existing server-rendered `_Toasts` partial / validation-summary pattern already wired into Profile's POST actions elsewhere in this codebase — "Couldn't {add/rename/delete} this subscription. Try again, and if it keeps happening, let a Dungeon Master know." No new error-surface mechanism is introduced. |
| Forbidden claim (duration) | No copy anywhere in this section may state or imply that the board or the calendar entry knows how long an event runs. 84-CONTEXT D-02's one-hour block is invented for calendar-client rendering only; do not write "your events show their real length," "one-hour sessions," or similar. |
| Forbidden claim (refresh speed) | No copy may promise a specific refresh interval ("updates every hour," "syncs within minutes"). Per `84-RESEARCH.md` Pitfall 2, every refresh-cadence signal is client-controlled and undocumented by the vendors (LOW confidence). If any copy addresses this at all, it must read like: "Your calendar app decides how often to check for updates — this can take anywhere from a few minutes to about a day," never a specific promised number. |
| Forbidden claim (`X-WR-CALNAME`) | No copy may promise the subscription will be named or renamed automatically inside the reader's calendar app (Apple Calendar is reported not to honour this reliably — Pitfall 1). The Name field is this app's own list label, shown here on Profile — not a guarantee about what the phone displays. |

### Address field presentation (D-06)

The full subscription address must be visible in the row at all times once the subscription exists — not hidden behind a reveal click (that would contradict D-06's "stays visible ... at any time"). On a narrow phone layout, an 80+ character bearer token cannot wrap or blow out the row:

- Render the address in a `readonly` (not `disabled`) monospace text field or styled `<code>` block, `font-size: 14px`, inside a fixed-width container with `overflow-x: auto; white-space: nowrap;` (horizontal scroll within the field, not page-level overflow) or CSS `text-overflow: ellipsis` if scroll is judged too fiddly on a touchscreen — planner's call between the two, either satisfies "stays visible and selectable."
- The field must remain focusable and fully selectable (`readonly` inputs are; do not use `disabled`, which is not focusable and cannot be selected or copied via keyboard).
- The Copy button is the primary, expected path (Copywriting Contract), but a manually-selectable field is the fallback for any browser or assistive-tech path where the clipboard API is unavailable.

### QR presentation (D-14)

- The QR is rendered **inside a modal**, triggered by a "Show QR Code" button per row — not inline in every row by default. 84-CONTEXT D-15 already accepts that "a subscription table with per-row rename and delete controls plus a QR code will dominate" the Profile page; gating the QR behind a per-row trigger is how this contract keeps that accepted cost from compounding across several rows (D-05: "a reader may hold several"). This does not violate D-06, since D-06 concerns the *address text*, not the QR's visual encoding of it — the address itself stays inline and always visible per the field above.
- Inline SVG (`SvgQRCode` per `84-RESEARCH.md`) sized to approximately 240×240px inside the modal on both layouts — large enough for a phone camera to focus on a laptop screen at arm's length, small enough not to need its own scroll region inside a Bootstrap modal body.
- The modal also restates the Copy button and the "Open in Calendar App" (`webcal://`) link alongside the QR, so all three of D-14's delivery paths are reachable from one place once opened — the row itself only needs the one "Show QR Code" trigger plus the always-visible Copy button next to the address field.

### Row focus order (accessibility)

For a populated row carrying Copy, Show QR, Rename, and Delete: order these controls left-to-right in the DOM exactly as they read visually — Copy adjacent to the address field it copies, Show QR next, then Rename, then Delete last (destructive actions trail, matching `ContactCategoryManagement/Manage.cshtml`'s Rename-before-Delete ordering). Do not use `tabindex` to reorder focus; this codebase's established `row-nav-link` convention relies on DOM order matching visual and focus order everywhere else, and this row should not be the exception.

### Rename affordance (decision, not left to the planner)

A small Bootstrap modal per row, reusing the existing `show.bs.modal` + `event.relatedTarget` idiom already established in this codebase (`Shop/Index.cshtml`, `ShopManagement/Index.cshtml`, `_CharacterSelectModal.cshtml`) — not a full-page navigation to a separate Edit view. The category-management precedent (a dedicated `Edit` page) is a heavier pattern appropriate to a page whose sole purpose is management; the subscription section lives inside Profile alongside unrelated content, so leaving and returning to rename one field would be worse UX here than the modal this codebase already knows how to build.
