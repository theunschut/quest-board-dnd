Write the failing tests first in `QuestBoard.UnitTests/Services/CalendarFeedWriterTests.cs` covering every behavior above, then widen `CalendarFeedWriter` until they pass. The writer stays a pure function: no injected clock, no configuration, no I/O, no `IOptions` of any kind — everything it needs arrives in `CalendarFeedEntry` or in the `calendarName` argument. **Branch selection.** `StartTime` being null is the whole test for an all-day entry, matching `EventEntity.StartTime`'s own documented meaning. There is no third branch and no "unknown duration" case.

**Timed branch.** Emit `DTSTART:` followed by `{Date:yyyyMMdd}T{StartTime:HHmmss}`, and `DTEND:` followed by the same instant plus exactly one hour, computed by building a `DateTime` from `Date` and `StartTime` and calling `AddHours(1)` so a late start rolls the date forward. Emit no zone parameter and no trailing `Z`: the value is floating local time, which the reading device interprets in whatever zone it is in. This matches the schema exactly — an event is a date plus a nullable time and the codebase holds no timezone concept anywhere. The one-hour length is invented for rendering and must never be described in any user-facing copy as something the board knows.

**All-day branch.** Emit `DTSTART;VALUE=DATE:{Date:yyyyMMdd}` and `DTEND;VALUE=DATE:{Date.AddDays(1):yyyyMMdd}`. Comment this in plain language: the date-valued end is exclusive, so a single-day entry ends on the following day; using the same date for both, or an inclusive end, renders a one-day event across two days on most clients.

**Escaping.** Add a private text escaper applied to every free-text value the writer emits — the composed title and the calendar name. Replace in this order: backslash with two backslashes, then semicolon with backslash-semicolon, then comma with backslash-comma, then any carriage-return-line-feed, bare line feed or bare carriage return with the two literal characters backslash and `n`. The order matters: escaping the backslash last would double-escape the escapes the earlier rules introduced. Board and event titles are free text a Dungeon Master types, so this is not theoretical.

**Folding.** Add a private folder applied to every content line after it is fully composed and escaped. Encode the line to UTF-8, emit at most 75 octets on the first physical line, then emit each subsequent chunk as one space followed by at most 74 octets, so no physical line exceeds 75 octets before its terminator. Cut only on a character boundary — walk the string by text element or by checking UTF-8 continuation bytes; splitting mid-sequence corrupts the reconstructed value on the reader's side. Do not fold the terminator itself.

**Transparency and omissions.** Every entry emits `TRANSP:TRANSPARENT` and `SEQUENCE:0`. The writer emits no description property, no link property, no alarm component and no cancellation status property. Comment each omission in plain language and for its own reason: an event description is unbounded Markdown and a calendar entry wants plain text; a link would open a board other than the one the reader is signed in to; a reader sets their own alerts once on a subscribed calendar rather than having them published to everyone; and a cancelled event is dropped from the query rather than marked, so a cancellation status can never occur here. There is no modified timestamp anywhere on an event, so the sequence number is a constant — say so, and say that changing it would need a new column rather than a different format.

**Line assembly.** Build the document into a `StringBuilder` and terminate every content line with `"\r\n"`, including the final calendar terminator. Do not rely on `AppendLine`, whose terminator follows the host platform.

The source file uses CRLF line endings; convert after writing if the tool emits LF. Put no requirement id, phase number or plan number in any comment or string literal.
