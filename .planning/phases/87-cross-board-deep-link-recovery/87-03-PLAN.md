<objective>
Give the group picker the one thing it has always been missing: when the link that sent the viewer there names a page on exactly one of their boards, stop asking which board and just take them to the page.

Purpose: this is the operator's own scenario, raised during the discuss pass — a session expires, the picker appears, they pick the board they were last on rather than the board the link belongs to, and they get the 404 anyway. It is a genuinely different code path from the wrong-board one, and it is the path every emailed link takes after a fresh login. The middleware cannot serve it, because a viewer with no board at all never reaches the middleware's guard.

Output: a return-URL reader sharing the closed registry, a new branch in `GroupPickerController.Index`, the third and last caller of the shared active-board switcher, and the tests that prove the skip happens when it should and provably does not when it should not.
</objective>

1. **Planner resolution of 87-RESEARCH.md Open Question 1, picker half.** The picker-skip path has no previous board — the viewer had none when they arrived — so it writes only the banner's target-name key and the shared partial renders the sentence with no switch-back control. Offering "go to the group picker" instead was considered and rejected: the viewer has just been deliberately routed *past* the picker, and a control sending them back to it undoes the whole point. The picker is still one click away in the ordinary navigation.
2. **Planner discretion — the skip is checked before the existing single-board auto-select, not after.** When the viewer has exactly one board both branches produce the same outcome, so the ordering only matters for a multi-board viewer, which is the case this branch exists for. Checking first also keeps the two branches independent: the existing one is about *having* one board, the new one is about the *link* naming one.
3. **Planner discretion — the return-URL reader lives on the same type as the route-value reader.** `CrossBoardRouteTarget` already turns route values into a registry hit; the picker needs the same answer from a URL string. Both entry points on one type keeps a single definition of "which routes participate" and makes it impossible for the two paths to disagree about a route.
4. **Scope honesty on the email chain (D-20).** The hop this phase changes — the picker receiving a return URL and resolving it — is covered end to end by an automated test. The hop *before* it, a successful interactive login handing the return URL to the picker, is asserted only at the redirect it emits: the shared integration harness authenticates through a test scheme rather than the Identity cookie, so a cookie-authenticated request after a real login is not something this suite can follow. That seam is flagged for the human-verify checkpoint in 87-04 rather than claimed as proven.
