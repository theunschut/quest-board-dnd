<assumption_delta_decision>
**Primary noun:** the request's *target board*.

**Decision: add-alongside.** Session stays the single source of truth for "which board am I on". The target board is resolved per request, written into Session before the action runs, and then forgotten — it never becomes an explicit, request-scoped noun carried through the pipeline, and no route is board-qualified.

This is not a fresh decision: 87-CONTEXT.md D-06 locked "a new middleware that repoints the session", and it explicitly rejected board-qualified routes (`/b/{board}/quest/42`) on the grounds that they rewrite every URL the app emits and do nothing for links already sitting in someone's mailbox — which is the case this phase exists for. That rejection is recorded as a deferred idea, not a cut one. This block records the consequence rather than re-deciding it.

**Accepted debt.** The application still cannot hold two boards live within one request. Everything downstream of the switch sees exactly one board, the newly-active one, and the board the viewer came from survives only as three TempData values rendered into a banner.

**What would force a promote.** Any of: a page that must render Board A's data while Board B is active (the cross-board agenda already sails close to this, and got there by doing its own membership-scoped read rather than by changing the noun); a cross-board *write*; a route that must serve two boards at once; or board-qualified URLs becoming the emitted shape. At that point the target board has to become explicit in the request — a resolved value carried through the pipeline with Session demoted to a default — and this middleware becomes the compatibility shim for old links rather than the mechanism.

**Optional contract test (not required by any task):** a future phase could assert that `IActiveGroupContext` exposes no second board id, so re-introducing the singular assumption after a promote goes red rather than landing silently.
</assumption_delta_decision>

A request that fails the gate is answered exactly as it is today. A client sending no `Sec-Fetch-*` headers at all fails the gate and gets today's 404 — chosen over a confirm interstitial because that would mean a second user-facing surface plus its mobile twin for a near-nonexistent client, and a missed twin is a recorded failure mode in this codebase.
8. **Planner discretion — the enum grows one member per implemented lookup, and the repository switch has no silent default.** This plan defines `CrossBoardLookupKind` with only the member the tracer uses. Plan 87-02 adds the rest. The repository's switch over the enum ends in a `default` that throws `ArgumentOutOfRangeException`, so a member added later without a projection fails loudly during development instead of silently resolving to "no board", which would look identical to a legitimate non-member miss.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → application | An authenticated viewer's request carries a URL naming an entity id on some board, plus `Sec-Fetch-*` headers the browser generates and a direct HTTP client can forge |
| session → EF Core global query filters | `ActiveGroupId` in Session is the single value 18 `HasQueryFilter` predicates key off; anything that writes it decides what every subsequent query in that request can see |
| application → tenancy boundary | `CrossBoardLinkRepository` is the only code in this phase permitted to read past those filters |
| another origin's page → this application | An inline subresource reference (image, iframe, fetch) to one of these URLs is a request this application will answer while carrying the viewer's cookies |
