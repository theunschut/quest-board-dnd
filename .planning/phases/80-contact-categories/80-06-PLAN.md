<objective>
Group the contacts index by category on both platforms, add the DM-tier entry point to the Manage
Categories page, and pin the three rules most likely to regress: a heading never appears for a
category the viewer can see nothing under, headings follow the DM's order with Ungrouped last, and a
board with no categories looks exactly as it does today.

The suppression rule is the sharpest in the phase. A category name is itself campaign-revealing, so a
heading over an empty space is a spoiler even with nothing beneath it. It is enforced structurally
rather than by a runtime check: the grouping runs over an already-visibility-filtered list, and a
grouping over a filtered sequence cannot produce an empty group. That is why the insertion point in
the controller is exact and non-negotiable.

Purpose: the feature's whole visible payoff.
Output: a grouped index on both platforms, with the rules under test.
</objective>

projecting each group into a `ContactCategoryGroupViewModel` whose title is the category name or the
literal `Ungrouped` when the id is null, whose uncategorised flag is set from that same null check,
and whose contacts are the group's members ordered by name.

Grouping runs over the already-filtered list, which is what makes empty-heading suppression
structural: a grouping over a filtered sequence cannot emit a group with no members, so no separate
drop-empty-groups step exists and none should be added. Do not move any part of this into the
repository, into the database query, or into either view. Do not add a count to the group projection —
the group view model has no count member and must not gain one.

Keep populating the flat `Contacts` list exactly as today in both cases. It stays the single source
for the page's "no contacts at all" empty state, so neither view has to reason about the interaction
between having categories and having nothing to show.
