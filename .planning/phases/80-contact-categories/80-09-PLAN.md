<objective>
Close the two contrast/legibility defects UAT found against the running app after phase 80's
eight implementation plans had already merged. Both belong to the same family: this project
themes card text by ENUMERATING elements, and any element outside the enumeration falls back
to a Bootstrap default that is wrong on the dark notice-board background.

Gap 1 — the mobile "New Category Name" label sits outside every card wrapper, and
`contacts.mobile.css` is the only mobile form stylesheet in the project with no `.form-label`
rule at all, so nothing matches it (relates to D-08, CONTACTCAT-08).

Gap 2 — `modern-card.css` enumerates `p, li, span, small` but never anchors, so the
"Manage Categories" link nested inside the zero-category helper text keeps Bootstrap's link
colour at a measured 3.09:1 (relates to D-07, CONTACTCAT-15).

Purpose: the one element on each surface that is supposed to instruct the DM is currently the
least legible thing on it. Gap 2 is an outright WCAG AA failure for body text.
Output: two scoped CSS rules per gap-family, one non-visual scoping class, and a six-fact
guard suite that pins the fixes and the two scoped overrides already shipped.
</objective>

<design_decisions>
Decisions taken during planning so the executor does not have to re-derive them. Each was
checked against the codebase, not assumed.

**Gap 1 — scoping class over unscoped rule over card wrapper.**
Three options existed. (a) A bare `.form-label { ... !important }` in `contacts.mobile.css` is
forbidden: an unscoped selector carrying `!important` is exactly the pattern this codebase has
been moving away from. (b) Wrapping the Add form in `.contact-section-card` changes the page's
visual layout, deviates from the markup 80-UI-SPEC.md pins for this view (the form is specified
at top level, above the first card), AND still does not fix anything on its own — grep confirms
`contacts.mobile.css` has no `.contact-section-card .form-label` rule either, so a wrap would
have to be paired with a new rule regardless. (c) Chosen: put a scoping class on the `<form>`
that already exists and scope the rule to it. Zero visual change, the selector is scoped, and
`.category-mgmt-add-form` follows the file's own established naming (`.category-mgmt-row`,
`.category-mgmt-reorder-btn`).

**Gap 2 — `.modern-card .form-text a`, never `.modern-card a`.**
A broad `.modern-card a` (specificity 0,2,1) would out-specify `.modern-card .btn` (0,2,0) and
repaint the text of every anchor-styled button inside every modern card in the app, and would
out-specify `.row-nav-link` (0,1,0), breaking the `color: inherit` that keeps clickable rows
looking like rows. Both are real regressions on surfaces this phase never tested. The narrow
`.modern-card .form-text a` matches only anchors inside form helper text — and the four Contacts
Create/Edit views are the only views in the project that put a link there (re-verified by grep
during planning). It also stays below `.modern-card .table .email-link` (0,3,1), so the table
email links are unaffected.

**Gap 2 needs TWO stylesheets, not one.**
The UAT lists all four Contacts Create/Edit views as affected, but only `modern-card.css` as the
artifact. That is incomplete: `Create.cshtml`/`Edit.cshtml` wrap in `.card modern-card`, while
`Create.Mobile.cshtml`/`Edit.Mobile.cshtml` wrap in `.contact-form-card` and load
`contact-form.mobile.css`. Neither `mobile.css` nor `site.css` themes a generic `a`. Fixing only
`modern-card.css` would leave the mobile half of the gap rendering Bootstrap link blue, so the
truth "the helper link reads as an invitation" would still be false on a phone. Both files get
the rule.

**The colour is cream `#F4E4BC`, not gold.**
`.character-detail-card a` and `.contact-detail-card a` already establish cream as this project's
treatment for an anchor inside a dark glass card. Gold is not available here: 80-UI-SPEC.md
reserves `#ffc107`/`#FFD700` for an explicit closed list (the Add Category / Rename / + Contact
buttons, the heading rule line, the `fa-tag` and page-header icons) and states it is never used
elsewhere on these surfaces. Cream is therefore both the in-convention and the spec-compliant
choice, and it introduces no new palette entry.

**Underline is load-bearing, not decoration.** Because the link now shares a hue family with the
surrounding helper text, Bootstrap's default underline is what keeps it distinguishable as a
link without relying on colour alone. Neither new rule may set `text-decoration: none`.
</design_decisions>
