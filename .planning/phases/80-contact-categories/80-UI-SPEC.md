# Phase 80 — UI Design Contract

> Visual and interaction contract for Contact Categories. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Stack note:** ASP.NET Core 10 MVC + Razor + Bootstrap 5 + FontAwesome, no SPA, no shadcn, no component registry. This is **not** a greenfield surface — it extends the existing Contacts feature (`contacts.css`, `contacts.mobile.css`, `contact-form.mobile.css`, `contact-detail.mobile.css`) and the existing `ShopManagement`/`Group` management-page idiom. Every markup block below is written to slot into the real files read during research (`Views/Contacts/*`, `Views/ShopManagement/*`, `Areas/Platform/Views/Group/Index.cshtml`, `wwwroot/css/modern-card.css`), not invented in isolation. Mobile markup is real per-file markup (`*.Mobile.cshtml`), never a media query — verification requires a real mobile User-Agent per D-08/Pitfall 4, never devtools emulation.

Nine surfaces carry a visual contract this phase: (1) the category heading itself, (2) the Ungrouped heading's visual distinction, (3) the Manage Categories page, (4) the delete confirmation, (5) the DM-tier entry point, (6) the disabled category select + helper text, (7) the Details-view category line, (8) empty/edge states, (9) accessibility (heading semantics, reorder button labels, post-POST focus).

## Spacing Scale

Declared values (must be multiples of 4), matching the rem-based convention already used in `contacts.css`/`contacts.mobile.css`:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px (0.25rem) | Icon-to-label gap (`me-1`/`me-2` on FontAwesome icons, per CLAUDE.md) |
| sm | 8px (0.5rem) | Gap between reorder up/down buttons in the `btn-group`; padding-bottom under a category heading's rule line |
| md | 16px (1rem) | Margin-bottom under a category heading; mobile `.contact-section-card` internal padding (existing, unchanged) |
| lg | 24px (1.5rem) | `.contact-grid` gap (existing, unchanged) |
| xl | 32px (2rem) | Vertical gap between one category block and the next on desktop — deliberately larger than the 24px intra-grid gap, so a category boundary reads as a stronger break than a card-to-card gap within one category |
| 2xl | 48px | Not used this phase |
| 3xl | 64px | Not used this phase |

**Exceptions:**
- The Manage Categories page's up/down reorder buttons must clear a **44×44px** tap target on mobile, even though their visible icon-only glyph is smaller — pad the button, don't just rely on `btn-sm`'s default box. This is the same exception every prior mobile-render phase (74, 77, 82) has carried for icon-only controls.
- `.category-heading`'s `padding-bottom` (8px) + `margin-bottom` (16px) combination is deliberately two different tokens, not one — the padding sits between the text baseline and the rule line beneath it; the margin is the gap between that rule line and the first card. Collapsing them into one value would either crowd the text against its own rule or push the rule too far from the cards it's introducing.

Two weights only on every new element: **400** for helper/body copy, **600** for anything scanned as a label or heading (category name, form label, page title). No third weight is introduced by this phase.

## Component Specifications

### 1. The category heading — desktop and mobile

**Desktop (`contacts.css` addition).** A category heading sits directly above its `.contact-grid` slice, inside the existing outer `.modern-card`/`.modern-card-body` — it is **not** its own card. `.modern-card h1–h6` already forces cream text (`#F4E4BC`) with a dark drop-shadow via `!important`; `.category-heading` only adds size, rhythm, and the accent rule beneath it, and does not fight that forced color.

```html
<div class="card modern-card">
    <div class="card-body modern-card-body">
        @if (Model.HasCategories)
        {
            @foreach (var group in Model.CategoryGroups)
            {
                <div class="category-block">
                    <h2 class="category-heading@(group.IsUngrouped ? " category-heading-ungrouped" : "")">
                        <i class="fas fa-tag me-2"></i>@group.Title
                    </h2>
                    <div class="contact-grid">
                        @foreach (var contact in group.Contacts)
                        {
                            <!-- existing .contact-card markup, unchanged -->
                        }
                    </div>
                </div>
            }
        }
        else
        {
            <div class="contact-grid">
                <!-- existing flat .contact-card loop, unchanged: a board with no categories renders exactly today's list -->
            </div>
        }
    </div>
</div>
```

```css
/* contacts.css addition */

    margin-top: 2rem; /* 32px — a stronger break than the 24px intra-grid card gap */
}

.contacts-page .category-heading {

    letter-spacing: 0.02em;
```

**Mobile (`contacts.mobile.css` addition).** `.contact-section-card` / `.contact-section-heading` already exist and are already the container/heading pair for exactly this purpose — today they wrap one static "Contacts" section; this phase is what gives the pattern more than one instance per page. **Upgrade the heading from a plain `<div>` to a real `<h2>`** (see Component Spec 9 — today it carries no heading semantics at all).

No new mobile CSS is needed for the base heading — `.contact-section-heading` already declares the uppercase/letter-spacing/cream-with-shadow treatment. Add only:

```css
/* contacts.mobile.css addition */

    overflow-wrap: break-word; /* defends the 60-char cap, same reasoning as desktop */
```

### 2. Ungrouped — same shape, deliberately muted, no accent

**Decision: same heading element, same icon, same size — muted via opacity and italics, not a different treatment.** A second icon or a differently-sized heading would read as "a different kind of thing" when it is structurally identical (still a heading, still a `.contact-grid`/row list beneath it); muting communicates "this bucket is synthetic" without inventing a second visual vocabulary for one heading.

```css
/* contacts.css addition */
.contacts-page .category-heading-ungrouped {
    font-style: italic;
    opacity: 0.75; /* mutes text, icon, and the rule line together — no !important fight with modern-card.css's forced color */
}

.contacts-page .category-heading-ungrouped i {
    color: rgba(244, 228, 188, 0.6); /* muted, not gold — Ungrouped is not a real, DM-named category */
}
```

```css
/* contacts.mobile.css addition */
.contact-section-heading-ungrouped {
    font-style: italic;
    opacity: 0.75;
}
```

Using `opacity` on the whole heading (rather than fighting `.modern-card h1–h6`'s `!important` color) is the deliberate mechanism — it mutes the icon, text, and desktop's accent rule line uniformly with one property and no specificity war.

### 3. Manage Categories page — desktop and mobile

**Route/controller:** `ContactCategoryManagementController`, plain (unareaed) controller mirroring `ShopManagementController`'s route shape — `/ContactCategoryManagement/Index`, `/Add`, `/Edit/{id}`, `/Delete/{id}`, `/MoveUp/{id}`, `/MoveDown/{id}`.

**Rename lives in a separate `Edit.cshtml` (GET+POST), not inline-editing the list row.** This codebase has zero inline-edit precedent anywhere (`GroupController.Edit`, `ShopManagementController.Edit` are both separate views); building the first one here would be new interaction surface for a rare action (renaming happens once per category, ever). A separate view also keeps the list row itself simple — no per-row `<form>`/JS-toggle complexity competing with the reorder buttons and delete form already living in that row.

**The add form is inline at the top of `Index.cshtml`/`Index.Mobile.cshtml`, not a separate `Create.cshtml`.** This is a deliberate, reasoned divergence from the literal `ShopManagement`-mirrored file list in 80-RESEARCH.md's project structure sketch. A shop item's Create page justifies its own screen (type, rarity, price, quantity, dates, an image). A category has exactly one field. CONTEXT.md's own D-06 wording — "Lists the board's categories with rename, delete, reorder, **and an add form**" — reads as one page, and a DM adding several categories in one sitting (the realistic first-run case — "Corridor", "Guild Members", "Last Bastion" in one sitting) should not round-trip a full page navigation per category. **Behavioral consequence for the controller the executor must satisfy:** on a failed `Add` POST (duplicate name), the controller must re-render `Index` with the category list repopulated and the failed `NewCategory` sub-model's `ModelState` errors intact — never redirect to a blank separate page.

### 4. The delete confirmation — plain `confirm()`, built safely from `data-*` attributes

**Decision: the existing plain-JS `confirm()` pattern** (`ShopManagement/Index.cshtml`'s `onsubmit="return confirm('...')"`, and Contacts' own `Details.cshtml` "Delete Contact" button), **not a Bootstrap modal.** `ShopManagement`'s one modal (`denyModal`) exists because denying requires a text-input reason — a real form. A delete confirmation with no additional input is exactly what the app's existing plain-`confirm()` idiom already covers everywhere else, and introducing a modal here would be a second pattern for the same job with no new need.

**Do not embed the category name directly inside an inline `onsubmit="confirm('...')"` string.** D-03's confirmation text must be dynamic (the count varies per row), and this codebase's category names are free text — a name like `Thieves' Guild` contains an apostrophe. Razor's default `HtmlEncoder` encodes `'` to `&#39;` in an HTML attribute; the browser decodes that back to a literal `'` **before** treating the attribute value as JS source, which would silently break (or worse, malform) a hand-quoted inline string. The fix costs nothing: pass the name and count as plain `data-*` attributes (already used in the markup above — `data-category-name`, `data-contact-count`) and read them via `element.dataset` in a small shared script, which returns the already-decoded string as real JS data, not source text:

```javascript
document.querySelectorAll('.category-delete-form').forEach(function (form) {
    form.addEventListener('submit', function (e) {
        var name = form.dataset.categoryName;
        var count = parseInt(form.dataset.contactCount, 10);
        var message = count > 0
            ? 'Delete "' + name + '"? This will move ' + count + ' contact' + (count === 1 ? '' : 's') + ' to Ungrouped.'
            : 'Delete "' + name + '"? It has no contacts to move.';
        if (!confirm(message)) {
            e.preventDefault();
        }
    });
});
```

Place this in `@section Scripts` on both `Manage.cshtml` and `Manage.Mobile.cshtml` (identical script, no platform branching needed — it is plain DOM/JS with no layout dependency).

### 9. Accessibility

**Heading semantics.**
- Desktop Contacts index: `<h1>Contacts</h1>` (existing, outside the card) → new `<h2 class="category-heading">` per category block, inside the card. This does not worsen the existing hierarchy — today's page already jumps from `<h1>` straight to `.contact-name`'s `<h5>` inside each card with nothing between; adding `<h2>` narrows that gap rather than widening it.
- Mobile Contacts index: today's `.contact-section-heading` is a plain `<div>` with **no heading semantics at all**. This phase upgrades it to a real `<h2>` (Component Spec 1) — a genuine accessibility improvement, not merely a style carryover. Do this in both the zero-category fallback and the per-category loop, so the page always exposes at least one real heading to assistive technology.
- Manage Categories page: `modern-card-header`'s `<h2>Manage Categories</h2>` (CLAUDE.md-mandated shape) is the page's only top-level heading — no separate `<h1>`, matching how `ShopManagement`/`Group` management pages already work.

**Reorder button accessible names.** Both up and down buttons are icon-only (`fa-arrow-up`/`fa-arrow-down`, no visible text) — every instance carries `aria-label="Move {CategoryName} up"` / `"Move {CategoryName} down"` (shown in Component Spec 3's markup), never a bare icon with no accessible name.

**Focus handling after a reorder POST.** `MoveUp`/`MoveDown` are plain form POSTs with a full-page redirect back to `Index` — with no extra handling, the browser resets scroll and focus to the top of the reloaded page, and a DM reordering several categories in a row loses their place after every single click. Fix: the controller redirects with a URL fragment naming the row that moved —

```csharp
return RedirectToAction(nameof(Index), fragment: $"category-{id}-row");
```

— and each row already carries `id="category-@category.Id-row" tabindex="-1"` (shown in Component Spec 3's markup on both platforms). A same-page `#fragment` reload alone only scrolls the browser to that element; it does not move keyboard/screen-reader focus. Add one small script (identical on `Manage.cshtml` and `Manage.Mobile.cshtml`, alongside the delete-confirmation script from Component Spec 4) to close that gap:

```javascript
if (location.hash) {
    var target = document.querySelector(location.hash);
    if (target) {
        target.focus({ preventScroll: false });
    }
}
```

This keeps the DM's place — visually and for assistive technology — through repeated reorder clicks, with no JS framework and no AJAX.
