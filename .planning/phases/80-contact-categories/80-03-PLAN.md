Create `QuestBoard.Repository/ContactCategoryRepository.cs` as
`internal class ContactCategoryRepository(QuestBoardContext dbContext, IMapper mapper) : BaseRepository<ContactCategory, ContactCategoryEntity>(dbContext, mapper), IContactCategoryRepository`.

Every query reads `DbContext.ContactCategories` and relies entirely on the global query filter for
board scoping — never add a manual `GroupId` predicate and never call `IgnoreQueryFilters()`.
That filter is the single point of enforcement for board isolation, and a second mechanism beside
it is how the two prior cross-board leaks in this application happened.

`GetOrderedForActiveGroupAsync` orders by `SortOrder` then by `Id` and maps to the domain model.
The secondary key on `Id` is the tie-break the entity comment documents; every ordered read in
this phase uses the same two keys so the index and the management page can never disagree.

`GetContactCountsAsync` returns one entry per category on the active board. Read the categories
first, then group `DbContext.Contacts` by `CategoryId` where the value is non-null, and project
into a dictionary that carries a zero for any category with no contacts. Both sets are already
board-scoped by their own filters, so the counts cannot include another board's contacts.

`GetNextSortOrderAsync` returns zero when the board has no categories, and otherwise the maximum
`SortOrder` plus one — the dense end-append convention the entity comment documents.

`SwapSortOrderAsync` loads both rows, exchanges their `SortOrder` values, and saves once. It does
nothing if either row is missing, which is what makes a stale button harmless. Adjacency is decided
by the caller, not here.

`DeleteWithDependentsLoadedAsync` loads the category by id, loads every contact whose `CategoryId`
matches into the change tracker, removes the category, and saves. Loading the dependents is
deliberate and is **not** a hand-rolled orphaning loop — do not assign `null` to any contact's
`CategoryId` yourself. The configured delete behaviour does the nulling; loading the dependents
first is what makes the in-memory provider the test suite runs on apply that same configured
behaviour, so the delete path behaves identically under test and against SQL Server. Add no
duplicate-name pre-check anywhere in this class; the unique index and the exception it raises are
the mechanism, and a pre-check would introduce a race the index already closes.

existing `IContactRepository` registration.

Create `QuestBoard.Domain/Services/ContactCategoryService.cs` as
`internal class ContactCategoryService(IContactCategoryRepository repository, IMapper mapper) : BaseService<ContactCategory>(repository, mapper), IContactCategoryService`.

`GetOrderedAsync`, `GetContactCountsAsync` and `DeleteAsync` are thin pass-throughs to the
repository, matching `ContactService`'s style — `DeleteAsync` calls the repository's
delete-with-dependents-loaded method.

`AddToEndAsync` reads the next sort position from the repository, assigns it to the category, and
calls the inherited add. The board id is stamped by the controller from the active board, exactly
as `ContactsController.Create` already stamps it onto a new contact — the service does not read
board state.

`MoveUpAsync` and `MoveDownAsync` are the only genuinely new mechanism in this phase; no existing
entity in this codebase has manual reordering, so there is no analog to copy. Both read the ordered
list once via `GetOrderedForActiveGroupAsync`, locate the target by id, and compute the neighbour
by list position rather than by arithmetic on the sort value — positions are dense today but a tie
or a gap must not produce a wrong neighbour. If the target is absent, or is already at the first
position for a move up or the last position for a move down, return without writing. Otherwise call
the repository swap with the two ids. Both methods return `Task<bool>` reporting whether a swap
happened, so the controller can decide whether to redirect with a focus anchor.

Register the service in `QuestBoard.Domain/Extensions/ServiceExtensions.cs` with
`services.AddScoped<IContactCategoryService, ContactCategoryService>();` beside the existing
`IContactService` registration.

Finally, modify `QuestBoard.Repository/ContactRepository.cs`: add `.Include(c => c.Category)` to
both `GetAllContactsWithDetailsAsync` and `GetContactWithDetailsAsync`, next to the existing
`.Include(c => c.CreatedByUser)` call in each. This is what makes the category name available on
the index and on both Details views with no second query. The include is safe against the category
query filter because the navigation is optional, so EF Core emits a left join and a contact whose
category is filtered out keeps its row with a null navigation rather than vanishing.
