<objective>
Add the Manage Categories page: a DungeonMaster-only controller with the six actions the UI
contract specifies, its four view files (desktop and mobile for both the list page and the rename
page), and the integration suite that pins the authorization gate, the duplicate-name path, the
delete-orphan guarantee and the reorder behaviour.

This is the only surface where a category's sort position can be edited, and the only surface
where a category is created or destroyed. Three of its behaviours are the ones most likely to be
got wrong quietly: a duplicate name that reaches the user as a server error instead of a message,
a delete that removes contacts instead of orphaning them, and a page that a player can reach by
typing the URL.

Purpose: give a DM the whole category lifecycle on one page, on both platforms.
Output: a controller, four views, and a passing management suite.
</objective>

category to a `ContactCategoryViewModel`, then sets `ContactCount` from the map (defaulting to zero
for a category absent from it), `IsFirst` on the first element and `IsLast` on the last, imperatively

`ContactCategoryManagementViewModel` with a fresh `NewCategory`, and return `View("Manage", viewModel)`.

the active board with the `is not { } activeGroupId` pattern and redirect to the board picker when
there is none, exactly as `ContactsController.Create` does — a user with no active board has no board
to stamp. On invalid model state, re-render `View("Manage", ...)` with the list repopulated and the
submitted `NewCategory` intact so the user sees their own input and the error together. Otherwise map
`NewCategory` to a `ContactCategory`, stamp `GroupId` from `activeGroupId` — never from anything in
the request — and call the service's add-to-end method so the new category lands last. Wrap that call
in the `try` / `catch (DbUpdateException ex) when (...)` filter copied from `GroupController`, matching
on "unique" or "duplicate" case-insensitively in the inner exception message, and on catch add a model
error on the new category's name field reading exactly "A category with that name already exists.
Please choose a different name." then re-render the populated list page. Add no pre-check that queries
for an existing name: the unique index is the mechanism, and a pre-check adds a race the index already
closes. On success set the success message in `TempData` the way `GroupController` does and redirect to
`Index`.

`Edit` (HttpGet, id) loads the category through the service, returns `NotFound()` when it is missing —
which is also what a category belonging to another board produces, because the board filter makes it
unreachable — maps it to a `ContactCategoryViewModel` and returns the default view so the rename page
pairs with `Edit.cshtml` and `Edit.Mobile.cshtml`.

`Edit` (HttpPost, id, `[ValidateAntiForgeryToken]`) rejects a mismatch between the route id and the
posted id with `BadRequest()`, reloads the existing category, returns `NotFound()` when absent,
re-renders the form on invalid model state, and otherwise writes only the name — never the sort
position and never the board id — before saving inside the same duplicate-name catch, with the same
message, re-rendering the rename form on catch.

`Delete` (HttpPost, id, `[ValidateAntiForgeryToken]`) calls the service delete and redirects to `Index`.
It does not load or modify any contact: the configured delete behaviour is what orphans them, and doing
it here as well would be a second mechanism for the same guarantee.

`MoveUp` and `MoveDown` (HttpPost, id, `[ValidateAntiForgeryToken]`) call the matching service method
and redirect to `Index` carrying the URL fragment `category-{id}-row`, using the `RedirectToAction`
overload that accepts a fragment. The fragment is what returns a DM to the row they just moved instead
of the top of a reloaded page. Redirect the same way whether or not a swap actually happened, so a
no-op at a boundary is indistinguishable from a successful move to the browser.

No action on this controller may call `IgnoreQueryFilters()`, and no action may read a board id from
route, query or form. Per CLAUDE.md, no comment or string literal in this file may contain a phase
number, plan number, requirement id or decision id — the user-facing strings above are product copy and
are fine.
