1. "How a release reaches the server": the timer polls, verifies, installs and health-checks; GitHub has no runner or credential on the box.
2. "Layout on the App CT": a table of paths.
3. "The poll": cadence, unauthenticated, about 12 requests an hour, the shared rate limit, journal-only idle and unreachable runs.
4. "What an install does": both orders from the interfaces block with and without migrations, and the verification chain (checksum, attestation pinned to repo, workflow, tag and hosted runners, attested commit on main). State plainly that verification needs the Sigstore service reachable, so an outage refuses rather than skips.
5. "Outcomes": a table with columns situation, what the installer does, mail result, remembered by the poll. One row per outcome, including GitHub unreachable and nothing newer.
6. "Notification mail": one mail per install outcome; the body carries version, result and timestamps only, plus the backup name when halted; the relay is the one the app uses; the shared Resend daily budget is why polls never mail.
7. "Commands": `poll`, `install` (newer, redeploy, older, override of a remembered tag), `rollback`, `verify`, `setup` (also how to apply an installer update when the outcome mail says one is available: run `/opt/questboard/releases/<version>/deploy/bin/questboard-deploy setup`).
8. "Why rollback sometimes stops": migrations only go forward; the halted outcome leaves the new release running and systemd retrying; the adopted release cannot be rolled back to automatically by hand.
9. "Restoring a pre-migration backup": a manual runbook with no automated command:
   - stop the app;
   - on the SQL CT, `RESTORE DATABASE ... FROM DISK = N'<default backup dir>/<backup name>' WITH REPLACE`;
   - a restore discards every write made after the backup began;
   - then `questboard-deploy rollback <previous version>`, or for the adopted release repoint `current` with an atomic `ln -s` plus `mv -T` and start the app;
   - prefer fixing forward once the service is back.
10. "Backups on the SQL CT": installing the prune script, a weekly cron line example, and checking free space before a migration-carrying release.
11. "Running the migrator by hand": the systemd-run command for `status` and `backup`, why the env file is never sourced, and the exit codes.
12. "Configuration": a table of the nine keys with defaults.
13. "Moving an existing push-based install over":
    - the bootstrap order: merge, tag, approve, verify on a workstation with `build/verify-published-release.sh`, fetch the zip on the CT and check the printed sha256, unzip to a temp dir, run `setup`, confirm the detected version with `--confirm-adopt-version`, edit `deploy.conf`, run `setup` again, then trigger the first install through `systemctl start questboard-deploy-poll.service` so the sandboxed path is exercised;
    - a subsection "Retiring the push-based deploy" that reproduces the four retirement steps of D-23 from 89-CONTEXT.md verbatim as commands, then the two-sided verification (zero runners via `build/check-github-settings.sh` or `gh api repos/<owner>/<repo>/actions/runners`, and no `actions.runner` unit on the CT);
    - a warning that only the runner's own directory is deleted and never the questboard home, because the app's Data Protection keys live there and deleting them signs everyone out and voids outstanding reset links.
    Every mention of the old runner, its directory, its service script, the restart permission file or the old server-side deploy script lives inside this section and nowhere earlier.
14. "Troubleshooting": the installer refuses a release that verifies on a workstation; a bus-connection error in the journal; a health timeout on a slow start (`QUESTBOARD_HEALTH_TIMEOUT_SECONDS`); a remembered tag; useful `journalctl -u questboard-deploy-poll.service` and `systemctl list-timers` commands.

Never describe verification as working without network access, and never say a poll sends mail. No planning references (decision ids, phase numbers, planning file names).
