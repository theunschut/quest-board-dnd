Write down what a share link actually is and what its limits are, then put the phase in front of the only judges that can settle its headline criteria: the deployed host and a real chat client.

  <action>
    Create `docs/link-previews.md` covering, in plain language and with no planning identifiers anywhere:

    What the feature is. A board member copies a share link from a quest page; pasted into Discord, Slack or Messages it unfurls as a card carrying the quest title, a short plain-text summary of the description, and a branded image. An ordinary quest URL that nobody copied through the control does not do this and reveals nothing.

    What the link grants. Card metadata only. The link does not log anyone in, does not open the quest page, and cannot be used to sign up or post anything. A recipient who follows it and is not logged in reaches the login page.

    What it cannot do — the section that matters most. The link has no expiry and cannot be revoked. There is no per-link kill switch and no board-wide one. Deleting the quest stops the card from rendering for any future fetch, because the card is built from a live read each time. But Discord and Slack cache an unfurl on their own servers, so a card already sitting in a channel stays there regardless of anything done on this side. State plainly that this is a real limit of how link previews work everywhere, not a gap in this implementation, and that it is the reason the copy control carries a standing warning rather than a dismissible one.

    What is deliberately kept off the card. Only the title, a short summary and a shared branded image travel. No roster, no proposed dates, no dungeon master name, no rewards, no signup counts.

    Platform differences worth knowing before someone files a bug. Messages on Apple platforms shows the title and image but does not display the description at all, and its preferred image shape differs from the one used here, so the image may appear centre-cropped there. Both are platform behaviours, not defects.

    Operational notes. Name the two environment values the feature depends on and point at the deployment document rather than duplicating it. Mention that the signing keys are stored in the database so links keep working across deploys, and that destroying that key material would invalidate every link ever issued.

    Then add a short pointer in `README.md` — one line under a heading consistent with its existing structure — naming the new document and what it covers.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| deployed host → third-party crawler | External services fetch the preview route and cache what they find on their own infrastructure, permanently and outside this project's control |
| reverse proxy → deployed application | The only place where forwarded scheme and host trust can actually be observed |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-78-07 | Repudiation | third-party unfurl caches | medium | accept | External caches cannot be invalidated from this side. The limit is stated in the interface where a user sees it before pasting, and explained in the new document for anyone who needs to reason about it. Accepting it honestly is better than building a revocation control that would not actually retract anything |
| T-78-05 | Spoofing | forwarded scheme and host on the deployed host | high | mitigate | Check 4 observes the real behaviour through the real proxy. A localhost or wrong-scheme value in the response is the tell that the trusted-proxy configuration is not in effect, and is a blocking failure rather than a cosmetic one |
| T-78-03 | Elevation of Privilege | signed link followed by a logged-out visitor | high | mitigate | Check 6 confirms end to end that the token yields a card and nothing more: the forward lands on the login page, never on the quest |
| T-78-04 | Tampering | tampered token against the deployed host | high | mitigate | Check 5 confirms the reject-don't-degrade rule holds in production, not only under test |
| T-78-24 | Information Disclosure | an uncopied quest URL | high | mitigate | Check 6 confirms an ordinary quest URL still unfurls to nothing, so sharing remains a deliberate act |
</threat_model>
