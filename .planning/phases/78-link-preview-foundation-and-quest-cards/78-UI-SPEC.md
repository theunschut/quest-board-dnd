# Phase 78 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

This is a backend-heavy phase with exactly **three** user-facing surfaces. Nothing else in this
phase carries a design contract: `QuestController.Details` gains `[Authorize]` (no visual change),
and the forwarded-headers/Data Protection/signing work is server-only.

1. The branded 1200×630 card image (rendered by Discord/Slack/iMessage, never by our own UI)
2. The standalone minimal preview interstitial (`/s/quest/{token}`)
3. The "Copy shareable link" control + permanence note (desktop + mobile Quest Details, one reusable pattern Phase 79 extends to 4 more call sites)

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — server-rendered ASP.NET Core MVC + Razor, not a JS component framework. shadcn gate not applicable (no `components.json`, no React/Next/Vite in this stack). |

Existing design system detected and reused as-is: `modern-card` / `modern-card-header` / `modern-card-body` (semi-transparent frosted glass over a fixed parchment/notice-board background image), a dark navbar, and a warm leather/gold/parchment palette (`#8B4513` brown-leather, `#FFD700`/`#ffc107` gold, `#F4E4BC` parchment text). Nothing in this phase introduces a new design system — it extends the existing one on Quest Details and produces one net-new static asset.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA (copy control, both platforms) | `Copy shareable link` — icon `fa-share-alt`, button classes `btn btn-secondary btn-sm` |
| Copy-confirmation (inline button-state swap, ~2s, then reverts) | `Copied!` — icon swaps to `fa-check`, button briefly becomes `btn-success` for the confirmation window only, then reverts to `btn-secondary` / `fa-share-alt` / `Copy shareable link` |
| Permanence note (always visible, muted, directly under the button — not hidden inside the confirmation) | `Heads up: this link works forever and can't be revoked. If it's already been shared, deleting the quest is the only way to stop it appearing.` |
| Empty state | Not applicable — this phase adds no list/collection UI. (The card's own "empty description" fallback is handled below as the description-copy contract, not as a page empty state.) |
| Card description fallback (quest has no/blank Markdown description, D-14) | `No description yet — open the link to see the full quest.` (kept under the ~200-char budget; never omit `og:description` entirely, per D-14) |
| Truncation contract (LINKPREV-06/D-14) | Max 200 characters **including** the ellipsis. Truncate on the rendered plain text (never the Markdown source) at the last whole-word boundary at or before 199 characters, then append a single Unicode ellipsis character `…` (not three periods). HTML-escape after truncation. |
| Preview page fallback link text (deliverable 2) | `Continue to Quest Board →` |
| Preview page site identity line (small, muted, above the H1) | `D&D Quest Board` (plain text, no logo image — see deliverable 2) |
| Destructive confirmation | Not applicable — no destructive action in this phase's UI scope |

**Why the permanence note is always visible rather than only in the confirmation:** a toast or transient message can be missed entirely if the user copies and immediately switches away (e.g., to paste into Discord). A muted one-liner that's always present under the button guarantees the warning is seen before the link is ever pasted anywhere, not after.

## Deliverable 1: Card Image Asset Specification

**File:** `QuestBoard.Service/wwwroot/images/link-preview-card.png` — lowercase, hyphenated, no spaces (every existing image filename in `wwwroot/images/` contains spaces; this one deliberately does not, because it is embedded in an absolute `og:image` URL and must never need percent-encoding).

**Canvas:** 1200×630px (1.91:1), matching Discord's and Slack's large-card convention. `twitter:card` is `summary_large_image` on the strength of this ratio (locked, D-13).

**One asset serves all three target platforms (Discord, Slack, iMessage).** Do not produce a second square crop. Apple's TN3156 guidance favors 1200×1200+ and will center-crop this 1200×630 asset — that is an accepted, documented platform limitation (research Pitfall 4), not a defect to fix in this phase. Revisit only if a real iMessage UAT paste shows unacceptable cropping; that becomes a follow-up, not a Phase 78 blocker.

**Composition:**

1. **Background layer:** a warm, aged parchment/leather texture drawn from the existing board art — `wwwroot/images/Ruined Posters/Ruined Poster 5.png` or `Ruined Poster 6.png` (both under 350KB source, already textured/aged, matching the brand's leather-and-parchment palette). Since all source posters are portrait (1000×1400 or similar), crop/scale a horizontal band from the texture rather than squashing the whole portrait — take a landscape-oriented slice from the poster's central texture area, scaled to fill 1200×630, then apply a subtle dark vignette (radial gradient, darker at the edges, ~15–25% opacity black) so text stays legible without a flat overlay panel killing the parchment texture entirely.
2. **Emblem accent:** one wax seal — `wwwroot/images/Wax Seals/Crown Seal.png` (400×400, reads as "official"/board-branding at a glance) — placed small and off-center (left third or bottom-left corner, roughly 120–160px rendered size), never centered behind the headline text, so it reads as a decorative signature mark rather than competing with the title.
3. **Headline text:** `D&D Quest Board` (or, if the composition needs less text density, just `Quest Board`) set in **Cinzel Bold (700)**, gold/parchment ink (`#FFD700` or `#F4E4BC`, whichever contrasts better against the chosen texture crop — verify against the actual background, don't assume), centered in the upper-to-middle third of the canvas, with a soft drop-shadow (`2–3px`, `rgba(0,0,0,0.7–0.9)`) matching the existing navbar-brand treatment (`site.css` navbar-brand text-shadow) for legibility over a textured background.
4. **Optional subhead / tagline:** a smaller line beneath the headline in Cinzel Semibold (600), e.g. `Adventures Await` or similar — optional, only if it doesn't crowd the composition. Not required.
5. **A single accent d20/dice icon** (FontAwesome `fa-dice-d20` glyph, rendered as a static shape in the design tool — not a live web font at this stage since this is a static exported image) may sit beside the headline, echoing the navbar brand mark (`<i class="fas fa-dice-d20">` next to "D&D Quest Board" in both layouts) for immediate visual continuity with the rest of the app.

**Safe area:** keep all text and the seal emblem within a centered 1120×580 safe zone (40px margin on every side) — Discord, Slack, and iMessage each apply slightly different crop/letterbox treatment at their card edges, and a 40px margin absorbs that variance without clipping text.

**Export:**
- Format: PNG (text-on-image benefits from lossless edges; the existing source art is also PNG).
- Target size: **under 200KB.** If a straight PNG export exceeds that, first try PNG-8/palette quantization (the composition is mostly flat gradient + texture + a few solid text/seal colors, which palette-compresses well) via a tool such as `pngquant` or TinyPNG. If it still exceeds budget after quantization, fall back to JPEG at quality ~82–88 — acceptable here because the *dominant* card content (title/description) comes from `og:title`/`og:description` text, not from this image; a very slight JPEG softness on the background texture is a non-issue.
- No redirect, no authentication (LINKPREV-08) — served as a plain static file under `wwwroot/images/`, reachable via `UseStaticFiles()` at the absolute URL `{AppUrl}/images/link-preview-card.png`.

**This is an asset production task, not only a code reference** — budget actual design-tool time (or a scripted composition pass) to produce the PNG before the preview route can be considered complete.

## Deliverable 2: Standalone Preview Page Specification

**Route:** `/s/quest/{token}` (illustrative per CONTEXT.md D-08 — exact path is the planner's discretion). **View:** a new `Views/LinkPreview/QuestCard.cshtml` with `Layout = null;` — it renders **no** `_Layout.cshtml` or `_Layout.Mobile.cshtml` at all (D-10). Selecting a layout by `MobileDetectionMiddleware`'s User-Agent match is exactly the coupling this deliverable exists to avoid.

**Every caller — crawler or human, any device — gets the identical HTTP 200 response** (D-11). There is no User-Agent branching anywhere on this route.

### What the document MUST contain

- `<!DOCTYPE html>`, `<meta charset="utf-8">`, `<meta name="viewport" content="width=device-width, initial-scale=1.0">`
- `<meta name="robots" content="noindex">`
- `<title>` — the quest title, plain text
- The full OG/Twitter meta block:
  - `og:type` = `website`
  - `og:site_name` = `D&D Quest Board`
  - `og:title` = quest title (HTML-escaped)
  - `og:description` = the truncated plain-text description (or the fallback line — see Copywriting Contract)
  - `og:image` = absolute URL to `link-preview-card.png` (deliverable 1)
  - `og:image:width` = `1200`, `og:image:height` = `630`
  - `og:url` = absolute URL to the **real** quest page, `{AppUrl}/Quest/Details/{id}` — not the signed preview URL itself (the signed URL is a one-time bearer link; the canonical resource it points at is the quest page)
  - `twitter:card` = `summary_large_image`
  - `twitter:title`, `twitter:description`, `twitter:image` mirroring the `og:` equivalents
- `<meta http-equiv="refresh" content="0;url={absolute quest details URL}">` — **0-second delay.** A human's browser follows it near-instantly; a crawler never follows a meta-refresh at all (that's the entire reason this isn't a 302 — D-11), so 0 costs a real visitor nothing and gives a crawler nothing to trip over.
- A minimal visible body, for the rare case a browser has meta-refresh disabled or slow:
  - A small muted site-identity line: `D&D Quest Board`
  - An `<h1>` with the quest title
  - A paragraph with the same truncated description text used in `og:description` (never more than what the card already exposes)
  - A single visible link/button: `Continue to Quest Board →`, pointing at the same absolute quest-details URL as the meta-refresh target

### What the document MUST NOT contain

- No `_Layout.cshtml` / `_Layout.Mobile.cshtml`, no navbar, no footer, no offcanvas nav
- No Bootstrap CDN link, no FontAwesome CDN link, no `~/js/site.js`, no jQuery
- **No Google Fonts / Cinzel load.** This is a deliberate divergence from the rest of the app's brand typography: the whole point of this route is a cheap, dependency-free fetch for a crawler, and an external font request adds latency and a third-party network call for a document a human essentially never reads. Use a plain system serif stack instead (see Typography table) — it still reads as "not the default browser page" without costing a network round-trip.
- No session-dependent content of any kind — the route is anonymous-allowed and must render identically regardless of whether the requester happens to also hold an authenticated session
- No quest data beyond what the card itself already exposes (title + the same truncated description + the same image) — no roster, no proposed dates, no DM name, no reward text, no signup counts
- No inline `<script>` — the redirect is pure `<meta http-equiv="refresh">`, no JS fallback needed

### Minimal inline styling (no external stylesheet file)

A single `<style>` block inside `<head>`, scoped to this page only, roughly:

```css
body { font-family: Georgia, 'Times New Roman', serif; max-width: 480px; margin: 60px auto; padding: 0 20px; color: #3a2a1a; background: #f5efe0; text-align: center; }
h1 { font-size: 28px; line-height: 1.25; }
p { font-size: 16px; line-height: 1.5; color: #5a4a3a; }
a.continue-link { display: inline-block; margin-top: 16px; padding: 10px 20px; background: #8B4513; color: #ffffff; text-decoration: none; border-radius: 6px; font-weight: 600; }
```

This echoes the app's brown-leather/parchment palette (`#8B4513`, warm parchment background) with zero external dependencies — brand-consistent without a network call.

## Deliverable 3: "Copy Shareable Link" Control — the reusable pattern

**This is ONE component pattern used identically on desktop and mobile Quest Details in this phase, and it is the exact pattern Phase 79 extends to Character and Contact Details (4 more call sites, 6 total).** Do not build a bespoke desktop treatment and a separate bespoke mobile treatment — one small partial, rendered in each host page's natural "summary" location.

### Structure

A single small partial (e.g. `Views/Shared/_ShareLinkButton.cshtml`) that receives the pre-minted absolute signed URL (minted server-side at page render per D-15 — no round trip, no antiforgery wiring) and renders:

1. The button: `<button type="button" class="btn btn-secondary btn-sm share-link-btn" data-share-url="@signedUrl">` containing `<i class="fas fa-share-alt me-2"></i>Copy shareable link`
2. Directly beneath it, always visible: `<small class="text-muted d-block mt-2">Heads up: this link works forever and can't be revoked. If it's already been shared, deleting the quest is the only way to stop it appearing.</small>`

### Interaction

- Click → `navigator.clipboard.writeText(url)` (client-side only, no server round trip — confirmed by research as the correct mechanism; `_Toasts.cshtml` is `TempData`-driven and has no JS-callable entry point, so it is the wrong tool for a clipboard action with no page reload)
- On success: button text/icon swap to `Copied!` / `fa-check`, button briefly becomes `btn-success`, reverts to the default state (`Copy shareable link` / `fa-share-alt` / `btn-secondary`) after ~2000ms
- No page reload, no `TempData`, no toast plumbing — this is intentionally the lightest-weight confirmation mechanism available, and it is the one pattern that behaves identically whether it is rendered inside `_Layout.cshtml`'s desktop DOM or `_Layout.Mobile.cshtml`'s mobile DOM

### Placement — Quest Details (this phase)

- **Desktop (`Views/Quest/Details.cshtml`):** inside the existing "Quest Summary" sidebar card (`col-lg-2 col-md-3`, the `modern-card` below/beside "DM Controls"), as its own row below the existing summary content — full-width button (`w-100` may be added to `btn-sm` for this slot) followed immediately by the permanence note. This keeps it visually subordinate to "Manage Quest" (which stays the only brown/primary-accent button on the page) while still being easy to find.
- **Mobile (`Views/Quest/Details.Mobile.cshtml`):** inside the existing `quest-header-card-mobile` block — the mobile page's equivalent "summary" surface (title, DM, status, description all already live there) — placed after the description/rewards content, below a `quest-card-divider`, as a full-width button with the permanence note beneath it. Verify with a **real mobile User-Agent**, not devtools emulation (established pattern, Phase 74 D-16 / Phase 72).

**Phase 79 note (for continuity, not a Phase 78 deliverable):** Character and Contact Details pages have a different card layout (a portrait card, not a "Quest Summary" sidebar card), so Phase 79 will render this same partial inside whichever card on those pages functions as that entity's "identity/summary" surface — the partial itself does not change, only its host slot does. Contacts additionally gate the control on `IsRevealed` (Phase 79's own concern, not this phase's).
