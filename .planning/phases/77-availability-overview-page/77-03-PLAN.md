<objective>
Build the page itself: the view models, the AutoMapper entries, the two Razor views plus the two
shared partials that carry the cell and count vocabulary, and the controller action that binds
them together with a clamped page size.

Purpose: this is where the aggregate from plan 77-01 and the stylesheet vocabulary from plan
77-02 become the thing a DM actually looks at. The two decisions that are easiest to lose here
are the five distinct cell renderings and the three-figure count block — both exist precisely to
stop "counted as available" being read as "somebody said yes", and neither may be simplified.

Output: three view model classes, two AutoMapper entries, four Razor files, one controller
action, and two test classes.
</objective>

  <action>
**`_AvailabilityCell.cshtml`** — `@model QuestBoard.Domain.Enums.AvailabilityCellState`. This is
the single source of the chip vocabulary; both surfaces render it, so the two can never diverge.
A `switch` over the model produces exactly five renderings:

- `ConfirmedYes` — `<span class="badge bg-success"><i class="fas fa-check me-1"></i>Yes</span>`
- `ConfirmedMaybe` — `<span class="badge bg-warning text-dark"><i class="fas fa-question me-1"></i>Maybe</span>`
- `ConfirmedNo` — `<span class="badge bg-danger"><i class="fas fa-times me-1"></i>No</span>`
- `UnconfirmedYes` — `<span class="badge avail-cell-yes-muted" title="Yes — counted, but not yet confirmed by this member" aria-label="Yes, unconfirmed default">` containing `<i class="fas fa-clock me-1"></i>` and `<em>Yes</em>`. The icon is the clock, never the tick: the fill difference alone is a difference of degree and is exactly what a colour-blind or low-contrast reader loses, so the distinct icon, the italic label and the dashed border from the stylesheet are three independent signals that survive greyscale.
- `Empty` — `<span class="text-muted avail-cell-empty" aria-label="No signup for this event">&mdash;</span>`. Deliberately not a badge: the shape alone separates "no signup row exists" from every vote-bearing state before colour is read, and it must stay visibly different from the unconfirmed default, which stores a Yes and is counted.

**`_AvailabilityCounts.cshtml`** — `@model EventOverviewRowViewModel`. Emits the two-line block:
a `<div class="avail-count-summary">` holding
`<span class="avail-count-headline"><i class="fas fa-users me-1"></i><strong>@Model.YesCount</strong> Yes</span>`
and `<span class="avail-count-detail text-muted">(@Model.ConfirmedYesCount confirmed) &middot; @Model.MaybeCount Maybe</span>`.
All three figures always render. The headline is the total that includes unconfirmed defaults and
is the figure that can mislead, so the confirmed subset sits next to it and never disappears; Maybe
is shown separately and is never folded into Yes. If the layout ever cannot fit them, the format
gives way — a third micro-line — never one of the three numbers. No per-board denominator is
added: a one-shot board has no fixed membership size for one to mean anything against.

**`Index.cshtml`** — `@model EventOverviewViewModel`, `ViewData["Title"] = "Availability Overview";`.
A `row` holding a `col-lg-9 col-md-8` main column and a `col-lg-3 col-md-4` legend column,
mirroring the calendar's grid-plus-legend split.

`<h2 class="mb-0"><i class="fas fa-calendar-check text-purple me-2"></i>@ViewData["Title"]</h2>`,

When `Model.Rows` is empty, render the empty state in place of the table: a centred block with

`<p class="mb-0">This board has no upcoming events yet. Once a DM schedules one, it will appear here.</p>`.
Same markup and copy on both surfaces, with no board-type or role branching.

Otherwise render `<div class="table-responsive">` wrapping
`<table class="table table-hover mb-0 avail-grid">`. The `<thead>` row is:
`<th class="avail-sticky-col avail-col-event">Event</th>`,
`<th class="avail-sticky-col avail-col-attendance">Attendance</th>`, then one `<th>` per entry of
`Model.Members` in order, showing the member's name and appending ` (you)` when
`member.UserId == Model.CurrentUserId`, with `class="avail-col-self"` on that one column's header.
Each `<tbody>` row is one entry of `Model.Rows` — events are rows and members are columns, and this

the same navigate-on-click idiom the mobile calendar agenda already uses. First cell:
`<td class="avail-sticky-col avail-col-event">` with `<strong>@row.Title</strong>`, a `<br />`, and a
`<small class="text-muted">` carrying the date and, when `row.StartTime` is not null, the time —
an all-day event has no time and must render without one. Second cell:
`<td class="avail-sticky-col avail-col-attendance">` rendering the `_AvailabilityCounts` partial.
Then one `<td>` per member, in the same index order as `Model.Members`, rendering the
`_AvailabilityCell` partial with `row.Cells[i]`, and carrying `class="avail-col-self"` on the

Legend column: `<div class="card modern-card legend-card">` with a

`[HttpGet] public async Task<IActionResult> Index(int? take = null, CancellationToken token = default)`

Body:

   ceiling is the point: an unclamped client-supplied page size would let one request ask the
   database for an unbounded window.
