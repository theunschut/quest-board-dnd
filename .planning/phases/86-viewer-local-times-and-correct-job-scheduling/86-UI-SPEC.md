# Phase 86 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Read this first.** This phase adds no new screen, no new page, no new component. It changes how one existing, already-styled value — a timestamp — is rendered at ~22 call sites across desktop Razor views and their `.Mobile.cshtml` twins (19 in 86-RESEARCH.md's original inventory, plus 3 corrections adopted below). The contract below is therefore a **rendering contract for one recurring inline element** (`Html.LocalTime`'s `<time>` output), not a page layout, and most of the standard template's page-level sections (spacing scale, color palette, typography scale) are marked Not Applicable with an explicit "inherit, don't introduce" rule in place of new tokens. The load-bearing content is the **Time Rendering Contract** section.

## Color

**Not applicable — introduces no new color token.** The `<time>` element must render in the exact inherited foreground color of its container (`#F4E4BC` inside `.modern-card .table td`, the muted gray of `.text-muted`/`.calendar-subscription-meta` elsewhere, etc.).

## Time Rendering Contract

This is the phase's actual design contract. It resolves the six open questions the phase scope flagged, in order, and is binding on the planner and executor exactly as if it were a page layout.

### 1. The `<time>` element markup

`Html.LocalTime(DateTime utcInstant, string style)` (exact method/parameter names at the planner's discretion per CONTEXT.md — the markup shape below is not) emits:

```html
<time class="local-time" data-style="date-time" datetime="2026-09-20T09:45:00Z" title="2026-09-20 09:45 UTC">Sep 20, 2026, 11:45 AM</time>
```

| Attribute | Value | Purpose |
|---|---|---|
| `class="local-time"` | fixed marker class | The client-side hydration pass selects `time.local-time[datetime]`, not the bare `time[datetime]` selector. This scopes the JS pass to elements this phase produces and protects against a future, unrelated `<time>` element (e.g. added for `<time>`'s native SEO/microdata semantics on a wall-clock game night) being accidentally swept into viewer-zone conversion. |
| `data-style="{name}"` | one of the four canonical style names in §3 | Tells the hydration script which `Intl.DateTimeFormat` options to apply. Required on every element — there is no default. |
| `datetime="{iso}"` | `utcInstant` formatted `yyyy-MM-ddTHH:mm:ss'Z'` (invariant culture) | The machine-readable instant. Round-trips through JS `new Date(el.getAttribute('datetime'))` with no parsing ambiguity. Built via `TagBuilder`, never raw string interpolation (RESEARCH.md's own security note — repeated here because it is part of the markup contract, not just an implementation nicety). |
| `title="{iso-readable} UTC"` | `utcInstant` formatted `yyyy-MM-dd HH:mm 'UTC'` (invariant culture), e.g. `2026-09-20 09:45 UTC` | D-02's disclosure mechanism. Always full date+time+"UTC" precision regardless of the visible style's granularity — the title's whole purpose is "what is the raw stored instant," so a date-only visible style (`date`, `date-compact`) still gets a full title. |
| Element text content | The board-zone–formatted string per §3, computed server-side at first render | D-05's first-paint value (see §2). Overwritten client-side after `DOMContentLoaded`. |

**What distinguishes a converted real instant from an untouched wall-clock value in the DOM:** presence vs. absence of the `<time class="local-time" datetime="...">` wrapper. A converted instant is always inside this element; an untouched wall-clock value (`FinalizedDate`, `EventEntity.Date`/`StartTime`, `ShopItem.AvailableFrom/Until`, `ProposedDates`) is rendered as it is today — plain text, no wrapper, no `title`, no `data-style`. This distinction is invisible to a sighted reader (by design, per D-01) but is exactly what a test, a code reviewer, or the client-side hydration selector inspects.

### 2. No-flash-of-UTC contract (first paint / no-JS reader)

**D-05 is authoritative and supersedes the roadmap's original framing.** The roadmap's opening scope note speculated the fallback would show "UTC with an explicit zone label." CONTEXT.md's discuss pass resolved this differently and explicitly rejected that option: *"Rejected: rendering UTC with an explicit label (a UTC flash on every page load for every reader, and a no-JS reader is left doing the arithmetic this phase exists to stop)."* The locked design is:

- **Server-rendered fallback = the board-zone formatted string**, using the same canonical style (§3) the client will later apply — never raw UTC, never a bare "wrong-looking" time, and never a UTC-plus-label compromise.
- **No zone label of any kind appears in the visible fallback text.** A board-zone reader (the common case today) sees the correct value on first paint with nothing to swap, because server value and eventual client value are identical. A reader abroad sees board time first, then their own zone a moment after hydration — a genuine value change, but not a "flash of an obviously wrong zone," since board time is the same zone every wall-clock game night on the same page is already in (D-05's own internal-consistency argument).
- **No-JS reader keeps the server-rendered board-zone value permanently.** This is a feature, not a degraded fallback: it is the same zone the game nights on the page are already rendered in, so the page never mixes UTC and wall-clock for a no-JS reader.
- **Swap mechanics:** the hydration script overwrites `el.textContent` in place — same element, same inherited font/color/weight, no re-layout of surrounding structure. For a board-zone reader the swap is a no-op (identical string in, identical string out). For a reader in another zone the string length may change by a few characters (e.g. a 24-hour clock in their locale vs. 12-hour AM/PM); this is an acceptable, expected content change, not a regression — **do not** add a fixed `min-width` or reserve extra whitespace to "prevent reflow," since that would create a visible empty gutter around the (already correct) common-case value for no benefit.

### 3. Format vocabulary (canonical styles)

RESEARCH.md found 19 real-instant render sites in 8 distinct raw `.ToString(...)` format strings, with no shared logic. This phase collapses them into **four canonical named styles**, each with one fixed server format and one fixed `Intl.DateTimeFormat` options object. Every real-instant call site maps to exactly one style — no call site keeps its bespoke format string.

| Style | .NET format (server fallback + `title`'s date portion) | `Intl.DateTimeFormat` options (client) | Example |
|---|---|---|---|
| `date` | `"MMM d, yyyy"` | `{ year: 'numeric', month: 'short', day: 'numeric' }` | `Sep 20, 2026` |
| `date-time` | `"MMM d, yyyy, h:mm tt"` | `{ year: 'numeric', month: 'short', day: 'numeric', hour: 'numeric', minute: '2-digit' }` | `Sep 20, 2026, 11:45 AM` |
| `date-compact` | `"MMM d"` | `{ month: 'short', day: 'numeric' }` | `Sep 20` |
| `date-time-compact` | `"MMM d, h:mm tt"` | `{ month: 'short', day: 'numeric', hour: 'numeric', minute: '2-digit' }` | `Sep 20, 11:45 AM` |

`date-compact`/`date-time-compact` (no year) are a deliberate carve-out, not an oversight: `Shop/Index.cshtml`'s `TransactionDate` and the `SignupTime` sites already omit the year today because the value is always read in the context of the current quest/purchase, never far enough in the past for the year to be ambiguous. Standardizing them up to a year-bearing style would be a gratuitous copy change this phase was not asked to make.

**Relative rendering ("2 hours ago") is declined**, per CONTEXT.md — not part of this vocabulary, and no call site should adopt it.

### 4. Zone labelling

- **The visible rendered text never carries a zone label, on any surface, for any value — real instant or wall-clock.** This is D-01, unconditionally: labelling would make the page look more timezone-aware than the model actually is.
- **The `title` attribute is the only place a zone designator (`UTC`) ever appears**, and only on real-instant `<time>` elements, only on hover/focus, per D-02. This is diagnostic metadata for whoever is debugging a "wrong time" report, not reader-facing content — see §6 for why this is acceptable despite not being keyboard-reachable.
- **Emails carry no zone label because the question is moot, not because it was rejected.** CONTEXT.md confirms all four transactional templates (`QuestFinalized`, `QuestDateChanged`, `SessionReminder`, `WaitlistPromoted`) render only `FinalizedDate` — a wall-clock game night, out of scope per D-01 — formatted `"dddd, MMMM d"` with no time component at all. There is no real-instant value anywhere in an email template for this phase to touch, so no email file appears in this phase's diff.

### 5. Desktop/mobile parity rule

**The rule:** every call site in the §3 table that renders a real instant today must gain the `<time>` treatment, and its `.Mobile.cshtml` twin, if that twin renders the *same property* today, must gain the identical treatment in the same wave. Shipping the conversion on one layout and leaving the other layout's existing (unconverted) render of the same value behind is the failure mode this codebase has hit three times before (Phases 43, 54, 72).

**The explicit non-regression carve-out — do NOT "fix" these by adding a new render site:**

Converting the value where it already renders is this phase's job; adding a brand-new rendered field to a mobile view solely to match its desktop twin is scope creep beyond a display-and-scheduling fix (RESEARCH.md Pitfall 6, restated here as a binding contract line, not just a risk note).

**One view-level ripple worth flagging for the plan, even though it isn't a `<time>` render site:** `Series/Details.cshtml:12,17` compute `DateTime.Today` directly in Razor for a "Today" divider label and a confirmation-message string. Once the board-clock seam lands (D-07), this view's "today" should reflect the same board-zone value the seam now provides elsewhere on the page — not a new visual treatment, just passing the already-resolved board-zone `DateOnly`/label down from `SeriesController` instead of the view calling the ambient clock itself.

### 6. Accessibility

- **What assistive tech announces:** a screen reader reads the `<time>` element's visible text content (e.g. "Sep 20, 2026, 11:45 AM") — not the `datetime` attribute, which has no standard exposure to the accessibility tree beyond making the *text* machine-parseable for tools that choose to read it. No `aria-label` or `aria-describedby` should be added; the element's accessible name stays its own text content, identical to how the plain text it replaces reads today.
- **`title` is not keyboard-reachable, and that is accepted, not fixed.** A non-interactive `<time>` element receives no keyboard focus stop by default, so a keyboard-only or screen-reader user cannot trigger the native `title` tooltip. Per D-02 (locked), `title` is the specified mechanism — this spec does not reopen that decision, but per this phase's own accessibility checklist item, states the trade-off explicitly: the raw-UTC disclosure in `title` is diagnostic information for a sighted, mouse-hovering reader debugging a "this time looks wrong" report, not information required to use the page. A keyboard/screen-reader user is left at exactly today's baseline — today's raw `.ToString(...)` renders disclose nothing at all (no title, no tooltip, no alternate text) — so this phase is a net accessibility improvement for sighted mouse users and a neutral no-op for everyone else, not a new regression.
- **Do not upgrade `title` to a Bootstrap `data-bs-toggle="tooltip"` widget.** The codebase has exactly one existing precedent for that pattern (`_MarkdownEditor.cshtml`'s info-icon hint), and it is also mouse/hover-only with no keyboard equivalent — so upgrading would not close the keyboard gap, while it would add a dotted-underline/focus-ring affordance and a small icon that D-02's "no visual weight" requirement explicitly rules out.
- **The client-side `textContent` swap needs no `aria-live` region.** Mutating the element after `DOMContentLoaded` without a live region means a screen reader that already announced the page on load will not re-announce the corrected value. This is intentional: an unsolicited live-region interruption for a routine, expected first-paint correction would be more disruptive than silent, and it matches D-05's design goal that the swap be imperceptible in the common (board-zone reader) case. If the user tabs back to the element later, assistive tech reads whatever text is currently in the DOM at that time — normal behavior, nothing special to implement.

### Implementation seam notes (non-visual, included because the contract is meaningless without them)

- **New helper location:** `QuestBoard.Service/Extensions/HtmlHelperExtensions.cs`, following the existing `Html.Markdown` precedent exactly — an `internal static` `IHtmlHelper` extension method that resolves `IBoardClock` from `RequestServices` (mirroring `Html.Markdown`'s `IMarkdownService` resolution), not a `TagHelper` (none exist in this solution).
- **Hydration script location:** `QuestBoard.Service/wwwroot/js/site.js`, the one shared, un-bundled script both `_Layout.cshtml:256` and `_Layout.Mobile.cshtml:217` already load identically. Implement as a plain function (e.g. `hydrateLocalTimes()`) invoked from inside the file's existing single bottom `DOMContentLoaded` listener — the same block that already initializes toasts and Bootstrap tooltips — rather than registering a second `DOMContentLoaded` listener, matching the file's existing one-listener convention.
- Selector: `document.querySelectorAll('time.local-time[datetime]')`, reading `data-style` to pick the matching `Intl.DateTimeFormat` options table from §3, and `Intl.DateTimeFormat().resolvedOptions().timeZone` (no argument passed to the locale, so the browser's own locale formatting conventions apply too — this is intentional, not just the timezone).
- **Null contract:** `Html.LocalTime` takes a **non-nullable** `DateTime`. Every existing call-site null guard stays exactly as it is today — no nullable overload, no `—` placeholder, no change to any conditional-render branch. See `## UI Considerations` → E1/empty.
- **Failure contract:** per-element `try`/`catch` inside the loop. A malformed `datetime`, a missing or unrecognised `data-style`, or an `Intl` throw skips that element with its server-rendered board-zone text intact and the loop continues. Never a default-style fallback, never a blank, never an aborted pass. See `## UI Considerations` → E2/error and E2/partial.
