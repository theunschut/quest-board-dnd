<objective>
Build the persistence layer for series: a dedicated `EventSeriesRepository` with its own interface, plus
the narrow occurrence-write methods the cancel, move and edit-scope paths need on `EventRepository`.

**Discretion resolved here, explicitly, so no later plan has to guess:** `EventSeries` gets its own
domain-model / repository / service triple rather than being folded into `IEventService`. Rationale: the
series surface is not one more CRUD entity — it carries a generator, an idempotent materializer, a
runway health query, a two-outcome removal, an end-by-date lifecycle and a template sweep. Folding that
into `IEventService` would make one interface serve two unrelated lifecycles, and this codebase's
convention is one service per entity (see `IEventSignupService` sitting beside `IEventService` rather
than inside it). 76-RESEARCH.md § Open Questions reaches the same conclusion.

Purpose: every read and write the rest of the phase performs lands here, and three of the phase's
hard constraints (D-18, D-20, D-12) are enforced by the shape of these queries.
Output: `IEventSeriesRepository` / `EventSeriesRepository`, four new `EventRepository` methods, DI
registration, and a repository test class proving the constraints.
</objective>

   write half of the edit-scope sweep (D-09).

3. `Task<int> CountLiveSiblingsOnDateAsync(int seriesId, DateOnly date, int excludeEventId, CancellationToken token = default)` —

   shown when a DM moves an occurrence onto a date another live session of the same series already holds

4. `Task<IList<Event>> GetOccurrencesForSeriesAsync(int seriesId, CancellationToken token = default)` —

Members, all group-scoped implicitly by the entity query filters — add no manual `GroupId` predicate and
do not bypass the filters anywhere in this file:

- `Task<EventSeries?> GetSeriesAsync(int seriesId, CancellationToken token = default)` — single row or
  null; another board's series returns null through the filter, which is what turns a cross-board id into
  a not-found rather than an exception.

- `Task<IList<EventSeries>> GetActiveSeriesAsync(DateOnly today, CancellationToken token = default)` —
  every series in the active board whose `EndDate` is null or is on/after `today`, ordered by `Id`. An
  ended series generates nothing further (D-11).

- `Task<IReadOnlyCollection<int>> GetSlotIndexesForSeriesAsync(int seriesId, CancellationToken token = default)` —
  selects `SeriesSlotIndex` for every occurrence of the series where the slot index is not null, and
  returns them as a `HashSet<int>`. **This method takes no date parameter and must never grow one.**
  Restricting it to a window is the exact optimisation that silently reintroduces the resurrection bug:
  an occurrence a DM dragged far into the future or backwards into the past sits outside any window, so
  the slot reads as free and regenerates on its original date, leaving two rows. It also deliberately
  includes cancelled occurrences, because a cancelled slot has been handled and must not be recreated
  (D-14, D-18, D-20).

- `Task<int> CountLiveFutureOccurrencesAsync(int seriesId, DateOnly today, CancellationToken token = default)` —
  counts occurrences of the series with `CancelledAt` null and `Date` on/after `today`. This is the runway
  measure: live upcoming sessions, not a date horizon, so a fortnightly series gets as many upcoming
  sessions as a weekly one and cancelling near the edge pulls more in (D-21).

- `Task<IList<SeriesRunwayStatus>> GetSeriesBelowRunwayAsync(DateOnly today, int runwayTarget, CancellationToken token = default)` —
  for every active series in the active board, project its id, title and its live-future occurrence count,
  and return only those below `runwayTarget`, ordered by count ascending. One query, no per-series round
  trip; this backs the DM-visible horizon banner (D-26).

- `Task<SeriesRemovalImpact> GetRemovalImpactAsync(int seriesId, DateOnly today, CancellationToken token = default)` —
  returns `PastCount` (occurrences dated before `today`), `FutureCount` (dated on/after `today`) and
  `AnsweredCount` (signup rows on those occurrences whose `UpdatedAt` is not null — answers a person
  actually gave, not automatic passes). Cancelled occurrences are counted in whichever bucket their date
  puts them (D-13).

- `Task<int> SetEndDateAsync(int seriesId, DateOnly endDate, bool removeFutureOccurrences, CancellationToken token = default)` —
  narrow scalar write setting `EndDate` on the series row. When `removeFutureOccurrences` is true, also
  removes occurrences of that series dated after `endDate`, letting the shipped signup cascade take their
  availability rows; occurrences dated on or before `endDate` are always kept because they record sessions
  that happened. Returns the number of occurrences removed, for the toast/confirm. One `SaveChangesAsync`
  (D-11).

- `Task<bool> SetTemplateAsync(int seriesId, string title, string? description, TimeOnly? startTime, CancellationToken token = default)` —
  narrow scalar write assigning the three template fields on the series row, one `SaveChangesAsync`,
  returning false when the series was not found. This is the only writer of the series template: template
  changes flow exclusively through the occurrence edit's scope prompt, so there is exactly one place they
  can be made and no second dialog whose propagation rules could diverge (D-09, D-10).

- `Task DeleteWithOccurrencesAsync(int seriesId, CancellationToken token = default)` — removes every
  occurrence of the series first, then the series row, in one `SaveChangesAsync`. The shipped foreign key
  from `Events` to `EventSeries` declares no delete behaviour and therefore defaults to no action, so
  removing the series while occurrences still reference it throws; the occurrence removal is not optional
  tidiness, it is what makes the delete possible at all. Signup rows go with their occurrences through the
  existing cascade (D-12).

- `Task DetachOccurrencesAndDeleteAsync(int seriesId, CancellationToken token = default)` — sets **both**
  `SeriesId` and `SeriesSlotIndex` to null on every occurrence of the series, then removes the series row,
  in one `SaveChangesAsync`. Nulling only the series id would leave a row that claims a slot of a series
  that no longer exists, and the filtered unique index would stop covering it while the data still says it
  belongs to a series. A cancelled occurrence keeps its cancelled marker when detached — a cancelled
  one-off is a coherent state, and clearing it would silently turn a session someone called off back into
  a live one (D-12, D-15).

- `Task CreateWithOccurrencesAsync(EventSeries series, IReadOnlyList<Event> occurrences, IReadOnlyCollection<int> campaignMemberIds, CancellationToken token = default)` —
  the one transactional boundary on the controller save path. Open a transaction only when the provider is
  relational (`DbContext.Database.IsRelational()`), because the in-memory provider used by the unit tests
  rejects transactions; hold it in a nullable local and commit it at the end if it exists. Inside: add the
  series through the base `AddAsync`, then for each occurrence assign the new `SeriesId` and call the
  existing `eventRepository.AddWithCampaignFanOutAsync` when `campaignMemberIds` is non-empty, or
  `eventRepository.AddAsync` when it is empty. Both repositories share the same scoped `QuestBoardContext`,
  so the transaction covers every save inside. Do **not** reimplement the fan-out here: the existing method
  already leaves each automatic signup's answered marker unset, and a second implementation risks stamping
  it and breaking the distinction the availability overview depends on (D-25, D-29, D-30).

Write a file-level or class-level comment explaining, in plain language and without tracking references,
why the slot-index query carries no date predicate. Do not write any requirement ID, phase number,
decision ID or plan number into any comment or string literal.
