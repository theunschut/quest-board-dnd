<objective>
Add the series detail page — reached from any occurrence — showing the recurrence rule and template
read-only, the occurrences the series has produced, and the two lifecycle controls: End Series, and
Remove with its delete-or-detach choice.

**Discretion resolved here:** the series page is a new `SeriesController` rather than more actions on
`EventsController`. Rationale: `EventsController` is already at eight actions across three concerns
(details, CRUD, availability), the series page has its own view folder and its own lifecycle, and a
separate controller gives the page a clean `/Series/Details/{id}` route that the occurrence page can link
to without route ambiguity.

Purpose: this is where a DM sees what a rule is actually doing, and the only place a series can be ended
or removed. It is also the surface that makes the runway honest — a DM who suspects something is wrong
comes here after the calendar banner has already told them to.
Output: `SeriesController`, two series view models, their mapping, and the series Details view.
</objective>

The controller name gives the view folder `Views/Series` and the route `/Series/...`.

Copy the private `SeriesIsOnActiveBoardAsync`, `IsDmTierAsync` and `GetEffectiveRoleAsync` helpers from
`EventsController` verbatim in behaviour, including their comments' reasoning: the read filter already
hides another board's schedule, and the explicit comparison is a deliberate second layer so a weakened
filter still cannot let a write land on another board's series; with no active group there is nothing to
match, so it fails closed.

**`[HttpGet] Details(int id, CancellationToken token = default)`** — any board member may view. Load the
series with `GetSeriesAsync` and return `NotFound()` when it is null, which is also what a cross-board id
produces through the query filter. Map it to `SeriesDetailsViewModel`, fill `CyclePositions` from
`EventSeriesDateGenerator.ParseMask(series.CycleMask)`, fill `Occurrences` from `GetOccurrencesAsync`, set
`CanManage` from `IsDmTierAsync`, and — only when `CanManage` — fill the three removal-impact counts from
`GetRemovalImpactAsync`. The counts are management information and there is no reason to compute or send
them to a player.

**`[HttpPost] [Authorize(Policy = "DungeonMasterOnly")] [ValidateAntiForgeryToken] End(int id, CancellationToken token = default)`** —
require `SeriesIsOnActiveBoardAsync` and return `BadRequest()` otherwise. Call
`eventSeriesService.EndAsync(id, DateOnly.FromDateTime(DateTime.Today), removeFutureOccurrences: true, token)`.
Ending sets a date rather than a flag, so the same column also expresses a fixed-length arc declared at
setup time on the create form; and because the confirm the DM just accepted states that upcoming sessions
will be cleared, the clearing is part of the same action rather than a second step. Sessions dated today
or earlier are always kept — they record sessions that happened. Set
`TempData["Success"] = "Series ended successfully.";` and redirect back to this page so the DM sees the
new end date.

**`[HttpPost] ... Delete(int id, ...)`** — same guards; call `eventSeriesService.DeleteAsync`, set
`TempData["Success"] = "Series deleted successfully.";` and redirect to the calendar index. Every
occurrence goes with the series and their availability rows follow through the shipped cascade.

**`[HttpPost] ... Detach(int id, ...)`** — same guards; call `eventSeriesService.DetachAsync`, set
`TempData["Success"] = "Series detached — its sessions are now one-off events.";` and redirect to the
calendar index. Only the rule is removed; every session stays as an ordinary one-off event, which serves
the case where the recurrence was wrong but the sessions that were played should stay.

Do not write any requirement ID, phase number, decision ID or plan number into any comment or string
literal.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Any authenticated member -> GET /Series/Details/{id} | A series id from a URL may name another board's series |
| DM browser -> POST /Series/End, /Series/Delete, /Series/Detach | Three destructive operations that can remove an entire board's worth of sessions |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-76-37 | Elevation of Privilege | `SeriesController.End` / `Delete` / `Detach` on another board's series | critical | mitigate | Every mutating action carries the DM-only authorization policy and antiforgery validation, and re-resolves the series' owning board against the active board before writing, failing closed when no board is active |
| T-76-38 | Information Disclosure | `SeriesController.Details` serving another board's rule and occurrence list | high | mitigate | The series and occurrence reads go through the fail-closed query filter, so a cross-board id yields a not-found rather than data |
| T-76-39 | Information Disclosure | Removal-impact counts exposed to a non-manager | low | mitigate | The counts are computed and populated only when the viewer is DM-tier; a player's page never carries them |
| T-76-40 | Tampering | Rule or template edited from the series page | medium | mitigate | The page renders no form field for the rule or the template at all, asserted by a grep for input elements; template changes have exactly one entry point elsewhere |
| T-76-41 | Repudiation | A destructive removal taken without understanding its blast radius | medium | mitigate | The removal dialog states the exact past, future and real-answer counts before either outcome can be chosen, and the end confirm names the same figures |
| T-76-SC | Tampering | npm/pip/cargo installs | high | accept | 76-RESEARCH.md § Package Legitimacy Audit records zero packages installed this phase; no plan in Phase 76 contains a package-install task |
