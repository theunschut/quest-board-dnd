# Phase 76 — UI Design Contract: Recurring Event Series

> Visual and interaction contract for the six surfaces this phase touches: Create Event, Edit Event, Event Details, the new Series Details page, the desktop calendar, and the mobile agenda. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Read alongside:** `76-CONTEXT.md` (30 locked decisions, D-01…D-30). This spec resolves the interaction-shape discretion items CONTEXT.md left open (D-09's dialog type, D-13's dialog type, toggle-strip styling and cap, preview count and past-anchor behaviour, and all confirm/banner/toast copy) and pins them as one design contract so planner and executor do not each resolve them differently.

## Spacing Scale

This is a Bootstrap 5 app; spacing is expressed through Bootstrap's spacer utility classes, not raw px. Bootstrap's default spacer scale already maps onto the required 8-point rhythm:

| Token | Bootstrap class | Value | Usage |
|-------|-----------------|-------|-------|
| xs | `gap-1` / `p-1` | 4px | Icon-to-text gaps inside a toggle-strip cell, badge padding |
| sm | `mb-2` / `gap-2` | 8px | Compact stacks — toggle-strip cell gap, button groups (`d-flex gap-2` already used on Details availability buttons) |
| md | `mb-3` | 16px | Default field spacing — every form field on Create/Edit already uses this |
| lg | `mb-4` | 24px | Section-to-section spacing inside a card body (e.g. between the repeats toggle and the fields it reveals) |
| 2xl | `mb-5` | 48px | Not used within this phase's surfaces — reserved for page-level breaks the existing layout already owns |

Exceptions:
- The cycle-mask toggle-strip cells (new component, D-03) use a fixed 32×32px touch target with 4px gap — see Cycle-Mask Toggle Strip below. 32px satisfies the 4-multiple rule and matches the existing vote-button `.btn-sm` icon-button footprint (`calendar.css` `.vote-buttons .btn`).
- `.modern-card-body` padding is fixed at `1.5rem` (24px) app-wide — do not override it for any new card this phase adds.

## Typography

This app has no declared type scale; it inherits Bootstrap defaults with `!important` color overrides in `modern-card.css`. This phase must not introduce a new scale — it declares the sizes already in effect so new markup matches without guessing.

| Role | Size | Weight | Line Height | Where it already exists |
|------|------|--------|-------------|--------------------------|
| Small / meta | 14px (`.small`, `<small>`) | 400 | 1.4 | Timestamps, badges, `.form-text` helper copy |
| Body | 16px (browser default, `.form-control`, `<p>`) | 400 | 1.5 | Card body copy, description text |
| Label | 16px (`.form-label`) | 600 | 1.3 | `.modern-card .form-label` is already forced to weight 600 |
| Heading | 24px (Bootstrap `h4`) | 600 | 1.2 | Sub-section card headers ("Actions", "Description", "Your Availability") |
| Display | 32px (Bootstrap `h2`) | 600 | 1.2 | Page-title card headers (`modern-card-header h2`) |

Only two weights are in play — 400 (body/meta) and 600 (labels/headings) — matching the existing CSS forcing every `.modern-card` heading and label to 600. Do not introduce a third weight for this phase's new markup (toggle strip, series page, badges).

## Color

The app's palette is a "parchment on dark fantasy glass" system, not a flat light/dark UI. Values below are the ones already shipped; this phase adds exactly one new semantic use (the cancelled/muted state) and reuses everything else.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `rgba(255,255,255,0.15)` glass over the app's dark background image | `.modern-card` body surface — every new card this phase adds (repeats section, series-rule card, occurrence list card) |
| Secondary (30%) | `rgba(255,255,255,0.05)` (card headers) and `#343a40` (mobile agenda entry surface) | `.modern-card-header`, `.agenda-event-entry` / `.agenda-quest-entry` dark surfaces |
| Accent (10%) | `#6f42c1` (event purple) | **Reserved exclusively for event/series identity** — the calendar event chip's left border, the mobile agenda event entry's left border, the Legend swatch, and (new) the cycle-mask toggle strip's "on" cell fill and the Series Details page header icon. Do not spread this purple onto generic buttons or onto quest chips. |
| Destructive | `#dc3545` (Bootstrap `btn-danger` / `text-danger`) | Delete Series, Delete Event (one-off), and the delete leg of the D-13 two-outcome dialog |

New semantic addition this phase:

| Role | Value | Usage |
|------|-------|-------|
| Cancelled / muted | `opacity: 0.55` + `text-decoration-line: line-through` on the existing chip/entry, no new hue | Desktop calendar cancelled chip (D-15), mobile agenda cancelled entry (D-15). Deliberately *not* a new color — a cancelled occurrence is the same purple event chip, faded and struck through, so it reads as "this event, but off" rather than a fourth chip type competing for attention. |
| Amber / warning-adjacent | `#ffc107` (Bootstrap `btn-outline-warning`) | Cancel-occurrence button (D-16) — see Cancel vs Delete below |

Accent reserved for: the event-purple `#6f42c1` never appears on anything except an event/series visual identity marker (chip border, agenda entry border, legend swatch, toggle-strip "on" state, series-page header icon). It must not be used for the repeats checkbox itself, for form focus rings (those stay Bootstrap's default `#3498db` per `modern-card.css:117`), or for any button.

## Interaction Contracts (per surface)

### 1. Create Event form — "Repeats" toggle (D-03, D-04, D-05, D-06, D-08)

Extends `Views/Events/Create.cshtml`. Follows the shipped checkbox-reveals-a-section idiom at `Views/ShopManagement/Create.cshtml:117-123`, with one deliberate deviation: because the revealed content (cadence + mask + preview) is structurally larger than two `disabled` inputs, the section is shown/hidden via a JS-toggled `d-none` class on a wrapper `<div>`, not via `disabled` attributes on always-rendered inputs.

Placement, in form order:
1. Existing Title field (unchanged).
2. Existing Date field — **this becomes the series anchor date when Repeats is on.** No separate "anchor date" field is added; label text below the field changes conditionally (see step 4).
3. Existing Start Time field (unchanged) — becomes the template start time for every generated occurrence (D-08).
4. New checkbox: `<div class="form-check mb-3">` — `id="enableRecurrence"`, label "Make this a recurring series". `.form-text` helper: "Generates future occurrences automatically on a repeating schedule."
5. New `<div id="recurrenceSection" class="d-none">` (revealed on check), containing, top to bottom:
   - **Interval**: number input, label "Repeat every", suffix "week(s)" — `min="1"`, default `1`.
   - **Derived weekday text**: a plain read-only line, not an input — "Every {N} week(s) on **{Weekday}**" (computed client-side from the Date field's current value via JS `Date`, updates instantly on Date change — this is presentation-only, not the generation logic, so no server round trip is needed for this line per se; the actual dates still come from the D-05 preview fetch).
   - **Cycle-Mask Toggle Strip** — see dedicated section below.
   - **End date (optional)**: `type="date"`, label "End after (optional)", helper text "Leave blank for an open-ended series. You can end it later from the series page."
   - **Live preview panel**: heading "Next occurrences", a `<ul>`/table listing dates, refreshed by the debounced fetch (below).
6. `<hr />` and the existing Cancel/Create Event button row (unchanged).

**Live preview fetch (D-05):**
- Follows the `Views/Quest/Details.cshtml:966` idiom: `fetch` with `FormData`, antiforgery token appended, **but** this call does not reload the page or `alert()` on failure — it is read-only and non-blocking. On success it replaces the preview list's contents; on failure it shows the inline error copy from the Copywriting Contract.
- Trigger: any change to Date, Interval, the mask strip, or End Date, debounced **400ms** after the last change, one in-flight request at a time (a new keystroke cancels/ignores a stale in-flight response by request-token comparison, not a naive "last response wins").
- Endpoint: `POST /Events/PreviewSeries` (or equivalent action name the planner assigns) — takes anchor date, interval, mask, optional end date; returns up to 10 candidate dates. Server-side this must call the **same Domain generator method** that materializes occurrences (D-05's core guarantee) — never a second implementation.
- Preview count: exactly **10** (EVTRECUR-02's "~10"), or fewer only when an End Date truncates the series to fewer than 10 sessions before that date.

### 2. Cycle-Mask Toggle Strip (D-03) — new component

This is the one genuinely new interactive widget in a codebase whose forms are otherwise plain Bootstrap inputs. Keep it visually minimal and consistent with the existing `.vote-buttons .btn` icon-button footprint rather than inventing a new visual language.

- **Structure**: a horizontal, wrapping row of square cells, one per cycle position. Each cell is a `<button type="button">` (not a checkbox — there is no natural `<input>` semantics for "toggle this position on/off" at variable length), `32×32px`, `4px` gap, `border-radius: 4px`.
- **States**: "on" cell — filled `#6f42c1` (event purple, the one reserved accent use for this component) with a white checkmark or filled dot; "off" cell — `1px solid` neutral border, transparent/white fill, no icon. Toggling is a plain click that flips the cell's state and re-triggers the debounced preview fetch.
- **Length controls**: a `+` button appended after the last cell (adds one position, defaulting to "on") and a `–` button (removes the last position, minimum length **1**). Both are small icon buttons (`btn-sm`, `fa-plus` / `fa-minus`), visually separated from the toggle cells by an 8px gap so they read as controls, not positions.
- **UI-level cap**: **24 positions**, well below the schema's ~100-position `nvarchar(200)` ceiling (D-03). Rationale: 24 fortnightly-equivalent slots is already a full year of rhythm variation; a UI that scrolls to 100 toggle cells is unusable, and the cap must be enforced before the fact (disable `+` at 24) rather than caught only by a paste-truncation validator. The `+` button becomes `disabled` at 24 with a `title` tooltip "Maximum cycle length reached." Server-side validation still enforces the true ~100 ceiling independently (defense in depth, not this UI's job to relax).
- **Above the strip**: a small live label, "Cycle length: {N}", updates as positions are added/removed.
- **Read-only variant** (Series Details page, D-10): identical visual cells, no click handlers, no `+`/`–` controls, `aria-disabled` and `pointer-events: none` — the rule is read-only there by design (D-10), so the widget must visibly communicate "you cannot edit this here" rather than merely silently ignoring clicks.

### 3. Edit Event form — scope prompt and collision notice (D-09, D-17)

Extends `Views/Events/Edit.cshtml`. The form itself is unchanged for a one-off event (`Model.SeriesId == null`) — same fields, same "Save Changes" button, same direct submit.

When `Model.SeriesId != null` (editing a series occurrence):
- No cadence/mask fields render on this form at all (D-07/D-10 — cadence is immutable and edited nowhere but at creation).
- Clicking "Save Changes" does **not** submit the form directly. JS intercepts the click, and opens the D-09 modal (see Copywriting Contract for exact copy and button labels).
- Before showing the modal, the intercepting JS calls a lightweight server check (can piggyback on the same debounced-preview-style fetch, or a dedicated small endpoint) to determine whether the occurrence's *current form date* collides with a live sibling occurrence's date. If so, the D-17 warning strip renders inside the modal; if not, the modal shows just the two scope buttons with no warning strip.
- Choosing "Only this event" or "This and all future events" submits the underlying form with a hidden `scope` field set accordingly, then behaves like any other POST (existing validation summary, redirect-with-toast on success).
- "Cancel" in the modal closes it with no submission — the user is back on the unsaved Edit form.

### 4. Event Details page — cancelled state, Cancel vs Delete, series link (D-06, D-15, D-16)

Extends `Views/Events/Details.cshtml`. No `.Mobile` variant exists for this view — one Razor view serves both platforms (confirmed in `<scope_note>`); all markup below must therefore hold up at both the desktop viewport and a real mobile User-Agent, not just visually inspected at desktop width.

- **Cancelled banner** (D-15): when `Model.IsCancelled` (or whatever the planner names the marker per CONTEXT.md's open naming discretion), render an `alert-secondary` block immediately above the "Your Availability" card: icon `fa-ban` + "This session has been cancelled." The entire "Your Availability" card (answer buttons, roster answer badges can stay visible as historical record, but the Yes/Maybe/No action buttons and the Withdraw button must not render) is suppressed for the acting user's own controls — matching D-15's "availability buttons removed."
- **Cancel vs Delete** (D-16): in the "Actions" card (`Model.CanManage` block), a series occurrence (`Model.SeriesId != null`) shows a "Cancel Occurrence" button in place of "Delete Event." Deliberately different visual treatment from Delete so the two are never confused at a glance: Delete stays `btn-danger` (filled red) with `fa-trash`; Cancel uses `btn-outline-warning` (amber outline, not filled) with `fa-ban` — same icon pairing precedent as `ShopManagement/Index.cshtml`'s discontinue control. A one-off event (`Model.SeriesId == null`) keeps "Delete Event" exactly as shipped — no change.
- **Series link** (D-06): every occurrence's Details page — cancelled or not, series or not-a-series — for a series member only, shows a link/button "View Series Details" (icon `fa-repeat` or `fa-sync-alt`, `btn-outline-secondary` sizing to match the existing "Edit Event" button footprint) inside the same "Actions" card, above the Cancel/Delete control.
- **Enforcement**: the Cancel-replaces-Delete rule is server-side (D-16) — re-resolve `SeriesId` on the POST action itself, not merely on which button rendered. This spec covers the visual contract; the server check is a planning/implementation concern already locked by D-16.

### 5. NEW — Series Details page (D-06, D-10, D-11, D-12, D-13)

New view, reached from any occurrence's Details page. Follows the `modern-card` / `modern-card-header` / `modern-card-body` pattern per `CLAUDE.md`.

```html
<div class="card-header modern-card-header">
    <h2 class="mb-0">
        <i class="fas fa-repeat text-purple me-2"></i>
        {Series.Title} — Recurring Series
    </h2>
</div>
```
(Where "text-purple" is a small new utility class — `color: #6f42c1 !important` — since Bootstrap has no built-in purple text utility and this is the one place the accent needs to color text rather than a border.)

Layout — three stacked cards in the body, in this order:

1. **"Recurrence Rule" card** (read-only, D-10 — no edit form anywhere on this page):
   - Anchor date, Interval ("every {N} week(s)"), derived weekday text, the **read-only** cycle-mask toggle strip variant (see component spec above), End Date or "No end date — runs indefinitely."
   - Template fields: Title, Start Time, Description (rendered via the same Markdown partial used on Details, read-only).
2. **"Occurrences" card**: a table — Date | Status | link — one row per materialized occurrence, past and future, ordered by date. Status badge: "Scheduled" (default, no badge needed — plain row) vs "Cancelled" (`bg-secondary` badge, row text struck through matching the calendar/agenda treatment for visual consistency across all three surfaces). A `<hr>` or a "Today" row divider separates past from future, reusing the same "today" visual marker convention `_Calendar.cshtml` already establishes (`day.Date.Date == DateTime.Today` → `today` class) rather than inventing a new past/future visual language.
3. **"Actions" card** (`Model.CanManage`-gated, matching Details' existing gate):
   - "End Series" button (`btn-warning`, `fa-flag-checkered` or `fa-stop`), native `confirm()` per the Copywriting Contract.
   - "Delete Series" button (`btn-danger`, `fa-trash`), opens the D-13 two-outcome modal per the Copywriting Contract.
   - Button order follows the existing convention: within this single-column Actions card (mirroring `Details.cshtml`'s vertical `w-100 mb-2` stack), not the `d-flex justify-content-between` row layout — that layout is for form Cancel/Submit pairs, not a vertical list of independent management actions, matching how `Details.cshtml`'s own Actions card already stacks "Edit Event" above "Delete Event."

### 6. Desktop calendar — cancelled chip, horizon banner, Legend row (D-15, D-26)

Extends `Views/Shared/_Calendar.cshtml` and `Views/Calendar/Index.cshtml` only.

- **Cancelled chip** (D-15): add a modifier class, e.g. `.calendar-event.cancelled`, applied when `eventOnDay.Event.IsCancelled` (naming per planner). CSS: `opacity: 0.55; text-decoration: line-through;` on the existing `.calendar-event` chip — no new color, no new border style, so it reads as "this event, faded" rather than a fourth visual category. The chip stays clickable (still links to Details, where the full cancelled banner lives).
- **Horizon banner** (D-26): rendered once, above the calendar card's month grid, inside `Views/Calendar/Index.cshtml` only (not inside `_Calendar.cshtml` itself, so the partial's other 5 call sites are structurally incapable of rendering it) — see the Guardrail below. DM-gated (same `CanManage`/DM-role check the Create Event nav entry already uses). Copy per the Copywriting Contract.
- **Legend row**: add one row to the existing Legend card (`Views/Calendar/Index.cshtml`, the card added by Phase 74 D-12) for the cancelled state: a `.legend-item` swatch styled `opacity: 0.55` matching the chip treatment, label "Cancelled". This keeps Phase 74's D-12 precedent — "the Legend is the one place the calendar explains its colour coding" — from going stale the moment this phase ships a fourth visual state.

**Guardrail (hard constraint, restated from the phase brief):** `_Calendar.cshtml` has exactly 6 call sites. Only `Views/Calendar/Index.cshtml:32` is in scope for this phase's changes. The other five — `Views/Quest/Details.cshtml:604,648,696` and `Views/Quest/Details.Mobile.cshtml:158,196` — render a per-quest date-picker widget and must render **no** series-specific or cancelled-state markup. The cancelled-chip CSS class (`.calendar-event.cancelled`) only ever applies when `EventsOnDay` is non-empty and an event is actually cancelled — the five protected call sites build their own `CalendarViewModel` and never populate `EventsOnDay`, so the class can never be reached there; this is the existing "collection defaults to empty" protection mechanism already established by Phase 74 D-09, and this phase must not weaken it (e.g. by adding a new ViewBag flag those 5 sites would need to explicitly opt out of). The D-26 horizon banner must be placed in `Calendar/Index.cshtml`'s own markup, never inside `_Calendar.cshtml`, for the same reason — a banner inside the shared partial would leak onto the 5 protected sites with no flag to suppress it.

### 7. Mobile agenda — cancelled entry (D-15)

Extends `Views/Calendar/Index.Mobile.cshtml` and `calendar.mobile.css` only.

- Same modifier approach as desktop: `.agenda-event-entry.cancelled` — `opacity: 0.55; text-decoration: line-through;` on the entry, no new color. Entry stays clickable to Details.
