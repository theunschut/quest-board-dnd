members it would inherit would offer a second way to remove a series that bypasses the deliberate
delete-versus-detach outcomes. Implement it as
`internal class EventSeriesService(IEventSeriesRepository repository, IEventRepository eventRepository, IUserRepository userRepository, IBoardTypeResolver boardTypeResolver, IActiveGroupContext activeGroupContext, IOptions<EventSeriesOptions> options) : IEventSeriesService`
in `QuestBoard.Domain/Services/EventSeriesService.cs`.

Register both in `QuestBoard.Domain/Extensions/ServiceExtensions.cs`: add
`services.AddOptions<EventSeriesOptions>().BindConfiguration(EventSeriesOptions.SectionName);` beside the
existing `EmailSettings` options line, and `services.AddScoped<IEventSeriesService, EventSeriesService>();`
immediately after the `IEventSignupService` registration. Because the options class carries code
defaults, a deployment with no matching configuration section still gets a runway of 20 and a preview of
10 — nothing has to change on a server environment file for the feature to work (D-22).

Members:

- `Task<(IReadOnlyList<DateOnly> Dates, bool AnchorFullyInPast)> PreviewAsync(DateOnly anchorDate, int intervalWeeks, string cycleMask, DateOnly? endDate, CancellationToken token = default)` —
  parses the mask, runs `GenerateSlots`, and returns the first `options.Value.PreviewCount` firing dates
  on or after today. `AnchorFullyInPast` is true when the first `PreviewCount` firing slots computed from
  the anchor are *all* before today, which is what lets the form explain that the listed dates start from
  today rather than from the anchor. Touches no database whatsoever — it is a pure read over the
  generator, which is precisely what makes it impossible for the preview to disagree with what a save
  later creates (D-05).

- `Task<EventSeries> CreateWithFirstPassAsync(EventSeries series, CancellationToken token = default)` —
  derives `series.WeekDay` from `series.AnchorDate.DayOfWeek` and writes it (D-04); resolves the active
  group id and throws `InvalidOperationException` when there is none, because a series with no board is
  not a state this method may invent; parses the mask; computes the first `options.Value.RunwaySize`
  firing slots dated today or later (D-23); builds one `Event` per slot from the series template with
  `Title`, `Description`, `StartTime`, `Date`, `SeriesSlotIndex` and `GroupId` set and `SeriesId` left for
  the repository to stamp; resolves the board type and, on a campaign board only, loads member ids via
  `userRepository.GetAllGroupMembers`; then calls `repository.CreateWithOccurrencesAsync` once so the
  series row and the whole first pass share a single transaction and a failure leaves nothing behind
  (D-25). Returns the created series with its new id.

- `Task<int> TopUpAsync(int seriesId, CancellationToken token = default)` — the idempotent materializer,
  and the single method both the controller path and the nightly job path use (D-24). Steps, in order:
  load the series and return 0 if it is missing or its end date has passed; parse the mask; load **every**
  existing slot index for the series into a `HashSet<int>` via `GetSlotIndexesForSeriesAsync` (no date
  argument exists on that method and none may be introduced); read the current live-future count; return 0
  immediately when it already meets `options.Value.RunwaySize`; resolve the group, board type and — on a
  campaign board — the member ids once; then walk `GenerateSlots` from slot 0 with `MaxSlotScan`, skipping
  non-firing slots, skipping slots dated before today, and skipping slots already present in the set.
  For each remaining slot: build the occurrence from the template, write it through
  `AddWithCampaignFanOutAsync` on a campaign board or `AddAsync` otherwise, then add the slot to the set
  and increment the live-future counter. Stop when the counter reaches the runway target or the generator
  runs out. Return the number created.

  Three properties of that loop are load-bearing and must not be "simplified": the membership check runs
  before *every* write rather than once at the top, so a retry after a mid-run crash finds the earlier
  occurrences already present and only creates the rest; each occurrence is its own unit of work with its
  own signups, so progress is monotonic under the app's global five-attempt retry policy; and a cancelled
  occurrence's slot is in the set, so cancelling never causes a re-creation while still freeing a runway
  slot for the *next* candidate (D-14, D-18, D-21, D-25).

- `Task<EventSeries?> GetSeriesAsync(int seriesId, CancellationToken token = default)`,
  `Task<IList<EventSeries>> GetActiveSeriesForActiveGroupAsync(CancellationToken token = default)`,
  `Task<IList<Event>> GetOccurrencesAsync(int seriesId, CancellationToken token = default)`,
  `Task<IList<SeriesRunwayStatus>> GetSeriesBelowRunwayAsync(CancellationToken token = default)` (passing
  today and `options.Value.RunwaySize`), `Task<SeriesRemovalImpact> GetRemovalImpactAsync(int seriesId, CancellationToken token = default)`,
  `Task<int> CountLiveSiblingsOnDateAsync(int seriesId, DateOnly date, int excludeEventId, CancellationToken token = default)` —
  thin delegates that supply "today" and the configured runway so no caller has to.

- `Task<int> EndAsync(int seriesId, DateOnly endDate, bool removeFutureOccurrences, CancellationToken token = default)`,
  `Task DeleteAsync(int seriesId, CancellationToken token = default)`,
  `Task DetachAsync(int seriesId, CancellationToken token = default)` — delegates to the matching
  repository methods. Ending sets a date, never a flag, so the same column also expresses a fixed-length
  arc declared at setup time (D-11); removal has two distinct outcomes and neither is a cascade (D-12).

- `Task<int> ApplyTemplateToFutureAsync(int seriesId, int editedEventId, string title, string? description, TimeOnly? startTime, CancellationToken token = default)` —
  the this-and-future scope. Load the series and every occurrence of it. Compute the eligible set
  **before** touching the series row, comparing each occurrence against the *old* template: eligible means
  the occurrence is not the one just edited, is dated today or later, is not cancelled, has a slot index
  whose `DateForSlot` value still equals its stored date (so it has not been separately moved), and whose
  `Title`, `Description` and `StartTime` still match the old template (so it has not been separately
  edited). Then call `repository.SetTemplateAsync` so newly generated slots inherit the change, then call
  `eventRepository.ApplyTemplateToOccurrencesAsync` with the eligible ids. Return the number of
  occurrences swept.

  No past occurrence is ever rewritten by any scope — past occurrences are the record of sessions that
  happened. And an occurrence somebody deliberately moved, edited or cancelled is skipped, because a
  deliberate one-off decision must not be silently undone by an unrelated title change (D-09).

Take "today" from `DateOnly.FromDateTime(DateTime.Today)` in this service, once per method, and pass it
down — the generator itself stays clock-free. Write doc comments explaining *why* the slot set carries no
date filter and why each occurrence commits separately, in plain language with no tracking references.
Do not write any requirement ID, phase number, decision ID or plan number into any comment or string
literal.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Hangfire retry -> materialization loop | A partially-failed run re-executes from the top under the app's global five-attempt retry policy |
| Persisted cadence (user-authored) -> generation loop | Anchor, interval and mask come from a form and drive an unattended loop |
| Active group context -> every series write | The service writes occurrences and signups; a wrong or absent group would write to the wrong board or fail closed |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-76-13 | Tampering | `EventSeriesService.TopUpAsync` under retry | high | mitigate | The slot-membership check runs immediately before every occurrence write, not once per invocation, and each occurrence plus its signups is its own save — a retry finds prior writes present and only adds the remainder; the database's filtered unique index is the second layer if two writers race |
| T-76-14 | Tampering | Campaign fan-out inside `TopUpAsync` / `CreateWithFirstPassAsync` | high | mitigate | The shipped `AddWithCampaignFanOutAsync` is called rather than re-implemented, so automatic signup rows keep their answered marker unset; a test asserts directly on the persisted rows that the marker is null |
| T-76-15 | Denial of Service | Generation loop driven by a persisted cadence | high | mitigate | The loop is bounded three ways: the generator's own scan ceiling, the runway target, and the end date; an all-zero mask cannot be persisted because the mask validator rejects it |
| T-76-16 | Elevation of Privilege / Information Disclosure | Writes performed with no active group | high | mitigate | `CreateWithFirstPassAsync` and `TopUpAsync` resolve the active group and throw rather than proceeding with none; the entity query filters are fail-closed so a null group would otherwise read zero rows and silently create nothing meaningful |
| T-76-17 | Tampering | `ApplyTemplateToFutureAsync` overwriting deliberate per-occurrence decisions | high | mitigate | Eligibility is computed against the old template before it is changed, and excludes past, cancelled, separately-moved and separately-edited occurrences; five separate test facts pin each exclusion |
| T-76-SC | Tampering | npm/pip/cargo installs | high | accept | 76-RESEARCH.md § Package Legitimacy Audit records zero packages installed this phase; no plan in Phase 76 contains a package-install task |
