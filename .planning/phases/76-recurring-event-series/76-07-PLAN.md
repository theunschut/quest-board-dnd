<objective>
Make the occurrence details page the one surface where a DM cancels or restores a single session, and
make the Cancel-replaces-Delete rule a server-side fact rather than a rendering choice.

Purpose: EVTRECUR-04 — cancel a single occurrence without affecting the rest. A hard delete on a series
occurrence removes the only record that its slot was handled, so the generator would recreate it on the
next run; the tombstone plus the server-side Delete refusal is what makes that impossible.
Output: `Cancel` and `Restore` actions, a `Delete` refusal for series occurrences, and the details view's
cancelled banner, action swap and series link.
</objective>

  <action>
**Add `Cancel`**: `[HttpPost] [Authorize(Policy = "DungeonMasterOnly")] [ValidateAntiForgeryToken] public async Task<IActionResult> Cancel(int id, CancellationToken token = default)`.
Load the event through `eventService.GetEventWithDetailsAsync` and return `NotFound()` when it is null —
an event on another board returns null through the query filter, which is what turns a cross-board id into
a not-found rather than an error. Then re-resolve the condition on the POST itself: if the event has no
`SeriesId`, return `BadRequest("Cancel is only supported for an occurrence of a recurring series.")`.
If it does, require `SeriesIsOnActiveBoardAsync` for that series id and return `BadRequest()` when it
fails, matching the existing edit path's second-layer check. Then call
`eventService.SetCancelledAsync(id, DateTime.UtcNow, token)`, set
`TempData["Success"] = "Event cancelled.";` and redirect back to this event's Details page so the DM sees
the cancelled state immediately rather than being bounced to the calendar.

**Add `Restore`**: the same shape and the same three guards, calling
`eventService.SetCancelledAsync(id, null, token)` and setting
`TempData["Success"] = "Event restored.";`. Un-cancelling is a single write of null and loses nothing,
which is the whole reason the cancelled state is a timestamp on the row rather than a deletion.

**Change `Delete`**: after loading the event and before removing it, if the event has a `SeriesId`,
return `BadRequest("Delete is not supported for an occurrence of a recurring series. Cancel it instead.")`.
This is the load-bearing half of the rule — hiding the Delete button in the view is a convenience, and a
posted delete must be refused on its own merits. A one-off event's delete path is otherwise completely
unchanged, including its existing toast.

Add a comment above the refusal explaining, in plain language, that removing a series occurrence outright
would erase the only record that its slot was ever handled, so the nightly generator would recreate it on
the next run.

Do not write any requirement ID, phase number, decision ID or plan number into any comment or string
literal.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| DM browser -> POST /Events/Cancel, /Events/Restore, /Events/Delete | Only an event id crosses; which button the browser rendered is not evidence of anything |
| Cross-board event or series id -> occurrence mutation | A posted id may name an occurrence or a series belonging to another board |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-76-27 | Elevation of Privilege | `EventsController.Delete` posted against a series occurrence | high | mitigate | The action re-resolves the event's series reference on the POST and returns a bad request; the hidden button in the view is treated as convenience only |
| T-76-28 | Tampering | `Cancel` / `Restore` posted for another board's occurrence | high | mitigate | The event lookup goes through the fail-closed query filter and returns null for another board, and the series is additionally re-checked against the active board with the shipped second-layer helper |
| T-76-29 | Elevation of Privilege | `Cancel` / `Restore` invoked by a non-DM or cross-site | high | mitigate | Both carry the DM-only authorization policy and antiforgery validation, matching every other write action on this controller |
| T-76-30 | Tampering | Forging a cancellation through the ordinary edit form | medium | mitigate | The cancelled marker is ignored on the view-model-to-domain map (plan 06), so the only writer is the dedicated narrow repository method these two actions call |
| T-76-31 | Information Disclosure | Roster remaining visible on a cancelled occurrence | low | accept | The roster is board-scoped and already visible to every member before cancellation; keeping it is the deliberate historical-record behaviour |
| T-76-SC | Tampering | npm/pip/cargo installs | high | accept | 76-RESEARCH.md § Package Legitimacy Audit records zero packages installed this phase; no plan in Phase 76 contains a package-install task |
