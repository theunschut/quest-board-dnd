<objective>
Add the nightly rolling-window top-up job: a dedicated Hangfire recurring job that enumerates real
groups, sets the active group context for each, and tops every active series back to its runway by
calling the same Domain method the controller calls — and correct the stale documentation that claims a
null active group means "see everything".

Purpose: this is the mechanism behind "an open-ended campaign never needs manual re-extension". It is
also the first job in this codebase that *writes* across every board rather than reading with a filter
bypass, which is why the per-group scoping is not a stylistic preference but the whole safety model.
Output: `RecurringOccurrenceTopUpJob`, its registration, its unit tests, and two corrected doc comments.
</objective>

Create `QuestBoard.Service/Jobs/RecurringOccurrenceTopUpJob.cs` in namespace `QuestBoard.Service.Jobs`
as `public class RecurringOccurrenceTopUpJob(IServiceScopeFactory scopeFactory, ILogger<RecurringOccurrenceTopUpJob> logger)`
with a single `public async Task ExecuteAsync(CancellationToken cancellationToken = default)`.

Structure:

1. Enumerate the boards. Declare a local list variable *before* the call, then call
   `HangfireJobHelper.RunInScopeAsync(scopeFactory, groupId: null, ...)` once, resolve `IGroupRepository`
   inside the delegate, call `GetAllWithMemberCountAsync`, and assign the result to that local. The helper
   returns a non-generic `Task`, so the value cannot be returned out of it — capturing into an outer local
   is the pattern, not adding a generic overload to the shared helper. A null group id is correct for this
   one call only, because the group table is the tenant boundary itself and carries no query filter.

2. For each board, call `HangfireJobHelper.RunInScopeAsync(scopeFactory, group.Id, ...)` — a fresh scope
   with a real, non-null group id, which is what sets the active group before any repository call inside.
   Inside the delegate resolve `IEventSeriesService`, call `GetActiveSeriesForActiveGroupAsync`, and call
   `TopUpAsync` for each returned series, accumulating the created count.

   This job writes, so it must never reach for the filter-bypass shortcut the one existing cross-group
   read uses. Every board gets its own scope and its own real group id. Add a comment saying exactly that,
   in plain language.

3. Wrap each board's scope call in a try/catch. Log the failure with the board id and continue to the next
   board, so one bad board cannot starve every other board's calendar. After the loop, if any board failed,
   throw an `InvalidOperationException` naming how many boards failed — the sweep still reports failure so
   the retry policy applies, and the slot-keyed idempotency makes the retry additive rather than
   duplicating what already succeeded.

4. Log one summary line at information level: boards processed, series processed, occurrences created,
   boards failed.

Do not register the job type in the DI container. The existing `DailyReminderJob` is not registered either
— Hangfire's ASP.NET Core job activator constructs an unregistered concrete type from the scope's
services — and adding a registration for one and not the other would be an inconsistency with no benefit.

Register it in `QuestBoard.Service/Program.cs` immediately after the existing
`RecurringJob.AddOrUpdate<DailyReminderJob>` block, inside the same non-Testing branch and therefore still
after `ConfigureDatabase()` so migrations have run before the job can fire:
`RecurringJob.AddOrUpdate<RecurringOccurrenceTopUpJob>("recurring-occurrence-top-up", job => job.ExecuteAsync(CancellationToken.None), "0 3 * * *");`
The job id is `recurring-occurrence-top-up` and the schedule is 03:00 server local time — daily rather than
weekly so a failed run self-heals the next night, at a distinct hour from the 09:00 reminder sweep so the
two never contend, and separate from that job so neither failure can take the other down (D-27).

Do not write any requirement ID, phase number, decision ID or plan number into any comment or string
literal — including the registration comment in `Program.cs`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Hangfire worker thread -> every board's data | The job runs outside the HTTP pipeline, so no session-based group context exists and nothing sets a board unless the job does |
| One board's failure -> every other board's calendar | A single-scope sweep would let one board's error stop generation everywhere |
