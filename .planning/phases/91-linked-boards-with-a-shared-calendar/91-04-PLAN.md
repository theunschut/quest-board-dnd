<objective>
Build the data side of the linked calendar: the per-viewer lookup of the other boards in the active board's set, and one narrowed, filter-bypassing read per entity for their quests and events (D-17). Each read is a flat, month-windowed projection pinned to the linked board ids (D-07), lives in an already-allowlisted repository, keeps cancelled events (D-10), and writes nothing (D-13).

Purpose: Plan 05 builds the overlay service and the desktop calendar on these reads, and the mobile agenda (Plan 08) and the Quest Details calendar (Plan 09) reach them through that service. Keeping the reads in their own plan, proven against InMemory in isolation, keeps the filter-bypass surface small and separately reviewable.
Output: the linked domain models, `GetLinkedBoardsForViewerAsync`, `GetLinkedEventsForCalendarAsync`, `GetLinkedQuestsForCalendarAsync`, and `LinkedCalendarReadTests`.
</objective>

<recorded_choices>
1. **Where the viewer's role per linked board lives (open point 2).** It lives in `LinkedBoardSetRepository.GetLinkedBoardsForViewerAsync`, as one projection over `Groups` with a correlated `UserGroups` lookup for the viewer. All three tables carry no query filter, so this file needs no bypass and is not added to the allowlist. Membership is "a UserGroups row exists for (viewer, board)", which is the same rows the deep-link resolver reads through `GetGroupsForUserAsync`, so "link rendered" and "link works" cannot disagree. The same read supplies the role D-20 needs. It is read fresh on every request and never cached. SuperAdmin is not a parameter here: Plan 05's service passes it separately, where it counts as Admin for DM-only visibility (D-20) but never as membership (D-08, no SuperAdmin branch).
2. **Linked read window (open point 3): windowed.** Quests use one predicate, "has a proposed date in [from, to)". This is a superset of both the open and the finalized placement rules, because a finalized quest only shows on a day that also has a proposed date. Events use `Date in [from, to)`. The predicates are deliberately simple (a single `Any`, no `||`, no conditional) to keep SQL translation low-risk. InMemory cannot prove translation, so Plan 10 carries a user-run local-SQL-Server checkpoint. The fallback if translation fails there is to drop the date predicates (unwindowed parity with own reads) and keep everything else.
3. **D-10 revised.** The linked event read has no cancellation predicate and projects `IsCancelled = e.CancelledAt != null`.
4. **Linked reads go in the already-allowlisted `QuestRepository.cs` / `EventRepository.cs`.** `CrossBoardLinkRepository.cs` promises it never selects entity data. The allowlist stays at five files.
5. **Campaign rule (D-01), lookup side.** The lookup requires the active board's own `BoardType` to equal the set's, and each linked board's to equal it too. Data edited outside the app therefore fails closed to "no linked boards". Whether quests are read at all for a Campaign set is decided by the service in Plan 05 from `ViewerLinkedBoards.SetBoardType`.
6. The assumption-delta decision for the overlay (add-alongside) is recorded in `91-05-PLAN.md`. These reads return separately typed linked rows and never feed the own `Quest`/`Event` collections.
7. ⚠ Spec-less probe fallback was skipped because this phase has no requirement IDs to probe. This is a visible, recorded choice.
8. Reversibility: reversible. These are repository methods and domain types behind stable seams, with no schema change.
</recorded_choices>
