<objective>
Lock the delete in with the three safety nets research says InMemory cannot provide on its own: a model-metadata pin
of every board-owned foreign key (so a new table with a `GroupId` fails a test, not production), the service's
typed-name rules, and a SQL Server-gated test that runs the real delete and a real rollback against the production
migration schema in a throwaway database. Plan 102-10 makes running that gated test against the user's server a
required gate before the phase closes.

This plan depends only on the delete contract from plan 102-01, so it runs in parallel with plan 102-04. Its tests
compile against `IGroupRepository.DeleteBoardAsync`; the gated facts exercise the complete delete when they run in
plan 102-10, after every plan has merged.

Purpose: InMemory enforces no foreign keys and runs no cascades, which is why the original bug shipped (RESEARCH
Pitfall 2). These tests close that gap.
Output: three new test files; no production change.
</objective>
