<objective>
Build the one piece both host views depend on: a shared, self-priming character-select modal that serves add, change and clear from a single instance per page — plus the single label function that keeps all four character dropdowns on the Details page telling the same story.

Purpose: `Details.cshtml` already carries two structurally identical character cells; adding mobile would make a third hand-copy of the same idea. This project's recorded drift class comes from exactly that. Extracting the modal once, and centralising the option-label string once, means the desktop and mobile plans that follow are pure wiring with nothing to diverge on.

Output: `_CharacterSelectModal.cshtml`, a `ToSelectLabel` extension with unit tests, and a fixed data-attribute contract that plans 03 and 04 consume verbatim.
</objective>

<discretion_decisions>
CONTEXT.md left six items to the planner. Decided here, and binding on plans 03 and 04:

1. **Partial boundary** — the partial renders the modal and its priming script only. Trigger buttons stay in each host view, because desktop places the trigger inside a table cell and mobile places it inline within a `<small>` line; those are not the same component. (RESEARCH.md open question 2, same conclusion.)
2. **Per-invocation priming** — `show.bs.modal` + `event.relatedTarget`, reading `data-*` attributes from the trigger, following the `denyModal` idiom in `ShopManagement/Index.cshtml`. No AJAX, no global state object.
3. **Null-posting mechanism** — a `type="button"` Remove control that clears `required`, empties and then **disables** the select before submitting the form programmatically. A disabled control is excluded from submission entirely, so `characterId` arrives absent and binds to null; nothing is posted twice and constraint validation cannot block it.
4. **Status suffix wording** — the enum name in parentheses appended to the existing option text, produced by `Character.ToSelectLabel()`. Active characters keep today's exact option text, byte for byte.
5. **Ordering** — none added. `CharacterRepository.GetCharactersByOwnerIdAsync` already orders Main role first, then Active before inactive, then by name. Inactive entries sort to the bottom for free; no Razor-side ordering.
6. **Toast wording** — owned by plan 01 (`Character updated.` / `Character removed from your signup.` / `You are no longer signed up for this quest.`).

Two further choices made here: the modal drops the add-only informational banner carried in the source block (it now serves three actions, and the field label already says what to do), and the submit button carries a single neutral caption for all three paths rather than swapping text.
</discretion_decisions>

**Priming, on `show.bs.modal`:**
1. Read `event.relatedTarget`; return early if it is missing.
2. Read `questId`, `currentCharacterId` and `currentCharacterLabel` from the trigger's `dataset`, defaulting each to an empty string.
3. Write the quest id into `#characterSelectQuestId`.
4. Reset state left behind by a previous invocation, in this order: re-enable `#characterSelect`, restore its `required` flag, and remove any previously injected current-character option by its id `characterSelectCurrentOption`. This matters because one modal instance serves every row on the page and the Remove path disables the select.
5. If there is a current character id: look for an existing `option` in `#characterSelect` whose value matches it. **If none exists, create one** — id `characterSelectCurrentOption`, value set to the current character id, text content set to the label from the trigger (falling back to a neutral caption such as `Current character` when the label is empty) — and insert it directly after the placeholder option. Only then set `#characterSelect`'s value to the current character id.

   This inject-if-missing step is the structural guarantee that the dropdown's initial selection always matches the row the player clicked. Without it, assigning a value with no matching option silently leaves the select on the placeholder, and a Save the player believed was a no-op would clear their character.
6. If there is no current character id, set the select's value to the empty string so the placeholder is selected.
7. Toggle `d-none` on `#characterSelectRemoveBtn` so it is visible only when a current character id is present.
8. Set `#characterSelectModalTitle`'s `textContent` to `Change Character on Your Signup` when a current character id is present, and `Add Character to Signup` when it is not.

Use `textContent` rather than `innerHTML` anywhere the character label is written, so a character name can never be interpreted as markup.

1. Show a native `confirm()` with a question naming the action (for example, asking whether to remove this character from the signup) and return without doing anything if the player declines.
2. Clear the select's `required` flag, set its value to the empty string, then set its `disabled` flag. A disabled control is excluded from form submission entirely, so the field arrives absent and binds to null on the server — the already-working clear path.
3. Submit the form by calling `submit()` on `#characterSelectForm` directly. Calling `submit()` rather than clicking the save button is deliberate: it bypasses browser constraint validation, so no interaction between the select's state and its validity can block the clear.

Write short plain-language comments on the inject-if-missing step and on the disable-then-submit step explaining why each is done that way. No requirement IDs, phase numbers or plan IDs.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Trigger `data-*` attributes -> modal priming script | Client-side DOM values with no authority; they decide what the picker shows, never what the server accepts |
| Character-supplied text (name) -> option text and `data-current-character-label` | User-authored strings rendered into HTML |
| Modal form -> `QuestController.UpdateSignupCharacter` | The POST re-validated server-side by plan 01; nothing in this partial is a security control |

## STRIDE Threat Register

ASVS level 1; blocking threshold: high.

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-72-07 | Tampering | `#characterSelect` option list and injected current-character option | medium | mitigate | The option list is a convenience only. Every value posted is re-resolved server-side and checked for ownership and board scope by `UpdateSignupCharacter` (plan 01, T-72-01/T-72-02). A tampered option value therefore yields a 400, not a write. This partial adds no client-side trust. |
| T-72-08 | Tampering (stored XSS) | Character name rendered into option text and into `data-current-character-label` | medium | mitigate | Option text is emitted with Razor's `@` so it is HTML-encoded; the trigger attribute is likewise Razor-encoded in plans 03/04; the script writes the label with `textContent`, never `innerHTML`. `Html.Raw` is prohibited in this file by an acceptance criterion. |
| T-72-09 | Tampering (CSRF) | `#characterSelectForm` | medium | accept | `asp-action` on a `method="post"` form emits the antiforgery token automatically, and the action carries `[ValidateAntiForgeryToken]`. The Remove path submits this same form, so the token travels with it — do not replace the form submit with a hand-built fetch. |
| T-72-10 | Denial of Service (self-inflicted data loss) | Silent character wipe on a no-op save | high | mitigate | Task 3's inject-if-missing step guarantees the select's value equals the signup's character on open, so a Save that touches nothing re-posts the same id. Backed server-side by plan 01's `UpdateSignupCharacter_Post_ResubmittingTheCurrentRetiredCharacter_LeavesItAssigned`. |
| T-72-SC | Tampering | npm/pip/cargo installs | high | accept | This phase installs zero packages; no task runs a package-manager install. No legitimacy checkpoint required. |
</threat_model>
