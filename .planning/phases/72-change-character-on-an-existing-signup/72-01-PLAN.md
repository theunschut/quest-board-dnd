<research_correction_notice>
CONTEXT.md D-13 describes a live cross-board hole in `UpdateSignupCharacter`. **There is no such hole.** `CharacterEntity` carries a global EF Core `HasQueryFilter` scoped to the active board (`QuestBoard.Repository/Entities/QuestBoardContext.cs:328-331`) that applies to every `Characters` query, including `GetCharactersByOwnerIdAsync` and `GetCharacterWithDetailsAsync`. A cross-board `characterId` already resolves to `null` and is already rejected by the existing `character == null` check.

The explicit board check in Task 2 still ships, unchanged, as documented defense-in-depth: insurance against a future refactor calling `IgnoreQueryFilters()` on a `Characters` query, which several SuperAdmin-facing flows already do for `Quest`/`ShopItem`. It mirrors the identical belt-and-suspenders check in `RemovePlayerSignup` (`QuestController.cs:640-646`).

Consequence for Task 3: the cross-board test will pass whether or not the explicit check exists, because the query filter fires first. Write it knowing that, and label it in the test's own doc comment as a boundary regression test, not as proof of the explicit check. The **same-board, different-owner** case in Task 1 is the genuinely isolatable, load-bearing half of the ownership requirement.
</research_correction_notice>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser form POST -> `QuestController.UpdateSignupCharacter` | `questId` and `characterId` arrive fully attacker-controlled; the modal's pre-selected value is a client-side hint with no authority |
