<objective>
Give the mobile quest Details page the same character change and clear capability the desktop page gets — from the same shared modal, with the same trigger contract — and prove the new markup is genuinely being served rather than silently falling through to the desktop view.

Purpose: mobile is where this feature matters most and where it currently does not exist at all. The character is plain text today with no control of any kind. Shipping it in the same phase as desktop is deliberate: splitting them is how the two platforms drift apart, which is the recorded lesson from earlier phases, and this repo already carries a live case of mobile markup that is never selected.

Output: `Details.Mobile.cshtml` rendering the shared partial with inline triggers on both row types, and a real-User-Agent integration test file that fails if the mobile view stops being selected.
</objective>

<ordering_note>
The roadmap's internal order reads partial first, then desktop, then mobile. The partial-first half is a hard dependency and is honoured: this plan cannot start before plan 02 exists. The desktop-before-mobile half was protection against the two platforms diverging on behaviour. That protection is now structural rather than sequential — plan 02 fixed the trigger attribute vocabulary, the modal element ids and the option-label function before either host view was touched, so both host views are wiring against one frozen contract. This plan therefore runs alongside plan 03 in the same wave; it modifies a disjoint set of files and must not edit `Details.cshtml` or plan 03's test file.

If any part of the contract turns out to need changing while wiring mobile, change it in the partial and update **both** host views in the same commit. Do not add a mobile-only attribute, a mobile-only modal, or a mobile-only script.
</ordering_note>

**Both row types get the same edit.** In the participant row and in the waitlist row, replace the single expression that renders either the character name or the no-character text with an explicit two-branch block **inside the existing small element**, keeping the small element, the line break before it, and the outer two-column flex div exactly as they are.

1. **Filled state** — render the character name as text, then, guarded only by `isCurrentUser` and nothing else, append the trigger:

   `<button type="button" class="btn btn-link p-0 border-0 align-baseline lh-1 ms-2 text-info" data-bs-toggle="modal" data-bs-target="#characterSelectModal" data-quest-id="@Model.Quest?.Id" data-current-character-id="@row.Character.Id" data-current-character-label="@row.Character.ToSelectLabel()" title="Change character"><i class="fas fa-edit fa-xs"></i></button>`

   substituting the row's own iteration variable for `row` (`participant` in the participant row, `player` in the waitlist row).

   The class list is load-bearing and must not be simplified to the desktop's `btn btn-sm btn-primary`: `p-0` and `border-0` remove the button box, `lh-1` stops the glyph from setting the line box height, `align-baseline` keeps it sitting on the same baseline as the character name, and `fa-xs` keeps the glyph smaller than the surrounding small text. Together these are what keep the row height unchanged. A padded button inside a small element grows the line box, which is exactly the regression this must avoid.

2. **Empty state** — render the existing no-character text, then, guarded by `isCurrentUser` **and** the character list being non-empty (mirroring the desktop empty-state condition), append the same trigger shape with `text-success` instead of `text-info`, a plus glyph instead of the pencil glyph, `title="Add character"`, and both `data-current-character-id` and `data-current-character-label` set to the empty string. Keeping the add and change states on separate glyphs is deliberate — they are two states of one control family, not one ambiguous button.

   For the filled state there is deliberately **no** check on how many characters the player owns: a character is already set, so there is always something to do — change it or clear it. Gating it on the owned-character count is what would lock a player out of clearing an inactive character.

3. **Render the shared modal exactly once**, at the very end of the body markup, immediately before the Scripts section opens: `@{ await Html.RenderPartialAsync("_CharacterSelectModal"); }`. One instance serves every row on the page; the partial carries its own script, so nothing needs to be added to the Scripts section.

Do not change the outer row div's class list, do not add a third column, and do not make the row itself a tap target — an invisible whole-row affordance was explicitly rejected and would be a new pattern in this codebase.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Rendered row data -> trigger `data-*` attributes | Character names and ids from the database rendered into HTML attributes on the mobile page |
| Request User-Agent -> `MobileDetectionMiddleware` -> view selection | An attacker-controlled request header decides which view file renders; it must never decide what data is returned |
| Trigger -> shared modal -> POST | Client-side only; the server re-validates every posted `characterId` (plan 01) |
| Other players' rows -> the acting player's browser | The mobile page already renders every participant's character name; this task must not add a control on rows the viewer does not own |

## STRIDE Threat Register

ASVS level 1; blocking threshold: high.

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-72-13 | Elevation of Privilege | Change trigger rendered on a mobile row the viewer does not own | high | mitigate | Both filled-state triggers are guarded by `isCurrentUser`, computed from the view's `currentUserId` local against the row's player id. Proved by `MobileDetails_MobileUserAgent_ForAnotherPlayersRow_RendersNoTriggerForThatRow`. Even if the guard were bypassed, `UpdateSignupCharacter` resolves the signup from the authenticated user and never from a posted id (plan 01, T-72-05). |
| T-72-14 | Spoofing | Forged User-Agent selecting a different view | low | accept | The platform split chooses a template only. Both templates render the same model produced by the same authorized controller action, with the same board and ownership scoping. A spoofed User-Agent yields a differently-styled page, never additional data. Documented here so a future reader does not mistake the split for an authorization boundary. |
| T-72-08 | Tampering (stored XSS) | Character name rendered into `data-current-character-label` and into option text on the mobile page | medium | mitigate | Both are emitted through Razor's `@`, which HTML-attribute-encodes; the label originates from `ToSelectLabel`, a plain string builder with no markup. `Html.Raw` is not used in the touched blocks, and the partial's script writes labels with `textContent`. |
| T-72-07 | Tampering | Client-supplied `characterId` from a hand-edited trigger attribute | medium | mitigate | Trigger attributes carry no authority. Ownership and board scope are enforced server-side on every POST (plan 01, T-72-01/T-72-02). |
| T-72-12 | Information Disclosure | Widened mobile picker exposing other players' or other boards' characters | low | accept | The list is owner-filtered in the controller and board-filtered by the entity's global query filter; widening only added the viewer's own inactive characters. No new disclosure surface on either platform. |
| T-72-SC | Tampering | npm/pip/cargo installs | high | accept | This phase installs zero packages; no task runs a package-manager install. No legitimacy checkpoint required. |
</threat_model>
